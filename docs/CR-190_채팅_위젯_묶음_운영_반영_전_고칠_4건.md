### 5.3 로컬 확인

- 문법: 고친 안 그대로를 운영과 같은 nginx 1.18.0 컨테이너로 `nginx -t`. 「syntax is ok」, 「test is successful」. 인증서 경로에는 시험용 자체 서명 인증서를 붙였다.
- 동작: 1.18.0 컨테이너는 맥(arm64)에서 요청을 받으면 작업 프로세스가 죽어(signal 11, 지금 운영 설정도 같음) 동작 시험은 nginx 최신판 컨테이너로 했다. 지금 운영 설정(옛)과 고친 안(새)을 각각 4절 1, 2 의 새 판 api 앞에 두고 같은 요청을 보냈다. 넘기는 곳만 `127.0.0.1:8280` 에서 시험 api 로 바꿨다.

| 순번 | 요청 | 옛 설정 | 고친 안 | api 직접 |
|---|---|---|---|---|
| 1 | `GET /share/<테넌트>/<없는 값>` | nginx 404 | api 404 | api 404 |
| 2 | 구독(토큰 없음, 틀린 토큰) | nginx 404 | api 403 | api 403 |
| 3 | 승인 `POST .../approve`(토큰 없음) | nginx 404 | api 403 | api 403 |
| 4 | 런 목록, 중지, 단계 기록 | nginx 404 | nginx 404 | api 403 |
| 5 | 음성 웹소켓 전환 요청 | 400(전환 안 됨) | 101 | 101 |

| 8 | 그 밖 `/api/v1/connections` | nginx 404 | nginx 404 | api 403 |

세 길이 api 에 닿고(1, 2, 3, 5), 열지 않은 길은 그대로 막히며(4, 8), 기존 길은 그대로다(6, 7). 구독 스트림이 실제로 흘러가는지는 토큰과 실행 중인 런이 있어야 해 보지 않았다. 버퍼링 설정은 운영에서 도는 대화 길 블록과 같다.

IR-002 7절 9번은 구독 주소가 api 의 401 을 준다고 적었는데, 토큰이 없거나 틀리면 api 는 403 을 준다(위 2). 배포 뒤 확인은 「nginx 404 가 아닌 api 응답」 으로 본다.

### 5.4 운영 적용 절차 (승인 뒤)

nginx 다시 읽기는 끊김이 없다. api 배포보다 먼저 해도 된다(IR-002 5절 1). 그때는 옛 api 가 답하므로 공유 링크와 음성은 api 의 거부나 404 가 나오고, 새 api 가 올라가면 열린다.

1. 고친 안을 서버 `/tmp/ai.banpoom.co.kr.conf` 로 보낸다.
2. `sudo cp -p /etc/nginx/sites-available/ai.banpoom.co.kr.conf /etc/nginx/sites-available/ai.banpoom.co.kr.conf.bak-<시각>` (sites-enabled 에는 .conf 연결만 있어 백업본은 읽히지 않는다)
3. `sudo install -m 644 /tmp/ai.banpoom.co.kr.conf /etc/nginx/sites-available/ai.banpoom.co.kr.conf`
4. `sudo nginx -t && sudo systemctl reload nginx`. `nginx -t` 가 실패하면 3 의 백업본을 되돌리고 다시 읽지 않는다.
5. 확인: `/share/x/y` 와 구독 주소가 nginx 404 가 아닌 api 응답, `/api/v1/connections` 는 nginx 404, 위젯 파일 200.
6. 되돌리기: 백업본을 제자리에 복사하고 `sudo nginx -t && sudo systemctl reload nginx`.

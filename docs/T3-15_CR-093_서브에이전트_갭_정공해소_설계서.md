## 0. 개요 / 한 줄

AGENT_CALL 서브에이전트가 Claude Code 수준에 거의 도달했음이 3자 벤치마크(Aimbase ↔ OpenClaude ↔ Claude CLI)로 입증된 상태에서, 코드 실측으로 드러난 **잔여 3개 갭**을 한 묶음으로 정공 해소한다. 갭 ① 도구 필터 미적용(즉시 패치), 갭 ② Plan FSM 자동 진입(설계 판단 필요), 갭 ③ Nesting 깊이 보호(실측 → 차단).

## 2. T2 — 아키텍처 설계

### 2.1 갭 ① 해소 — 도구 필터 전달 경로

```
SubagentRunner.executeAgent
  └─ AgentTypeRegistry.getConfig(agentType)
       └─ AgentTypeConfig.allowedTools() : String[]
  └─ ChatRequest 생성 시 toolFilter 필드에 ToolFilterContext 주입
       └─ ToolFilterContext(allowedTools=allowedTools, excludeTools=null, ...)
  └─ OrchestratorEngine.chat(request) 그대로 위임
       └─ ToolCallHandler가 SessionToolRegistry 거쳐 필터링
```

**핵심 수정 지점**: `SubagentRunner.executeAgent()` ChatRequest 생성 직전.

```java
// 추가:
String[] allowedTools = agentTypeRegistry.getConfig(req.agentType()).allowedTools();
ChatRequest.ToolFilter toolFilter = allowedTools != null
    ? new ChatRequest.ToolFilter(List.of(allowedTools), null, null)
    : null;

ChatRequest chatRequest = new ChatRequest(
    req.model(),
    context.getChildSessionId(),
    messages,
    false, true,
    null, null,
    req.connectionId(),
    toolFilter,  // ← 기존 null
    null,
    responseFormat
);
```

**ChatRequest.ToolFilter 정의 확인 후 시그니처 정확 매칭 필요.** 만약 ChatRequest에 toolFilter 필드 없으면 추가하거나 ToolFilterContext 별도 경로 사용 — T3에서 확정.

### 2.2 갭 ② 해소 (A안 채택 시) — Plan FSM 자동 진입

```
SubagentRunner.executeAgent (agentType == PLAN)
  └─ PlanService.createPlan(parentSessionId, childSessionId) → planId
  └─ SubagentContext.planId = planId
  └─ OrchestratorEngine.chat 결과 받은 후:
       └─ PlanService.transitionTo(planId, VERIFYING)
       └─ 자식 응답을 plan_steps로 파싱 → 저장
       └─ 최종 PlanService.transitionTo(planId, ABANDONED|COMPLETED)
```

**판단 요점**:
- A안: FSM 자동 진입 → 검증 단계 누락 불가 / 단점: 모든 PLAN 호출이 PlanService 부담
- B안: 현 상태 유지 (프롬프트 강제만) → 단점: 모델 자율 실패 시 검증 누락

**권장**: 사용자에게 A/B 선택 요청 (실측 미완 = 두 안의 품질 차이 측정 안 됨)

### 2.3 갭 ③ 해소 — Nesting 깊이 보호

**Step 1 — 실측 확인** (선행):
- 자식 세션의 SessionToolRegistry에 AgentTool/Task 도구 노출되는지 코드 추적
- 노출 안 되면 갭 아님 — 메모리 정정만으로 종결

**Step 2 — 노출 시 차단** (조건부):

```
SubagentContext에 depth: int 필드 추가
  └─ 부모 SubagentContext의 depth + 1로 초기화 (없으면 0)
SubagentRunner.run 진입 시점:
  └─ depth > BIZ-109(3) 검사 → 초과 시 IllegalStateException
ChatRequest.metadata에 subagent_depth 전파
  └─ 자식 OrchestratorEngine이 ToolFilterContext에 자기 호출 차단 (depth+1 > 3 시 AgentTool exclude)
```

**런타임 차단 위치**:
- SubagentRunner.run() 시작 시 깊이 검사
- 또는 AgentTool/Task 실행 시점에 SessionToolRegistry가 depth 기반 차단

### 3.2 단위 테스트 시나리오

#### 갭 ①
- `should_filter_tools_for_PLAN_agent`: PLAN 자식 도구 목록에 BashTool 없음 검증
- `should_allow_all_tools_for_GENERAL`: GENERAL은 allowedTools null → 필터 미적용
- `should_filter_tools_for_VERIFICATION`: read/search/glob/grep만 노출

#### 갭 ② (A안 시)
- `should_create_plan_for_PLAN_agent`: PlanService.createPlan 호출됨 + planId 컨텍스트 주입
- `should_transition_to_VERIFYING_on_completion`: 자식 응답 후 상태 전이
- `should_not_create_plan_for_non_PLAN`: GENERAL/EXPLORE 등은 Plan 생성 안 함

#### 갭 ③
- `should_allow_depth_1_to_3`: 부모(0) → 자식(1) → 손자(2) → 증손자(3) 정상
- `should_block_depth_4`: 4단계 호출 시 IllegalStateException("subagent depth exceeded")
- `should_propagate_depth_via_metadata`: ChatRequest.metadata.subagent_depth 전파

## 3. 서버

### 3.1 승인을 받을 도구 정하기 [PRD-563, BIZ-240]

- 정책의 `match_rules` 에 `tools`(도구 이름 목록)를 새로 둔다. `tools` 가 있는 정책은 도구 호출에만 걸리고, 없는 정책은 지금처럼 작업(ACTION) 평가에만 걸린다. 두 평가가 서로의 정책을 보지 않는다
- 도구 호출 평가: 켜진 정책을 우선순위 높은 순으로 보고, `tools` 에 그 도구 이름이 있는 정책의 규칙 가운데 처음 나온 REQUIRE_APPROVAL 또는 DENY 에서 멈춘다(BIZ-005 와 같은 순서)
  - REQUIRE_APPROVAL: 승인을 묻는다. 규칙의 `message` 가 카드의 안내 문구가 된다
  - DENY: 실행하지 않고 규칙의 `message` 를 도구 오류 결과로 돌려준다
- 묻는 도구는 정책으로만 정한다. 도구 계약의 승인 필요 표시(`approvalRequired`)는 보지 않는다. 지금 이 표시가 있는 도구는 `http_request` 하나이고 워크플로우와 에이전트가 사람 없이 부른다. 표시로 묻게 하면 위젯 대화 밖의 그 호출이 모두 막힌다(BIZ-241). 9.2 의 10번(정책 없는 테넌트는 지금 그대로)과도 맞춘다 [설계보정 2026-11-13, 구현 전 코드 확인]
- 평가는 `PolicyEngine.evaluateToolCall(toolName, sessionId)` 로 따로 둔다. 기존 `evaluate(ActionRequest)` 는 `tools` 가 있는 정책을 건너뛴다
- `tools` 가 빈 목록인 정책은 저장하지 않는다(400 `policy_tools_empty`). 빈 목록이 작업 평가로 흘러 모든 요청에 걸리는 일을 막는다

### 3.2 대화 중 승인 흐름 [PRD-560, BIZ-241 ~ BIZ-243, BIZ-246]

서버 도구가 실행되는 길이 모두 지나는 두 자리에 같은 승인 관문(`ToolApprovalGate`)을 둔다.

| 순번 | 자리 | 지나는 길 |
|---|---|---|
| 1 | ToolRegistry 의 도구 실행(`execute`, `executeInSession`), 입력 검증 다음 | API 연결 대화(스트림, 비스트림), 서브에이전트, 원격 트리거 도구, 워크플로우 도구 단계(TOOL_CALL), 예약 실행, 관리 화면 도구 실행과 도구 시험 |
| 2 | ServerMcpToolDispatcher 의 도구 실행, PRE_TOOL_USE 훅 다음 | Claude CLI 연결(CLI 가 서버 MCP 로 부르는 도구). 이 길은 ToolRegistry 를 거치지 않고 도구를 바로 실행한다 |

- 설계보정 2026-11-13: 처음 설계는 1 자리를 ToolCallHandler 에 두었다. 그러면 원격 트리거 도구, 워크플로우 도구 단계, 예약 실행, 관리 화면 도구 실행이 정책과 상관없이 묻지 않고 실행되어 BIZ-241 과 어긋난다([기록/CR-185_승인문_빠진_실행길.md](기록/CR-185_승인문_빠진_실행길.md)). 공통 지점으로 옮겼다(사용자 06:29 권장안 승인을 컨타에 위임, 컨타 승인)
- 테넌트가 없는 실행(서버 점검용 도구 시험)은 정책을 보지 않고 실행한다. 정책은 테넌트 DB 에만 있다

관문의 순서:

1. 3.1 평가가 ALLOW 면 그대로 실행한다
2. DENY 면 실행하지 않고 도구 오류 결과(`message`)를 돌려준다
3. REQUIRE_APPROVAL 이면 그 세션에 열린 대화 턴(`ChatTurnRegistry`)을 찾는다
   - 세션 번호: API 연결은 도구 문맥의 세션, CLI 연결은 머리글 `X-Aimbase-Session-Id`(3.6)
   - 열린 턴이 없으면(스트림이 아닌 대화, 워크플로우 단계와 도구 단계, 예약 실행, 원격 트리거 도구, 관리 화면 도구 실행, 서브에이전트, 바깥 MCP 호출) 물을 사람이 없다. 실행하지 않고 「승인이 필요한 도구라 위젯 대화에서만 실행할 수 있습니다」 오류 결과를 돌려준다(BIZ-241)
4. pending_approvals 에 한 줄을 만든다(`approval_channel=chat`, 세션, 도구 이름, 입력, 요청한 사람 = 턴을 연 사용자, 마감 = 지금 + `chat.approval-timeout-seconds`)
5. 턴의 스트림으로 `approval_required` 를 보낸다(3.5)
6. 결정을 기다린다. 기다리는 동안 15초마다 스트림에 주석 줄(keep-alive)을 보낸다
7. 결과에 따라
   - 승인: 도구를 실행하고 결과를 그대로 돌려준다
   - 거절: 실행하지 않고 도구 오류 결과 「사용자가 실행을 거절했습니다」. AI 는 이것을 받고 응답을 잇는다
   - 시간 지남: 상태 `timeout`, 도구 오류 결과 「승인 시간이 지나 실행하지 않았습니다」. AI 가 응답을 잇는다
   - 응답 중지(abort) 또는 스트림 끊김: 상태 `cancelled`, 실행하지 않고 턴을 끝낸다
8. 정해지면 같은 스트림으로 `approval_resolved` 를 보낸다

- 승인이 필요한 도구는 병렬 실행 묶음에서 빼 차례로 실행한다. 한 응답에서 여럿을 부르면 부른 순서대로 하나씩 묻는다
- 대화 턴 등록부(`ChatTurnRegistry`)는 스트림을 열 때 세션 번호, 턴을 연 사용자(토큰 `user_ref`, 없으면 주체 id), 스트림 보내기 함수를 올리고 done 이나 오류에서 내린다. 기다림은 메모리 안 결정 대기(Future)로 하고, 결정 API 가 그것을 깨운다. 응답 중지 등록부(CancellationRegistry)와 같이 한 서버 안에서 동작한다
- 실행기, 스트림, 실행기 호출 한도가 모두 300초라 승인 기다림은 그보다 짧아야 한다. `chat.approval-timeout-seconds` 는 10 ~ 240 만 받는다(BIZ-242)

### 3.3 대화 승인 결정 API [PRD-560, PRD-562, BIZ-243, BIZ-245]

`POST /api/v1/chat/approvals/{approvalId}` (권한 `chat:stream` 또는 로그인)

```json
{ "decision": "approve" }        // approve | reject
```

| 결과 | 응답 |
|---|---|
| 정함 | 200 `{ approval_id, status, decided_by, decided_at }` |
| decision 이 approve, reject 가 아님 | 400 `invalid_decision` |
| 없는 승인 또는 다른 테넌트 | 404 `approval_not_found` |
| 요청한 사람이 아니고 관리자도 아님 | 403 `not_requester` |
| 이미 정해짐(승인, 거절, 시간 지남, 중지) | 409 `approval_closed`, `data.status` 에 지금 상태 |
| 대화 승인이 아님 | 400 `not_chat_approval` |

- 바꾸기는 `status='pending'` 일 때만 되는 한 번의 갱신으로 한다. 둘이 함께 눌러도 하나만 지난다
- 정한 사람(`approved_by`)은 토큰 주체로 남긴다. 감사 기록(BIZ-020)에 `APPROVAL_DECIDED` 를 남긴다

### 3.4 워크플로우 승인 막기 [PRD-561, PRD-562, BIZ-244, BIZ-245]

- `POST /api/v1/workflows/runs/{runId}/approve`
  - 위젯 토큰은 권한 `workflow:approve` 가 있어야 한다. 없으면 403 `scope_required`
  - 그 단계의 승인자 목록이 있으면 토큰 `user_ref` 가 목록에 있어야 한다. 없으면 403 `not_approver`
  - 로그인(관리 화면) 토큰과 API 키는 지금처럼 정한다
  - 정한 사람을 남긴다(`approved_by`, `resolved_at`)
  - 실행 상태 `pending_approval` 에서 바꾸는 갱신을 한 번에 한다. 이미 바뀌었으면 409 `approval_closed`
- `workflow:approve` 는 위젯 기본 허용 권한(`widget.allowed-scopes` 기본값)에 넣지 않는다. 테넌트가 런타임 설정에 넣고, 붙이는 앱이 토큰을 받을 때 요청해야 열린다
- 관리자 승인 API(`/api/v1/admin/approvals/{id}/approve|reject`)는 정한 사람을 요청 본문이 아니라 로그인 주체로 남긴다. 대화 승인(`chat`)도 이 API 로 정할 수 있고, 같은 결정 처리(3.3)를 탄다
- 승인 대기 마감 정리(ApprovalTimeoutSweeper)는 대화 승인도 맡는다. 서버가 다시 떠서 기다리던 턴이 사라진 대화 승인은 마감이 지나면 `timeout` 으로 닫는다

### 3.5 대화 스트림 이벤트 [PRD-560]

| 이름 | 언제 | 내용 |
|---|---|---|
| `approval_required` | 승인을 묻기 시작 | `approval_id`, `tool_use_id`, `tool_name`, `description`(도구 설명 첫 줄), `input`(값마다 2,000자에서 자름), `message`(정책 안내 문구, 없으면 빠짐), `expires_at`(ISO, 시간대 포함), `timeout_seconds` |
| `approval_resolved` | 정해짐 | `approval_id`, `status`(approved, rejected, timeout, cancelled), `decided_at` |

- 위젯 본체는 두 이름을 모르므로 틀의 `streamEvent` 로 승인 기능 파일에 간다
- 붙이는 앱이 위젯 없이 스트림을 직접 읽는 경우도 같은 이벤트를 받는다(API 가이드)

### 3.6 CLI 실행기 [PRD-560]

- 실행기가 서버 MCP 항목 머리글에 `X-Aimbase-Session-Id: <run 번호>` 를 더한다(작업장, 스킬 머리글을 넣는 같은 자리). 대화에서는 run 번호가 대화 세션 번호다
- CR-183(데이터 파일 도구)이 같은 이름, 같은 자리의 머리글을 설계했다(CR-183 3절). 먼저 구현하는 CR 이 넣고 다른 CR 은 그것을 쓴다. 이름을 따로 두지 않는다
- 서버의 요청 필터(AgentIdRequestFilter)가 이 머리글을 요청 문맥(RequestContext)에 옮기고, ServerMcpToolDispatcher 가 관문에 세션 번호로 준다
- 실행기가 CLI 에 도구 호출 한도 `MCP_TOOL_TIMEOUT` 을 넘긴다(실행기 설정 `aimbase.runner.mcp-tool-timeout-seconds`, 기본 300초). CLI 기본값 60초로는 승인 대기가 1분을 넘을 때 호출이 먼저 끊겨 AI 가 시간 초과로 답을 끝낸다(59 확인 중 발견)
- 실행기를 새로 배포해야 CLI 연결에서 카드가 뜬다. 옛 실행기에서는 머리글이 없어 열린 턴을 못 찾고 BIZ-241 대로 실행하지 않는다(승인 없이 실행되는 일은 없다)

### 4.2 동작

| 순번 | 무엇 | 동작 |
|---|---|---|
| 1 | 도구 카드 띄우기 | `streamEvent` 의 `approval_required` 를 받으면 카드를 만들어 `mount` 한다. 남은 시간은 `expires_at` 기준으로 1초마다 줄인다 |
| 2 | 승인, 거절 | 누르면 두 단추를 잠그고 3.3 을 부른다. 성공하면 결과 줄(「승인했습니다」, 「거절했습니다」와 시각). 409 면 서버 상태로 결과 줄. 그 밖의 실패면 단추를 풀고 카드 아래 「승인 결과를 보내지 못했습니다」 |
| 3 | 결과 받기 | `approval_resolved` 를 받으면 같은 카드를 결과 줄로 바꾼다(관리자가 정했거나 시간이 지난 경우 포함) |
| 4 | 응답 중지 | 기다리는 카드가 있는 채로 `answerDone`(중지, 오류)을 받으면 「응답을 중지해 실행하지 않았습니다」 |
| 5 | 워크플로우 카드 | `workflowApproval` 을 받으면 카드를 `mount` 한다. 토큰 내용의 `scopes` 에 `workflow:approve` 가 없거나, 승인자 목록이 있는데 `user_ref` 가 없으면 단추 대신 「승인자만 정할 수 있습니다」. 누르면 3.4 를 부르고 403 이면 같은 안내, 409 면 「이미 다른 사람이 정했습니다」 |
| 6 | 워크플로우 결과 | 워크플로우 진행 칸이 끝나면(틀 `workflowDone`) 이 사용자가 정하지 않은 카드를 결과 줄로 닫는다. `code` 가 `approval_timeout` 이면 「마감이 지나 실패했습니다」, 그 밖의 완료, 실패, 취소는 「이미 다른 사람이 정했습니다」 |
| 7 | 키보드 | 카드 단추는 Tab 으로 가고 Enter, Space 로 누른다. Esc 는 위젯 본체의 응답 중지를 그대로 쓴다 |

### 4.3 붙이는 앱 옵션

| 옵션 (JS / 속성) | 바뀌는 것 |
|---|---|
| `allowApproval` / `allow-approval` | 기본값을 false 에서 true 로 바꾼다. false 면 워크플로우 카드에 단추 없이 안내만 두고 지금처럼 `onApprovalRequired` 만 알린다. 대화 중 도구 카드는 이 옵션과 상관없이 뜬다(서버가 기다리므로 끌 수 없다) |

## 5. 관리 화면 [FE-130]

- Policies(`/policies`) 정책 만들기 창에 규칙 타입 「도구 실행 전 승인」을 더한다
  - 대상 도구: 여러 개 선택. 목록은 `GET /api/v1/tools` 의 이름과 설명. 하나도 선택하지 않으면 칸 아래 「도구를 하나 이상 선택하세요」
  - 안내 문구(선택): 규칙의 `message`
  - 저장 모양: `match_rules = { "tools": [...] }`, `rules = [{ "type": "REQUIRE_APPROVAL", "message": "..." }]`
- 정책 목록 행에 `tools` 가 있으면 「대상 도구: a, b」를 함께 보인다
- 새로 넣는 칸은 디자인시스템 컴포넌트로 만든다. 기존 칸은 이 건에서 고치지 않는다

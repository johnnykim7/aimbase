# CR-143: 워크플로우 LLM_CALL 구조화 출력 검증과 재시도 설계

- 발번: 2026-10-10
- 원본 요구사항: `docs/origins/원본_요구사항_CR143_워크플로우_구조화출력_검증재시도_20261010.md`
- 관련 규칙: BIZ-033, BIZ-034
- 상태: 설계 확정

---

## 1. 문제

워크플로우 LLM_CALL 은 response_schema 를 선언해도 결과가 스키마를 만족하는지 보지 않는다.
CLI·OpenAI·Ollama 경로는 어댑터 출구에서 텍스트를 JSON 으로 바꿔 보는데(CR-113), 실패하면 경고 로그만 남기고
원문 텍스트를 그대로 돌려준다. LLM_CALL 은 이를 받아 `structured_data` 없이 성공으로 끝낸다.

그 결과 run 은 `completed` 인데 소비앱이 읽을 결과가 비어 있다. BIZ-034(검증 실패 시 2회 재시도, 이후 에러 반환)가
채팅 경로에만 구현되어 있고 워크플로우 경로에는 없다.

## 2. 실측 근거

| 항목 | 위치 |
|---|---|
| 채팅 경로의 BIZ-034 구현(파싱, 검증, 2회 재시도) | `OrchestratorEngine.validateAndConvertStructuredOutput` (orchestrator/OrchestratorEngine.java:811) |
| 어댑터 출구 정규화, 실패 시 원문 유지 | `StructuredOutputNormalizer.normalize` (llm/adapter/StructuredOutputNormalizer.java:76-80) |
| LLM_CALL 결과 조립, structured_data 없으면 생략 | `LlmCallStepExecutor.buildResult` (workflow/step/LlmCallStepExecutor.java:617) |
| CLI 워커는 마지막 USER 메시지부터만 보내고 이전 대화는 세션이 보유 | `ClaudeCliWorker.trimToCurrentTurn` (cli-runner) |
| CLI 워커는 run 단위로 유지 | `ClaudeCliWorkerPool` runs.computeIfAbsent(runId) |

## 3. 설계

LLM_CALL 이 Phase 1 또는 Phase 2 에서 잘리지 않은 응답을 받으면, response_schema 가 있을 때 결과 조립 전에 검증한다.

1. 판정: `ContentBlock.Structured` 가 있고 `SchemaValidator.validate(schema, data)` 를 통과하면 성공
2. 실패 사유
   - Structured 가 없으면 원문을 펜스 제거 후 직접 파싱해 본 오류 메시지(위치 포함)
   - Structured 가 있으나 검증 실패면 검증 오류 목록
3. 재요청: 채팅 경로와 같은 방식으로 대화 이력에 직전 응답(ASSISTANT)과 교정 지시(USER)를 덧붙여 같은 어댑터로 다시 호출한다.
   - API 경로는 이력 전체가 전달된다
   - CLI 경로는 워커가 마지막 USER 만 보내지만 같은 run 의 세션이 앞 대화를 가지고 있어 맥락이 이어진다
   - max_tokens, extended thinking 설정은 원 호출과 같다
4. 최대 2회 재요청 후에도 실패하면 예외를 던져 스텝을 실패시킨다. 메시지에 BIZ-034 와 마지막 실패 사유를 담는다.
5. 재요청 응답도 LLM_RESPONSE 이벤트로 적재한다 (CR-090, CR-102 와 같은 기록).

엔진의 스텝 재시도(errorHandling.retryMaxAttempts)는 그대로 적용된다. 최악의 호출 수는
(retryMaxAttempts + 1) x 3 이므로, 출력이 긴 워크플로우는 retryMaxAttempts 를 낮게 둔다.

## 4. 범위 밖

- 채팅 경로는 2회 재시도 후에도 실패하면 원문 텍스트를 돌려준다. BIZ-034 의 "에러 반환" 과 다르지만,
  채팅 소비앱의 응답 계약이 바뀌므로 별도 결정으로 둔다.
- Phase 3 자동분할의 병합 결과, AGENT_CALL, TOOL_CALL 의 response_schema 는 이번에 다루지 않는다.

## 5. 영향

response_schema 또는 워크플로우 outputSchema 를 쓰는 모든 테넌트의 LLM_CALL 이 대상이다.
지금까지 형식이 깨진 결과가 `completed` 로 나가던 경우가 재요청 후 성공하거나 `failed` 로 바뀐다.
정상 응답은 검증 1회만 추가된다.

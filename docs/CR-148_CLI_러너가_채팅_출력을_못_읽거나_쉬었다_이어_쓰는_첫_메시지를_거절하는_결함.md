## 1. 문제

CLI 연결(Max 구독 러너)로 채팅할 때 두 가지가 일어난다.

1. 한 CLI 워커가 살아 있는 동안 다른 채팅을 열면, CLI 는 답을 다 냈는데 러너가 그 출력을 읽지 못해 응답이 오지 않는다. 러너의 턴 시간 제한(600초)이 지나서야 끊긴다
2. 한동안 쉰 채팅에 이어 쓰면 첫 메시지가 "turn() called before turnFirst()" 로 한 번 실패한다. 두 번째부터는 정상이다

워크플로우는 끝날 때 워커를 닫으므로 2는 겪지 않는다. 1은 워크플로우도 다른 워커가 살아 있으면 겪을 수 있다(확인 안 함).

## 2. 원인

### 2.1 CLI 출력 읽기가 실행 자리를 붙잡는다

| 항목 | 위치 |
|---|---|
| 워커마다 CLI 의 표준출력과 표준오류를 가상 스레드 2개로 읽는다 | `ClaudeCliWorker.start` (cli-runner/.../ClaudeCliWorker.java:235~240), `drainStdout` (:916~934) |
| 가상 스레드가 도는 자리(캐리어)는 CPU 수만큼이다. AWS 러너는 CPU 2개다 | AWS `nproc` = 2 |
| 2026-10-11 23:41Z 실측: 캐리어 스레드 2개가 모두 파이프 읽기(anon_pipe_read)에 묶여 있었고, 살아 있는 CLI 는 다른 채팅(cr150-tool-call3) 하나뿐이었다. 캐리어를 더 늘리지 않았다 | `/proc/<pid>/task/*/wchan` |

그래서 살아 있는 워커 하나가 두 자리를 다 차지하면 새 워커의 출력 읽기 스레드는 돌지 못한다.
같은 날 23:30 의 채팅(cr150-chat-read-1)은 CLI 세션 기록상 23:30:10 에 도구 호출과 답을 마쳤지만, 러너 로그에는 그 뒤로 아무 출력도 없었고 23:40:05 에 "turn timeout after 600s" 로 끝났다.

### 2.2 첫 턴 표시가 워커와 따로 논다

| 항목 | 위치 |
|---|---|
| 러너는 run 마다 첫 턴을 보냈는지를 따로 기억한다 | `RunnerService.firstTurnDone` (aimbase-agent/.../RunnerService.java:34, :149) |
| 쉬는 워커 정리(CR-121)는 워커를 닫고 풀에서 빼지만 이 표시는 지우지 않는다 | `ClaudeCliWorkerPool.reapIdleWorkers` (cli-runner/.../ClaudeCliWorkerPool.java:113~146) |
| 다음 호출은 새 워커를 띄우고, 표시가 남아 있으니 이어지는 턴으로 보낸다. 새 워커는 첫 턴을 받은 적이 없어 거절한다 | `ClaudeCliWorker.turnInternal0` (:333~337) |
| 실패 처리에서 표시를 지우므로 그다음 호출은 정상이다 | RunnerService.java:173 |

AWS 실측: cr150-tool-call3 워커가 21:37Z 에 정리됐고, 23:24Z 호출이 이 오류로 실패했으며, 23:25Z 재호출은 성공했다.

## 3. 설계 방향 (설계 때 확정)

1. CLI 출력과 오류 읽기를 일반(플랫폼) 데몬 스레드로 돌린다. 파이프 읽기는 오래 막히는 일이라 가상 스레드에 맞지 않는다
2. 첫 턴 여부는 run 단위 표시가 아니라 지금 쓰는 워커가 첫 턴을 받았는지로 정한다. 새 워커에는 대화 전체를 첫 턴으로 보낸다

## 4. 확인 계획

- 단위시험: 워커가 정리된 뒤 같은 run 호출이 첫 턴으로 가는지. 워커가 여럿일 때 출력 읽기가 서로 막지 않는지
- 로컬: CPU 를 2개로 제한한 러너에서 채팅 둘을 차례로 열어 둘 다 응답하는지. 쉬는 워커 정리 시간을 줄여 이어 쓰기가 첫 메시지부터 되는지

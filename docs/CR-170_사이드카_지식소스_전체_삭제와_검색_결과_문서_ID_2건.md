## 1. 배경

- AXOPM 운영이슈 ISS-82: 유사 이슈 검색이 0건이다. AXOPM IR-002 조사에서 원인 하나로 Aimbase 사이드카의 문서 넣기가 지식소스 전체를 지운다는 것을 찾았다. AXOPM 은 이슈를 하나씩 공용 지식소스 하나에 넣으므로 마지막에 넣은 이슈만 남는다

### 2.2 검색 응답 (2건)

`POST /knowledge-sources/search` 의 `data.results[]` 는 content, score, sourceId, sourceName, metadata 만 준다. score 는 재순위가 되면 cross-encoder 원점수, 안 되면 하이브리드 결합 점수(RRF)라 범위가 정해져 있지 않고 한 검색 안에서만 견줄 수 있다. 지금 59 에서는 재순위가 모두 실패해 결합 점수가 나간다(8절 1). 사이드카의 벡터 검색과 키워드 검색은 문서 ID 를 읽지 않고, 재순위는 content 와 metadata 만 남겨 벡터 유사도를 버린다.

## 3. 설계

### 3.1 지우는 범위 (1건)

| 순번 | 호출 | 지우는 범위 |
|---|---|---|
| 1 | 사이드카 `ingest_document`, 문서 ID 있음 | 그 지식소스의 그 문서만 |
| 2 | 사이드카 `ingest_document`, 문서 ID 없음 | 지식소스 전체(전과 같다). 문서 ID 로 지식소스 ID 를 쓰는 단일 문서 지식소스다 |
| 3 | 사이드카 `ingest_file` | 지식소스 전체(전과 같다). 파일을 읽은 뒤 지워 파일을 못 읽으면 기존 임베딩이 남는다 |
| 4 | BE 동기화, 사이드카 경로(모든 전략) | 모은 문서가 있으면 첫 문서 전에 한 번 전체를 지우고 문서마다 넣는다. 모은 문서가 없으면(`api` 유형) 지우지 않는다 |

`ingest-text` 의 BE 단계 문서 단위 삭제는 그대로 둔다. 사이드카와 겹치지만 결과가 같다.

### 3.2 검색 응답 칸 (2건)

| 칸 | 뜻 | 값 |
|---|---|---|
| `documentId` | 넣을 때 준 문서 ID | 문서 ID 없이 넣은 청크는 지식소스 ID. 알 수 없는 경로(부모-자식 검색)는 null |
| `vectorScore` | 질문과 청크의 코사인 유사도 | 0 ~ 1. 키워드로만 걸린 청크는 0, 음수는 0. 사이드카가 없는 경로도 코사인(1 - 거리) |

`score` 는 그대로 둔다. 사이드카는 벡터 검색과 키워드 검색 결과에 `document_id` 를 싣고, 하이브리드 결과에 `vector_score` 를 남기고, 재순위는 받은 칸을 지키고 `rerank_score` 만 더한다.

## 7. 이 건에서 고치지 않는 것

1. BE 의 parent_child 동기화가 자식 청크를 나누는 함수(`IngestionPipeline.splitFixed`)는 마지막 구간에서 시작점이 되풀이된다. 글이 50자 미만이면 예외로 그 문서가 실패하고, 50자 이상이면 끝나지 않을 수 있다. 운영 59 의 지식소스는 api 와 file 유형뿐이라 이 경로를 타지 않는다. 별건으로 고친다
2. 사이드카 경로 동기화는 `incremental` 설정을 쓰지 않는다. 전과 같다. 사이드카가 없는 경로만 해시로 바뀐 청크만 넣는다
3. 사이드카 호출 180초 시간초과와 재시도. 이 건으로 재시도해도 결과가 같아졌다

5. 부모-자식 검색 경로의 `documentId`, `vectorScore`. 검색 API 는 이 경로를 쓰지 않는다
6. AXOPM 공용 지식소스에서 이미 지워진 이슈를 다시 넣는 것. AXOPM CR-168 이 한다

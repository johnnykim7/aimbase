## 1. 문제

검사 반복(EVALUATOR_LOOP)은 회차마다 작성 LLM 과 검사 LLM 만 부른다. 통과 판정은 검사 LLM 이 낸 JSON 을 세 방식(SCORE_THRESHOLD, JSONPATH_MATCH, LLM_JUDGE)으로 읽는 것뿐이다(`EvaluatorLoopStepExecutor.java:260~262`).
「작성 결과의 법조문이 사건자료와 작성법에 글자 그대로 있는가」 같은 글자 대조는 LLM 이 놓친다. 2026-11-14 서면 61종 시험에서 검사 LLM 이 자료 밖 조문 3건을 통과시켰고, 조문 목록을 먼저 적게 한 보정도 실패했다. 같은 판정을 코드로 하면 잡힌다(Lexflow `check61.py`).
회차 안에서 코드를 돌릴 자리가 없어 지금은 이것을 막을 수 없다.

## 3. 바꾸는 것

1. 검사 반복 설정에 선택 묶음 `code_check` 를 더한다. 없으면 지금과 똑같이 돈다.
2. `code_check` 가 있으면 회차마다 작성 결과에 대조 스크립트를 돌리고, 그 결과를 회차 판정과 다음 작성 지적에 더한다.
3. 대조 스크립트는 스킬 묶음의 파일이다. 엔진이 입력 파일을 run 작업장에 쓰고 그 경로를 인자로 넘기며, 스크립트는 stdout 에 JSON 하나를 낸다(5절 규약).
4. 회차 기록(`iterations[].code_check`)에 대조 결과를 남긴다. 실행 상세 화면의 반복 이력에도 보인다.
5. 워크플로우 편집 화면이 `code_check` 를 글이 아니라 객체로 저장하게 한다(지금은 모르는 객체 칸을 글로 바꿔 저장한다, `ConfigPanel.tsx:149`).
6. 편집 화면이 숫자 칸(최대 반복 횟수, 처리 상한, 동시 실행, 타임아웃 등)과 원래 숫자, 참거짓이던 값을 글로 바꿔 저장하던 결함을 고친다. 빈 칸은 지워 기본값을 쓰게 한다. CR-055 부터 검사 반복은 편집 화면에서 저장하면 400 으로 막혔다(로컬 확인 중 발견, 결정 3).

### 설정 모양

```json
"code_check": {
  "skill": "lexflow-draft-checks",
  "version": 1,
  "script": "scripts/check_laws.py",
  "timeout_seconds": 30,
  "input": {
    "case": "{{input.case}}",
    "docType": "{{input.docType}}",
    "guide": "{{guide.output}}"
  }
}
```

| 칸 | 필수 | 뜻 |
|---|---|---|
| skill | 예 | 대조 스크립트가 든 스킬 묶음 이름. 테넌트 전용이 먼저다(BIZ-120) |
| version | 아니오 | 묶음 판. 없으면 단계가 시작할 때의 최신 판으로 고정해 모든 회차가 같은 판을 쓴다 |
| script | 예 | 묶음 안 스크립트 경로. 확장자는 `skills.runnable-extensions` 중 하나 |
| timeout_seconds | 아니오 | 회차당 실행 시간 한도. 없으면 `skills.script-timeout-seconds`(120), `skills.script-timeout-max-seconds`(600)를 넘으면 그 값으로 줄인다 |
| input | 아니오 | 스크립트에 넘길 값. 값마다 `{{...}}` 를 풀며, 참조 하나만 있는 값은 객체 그대로 넘긴다(사건자료 JSON 이 글로 바뀌지 않는다) |

## 4. 결정 (2026-11-15 09:08 둘 다 ①)

### 결정 1. 코드 대조의 자리와 LLM 검사를 건너뛸지

1. ① 코드 대조를 작성 바로 뒤, LLM 검사 앞에 돌리고 LLM 검사는 늘 돈다 (권장). 그 회차 통과는 코드 대조 통과이면서 지금의 통과 기준도 통과일 때다. 다음 작성에 넘기는 지적은 코드 대조 지적 다음에 LLM 지적을 이은 것이다. 근거: 반복이 최대 2회라 첫 회차에 판례, 날짜, 금액, 구성 순서 지적까지 모두 나와야 2회차에 고칠 수 있다(Lexflow 설계서 3.3 「첫 검사에서 모두 적는다」와 같은 이유). LLM 이 늘 돌면 앞뒤 순서는 판정에 영향이 없고, 코드가 빠르니 앞에 둔다.
2. ② 코드가 위반을 찾으면 그 회차 LLM 검사를 건너뛴다 (회차당 LLM 호출 1회를 아낀다. 잃는 것: 나머지 기준 지적이 한 회차 늦게 나와 2회 안에 고치지 못하고, 마지막 회차면 LLM 이 한 번도 보지 않은 초안이 나간다)

### 결정 2. 대조 스크립트가 실패하거나 시간을 넘을 때

실패는 종료 코드가 0 이 아님, 시간 초과, stdout 이 규약의 JSON 이 아님, 실행 컨테이너에 닿지 못함이다.

1. ① 그 회차는 통과로 치지 않고, LLM 지적만 넘겨 다음 회차로 간다 (권장). 마지막 회차면 지금처럼 마지막 초안을 내고 `loop_exhausted` 가 true 다. 단계는 실패하지 않는다. 오류(종료 코드, 시간 초과 여부, stderr 앞부분)는 회차 기록과 로그에 남는다. 재시도는 하지 않는다(같은 입력이면 같은 결과). 근거: 조문 대조가 돌지 않은 초안을 통과로 표시하지 않고(이 기능이 막으려는 일), 실행 컨테이너가 잠깐 막혀도 사용자는 초안을 받는다. LLM 검사가 실패했을 때 그 회차를 판정 없이 넘기는 지금 방식과 같다(`EvaluatorLoopStepExecutor.java:50`).
2. ② 단계 실패로 끝낸다 (가장 엄격하다. 잃는 것: 실행 컨테이너가 잠깐 막혀도 Lexflow 사용자가 초안을 받지 못한다)
3. ③ 그 회차는 LLM 판정만 쓴다 (잃는 것: 조문 대조가 돌지 않은 초안이 통과로 나간다. 지금 막으려는 일과 같다)

결정과 무관하게 설정 자체가 틀린 것은 첫 작성 전에 단계 실패로 끝낸다. 없는 스킬이나 판, 묶음에 없는 스크립트, 실행할 수 없는 확장자, run 작업장이 없는 실행이다. 저장 때 알 수 있는 것(칸 누락, 칸 형식)은 저장을 거절한다. 스킬과 판이 있는지는 CR-147 단계 스킬과 같이 실행 때 본다(판은 저장 뒤에 올라올 수 있다).

| 입력 파일 | UTF-8 JSON. `step_id`, `iteration`(0부터), `output`(작성 결과의 구조화 출력, 없으면 null), `output_text`(작성 결과 글), `input`(설정 `input` 을 푼 값) |

| 시간 | `timeout_seconds`. 넘으면 프로세스를 죽이고 실패로 본다 |
| 출력 상한 | stdout, stderr 각각 `skills.script-output-max-bytes`(64KB). 잘린 stdout 은 JSON 이 아니므로 실패다 |
| 환경 | Python 3.12(python-docx, openpyxl, pillow 등), Node.js, bash. 인터넷과 비밀값 없음. 표준 입력 없음 |

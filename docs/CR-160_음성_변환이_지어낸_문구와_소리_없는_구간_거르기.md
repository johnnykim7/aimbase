## 1. 문제

1. 맥 사이드카(MLX)가 쓰는 lightning-whisper-mlx 0.0.10 은 30초 창마다 소리 없음 확률(`no_speech_prob`), 평균 로그확률(`avg_logprob`), 압축비(`compression_ratio`)를 계산하지만 결과 구간에는 시작, 끝, 글만 담는다(라이브러리 `transcribe.py` 435행 `all_segments.append([start_seek, end_seek, text])`). faster-whisper 경로는 구간에 값이 있는데 사이드카가 옮기지 않는다(`transcribe-sidecar/src/app.py` `_transcribe_faster`)
2. aimbase 는 사이드카 응답에서 구간마다 start, end, text 만 옮겨 담는다(`LocalWhisperSpeechService.parse`)
3. 그래서 소비처는 구간 글만 보고 의심 구간을 고른다. 원문 45 는 「자막제공자」 한 구간뿐이라 고를 근거가 없어 0건이었다

## 2. 측정

개발기 bp-office 녹음을 맥 사이드카와 같은 모델(large-v3, 언어 ko, 배치 12)로 다시 돌려 창의 값을 꺼냈다(10/26 23:00). 무음과 잡음은 비교용으로 만든 녹음이다.

| 녹음 | 길이 | 소리 크기(RMS) | 받아쓴 글 | 소리 없음 확률 | 평균 로그확률 |
|---|---|---|---|---|---|
| 원문 45 | 4.3초 | 0.133 | 자막제공자 | 0.495 | -0.70 |
| 원문 15 | 2.6초 | 0.092 | 자막 제공 및 자막 제공 및 광고를 포함하고 있습니다. | 0.764 | -0.32 |
| 원문 42 | 7.0초 | 0.138 | 읽은 문장과 같음 | 0.016 | -0.06 |
| 원문 44 | 3.9초 | 0.133 | 빠른 말, 일부 틀림 | 0.512 | -0.63 |
| 원문 46 | 4.9초 | 0.136 | 거의 맞음 | 0.396 | -0.32 |
| 무음 4초 | 4.0초 | 0 | 감사합니다. | 0.829 | -0.46 |
| 잡음 4초 | 4.0초 | 0.010 | 시청해주셔서 감사합니다. | 0.843 | -0.42 |

1. 원문 45 는 말소리가 있는 녹음이다(소리 크기가 정상 녹음과 같다). 소리 없음 확률 0.495 가 원문 44(0.512)보다 낮아 소리 없음 기준으로는 가를 수 없고, 흔한 지어낸 문구로만 걸린다
2. 소리 없는 녹음은 0.76 이상, 말이 있는 녹음은 0.52 이하다. 기준 0.6 이면 양쪽에 여유가 있다
3. 「감사합니다」처럼 실제 말에도 흔한 글은 문구 목록에 넣지 않고 소리 없음 기준으로 거른다

## 3. 바꾸는 것

### 3.1 사이드카

| 항목 | 내용 |
|---|---|
| 응답 구간 | `no_speech_prob`, `avg_logprob`, `compression_ratio` 를 더한다. 값이 없으면 null. 기존 start, end, text 는 그대로 |
| MLX 경로 | 라이브러리가 값을 밖으로 내는 길이 없어 lightning-whisper-mlx 0.0.10 의 `transcribe.py` 를 `src/vendor/lightning_transcribe.py` 로 옮겨 두고, 구간을 담는 줄만 창의 값을 같이 담게 바꾼다. 창 나누기, 추론, 받아쓴 글은 그대로다 |
| faster 경로 | faster-whisper 구간의 같은 이름 값을 옮긴다 |
| 실시간 스트리밍(CR-135) | 바꾸지 않는다 |

### 3.2 aimbase 변환 작업

| 항목 | 내용 |
|---|---|
| 사이드카 값 | 구간에 세 값을 옮겨 담는다 |
| 표시 | 변환 작업이 끝날 때 글이 있는 구간마다 `suspect_reason` 을 붙인다. `NO_SPEECH` 소리 없음 확률이 기준 이상, `KNOWN_PHRASE` 흔한 지어낸 문구를 담음, 해당 없으면 null. 둘 다 맞으면 `NO_SPEECH` |
| 글 없는 구간 | 표시하지 않는다. 라이브러리가 이미 글을 비운 소리 없는 창이라 지어낸 말이 없다. 긴 회의의 쉬는 구간마다 점검이 오르지 않게 한다 |
| 문구 비교 | 띄어쓰기와 문장부호를 빼고 영문 대소문자를 가리지 않고, 문구가 구간 글 안에 있는지 본다 |
| 받아쓴 글 | 바꾸지 않는다. 지우지 않고 표시만 해 사람이 듣고 정한다 |
| 조회 | `GET /api/v1/transcribe-jobs/{id}?include_segments=true` 의 구간에 위 네 칸이 더해진다 |
| 위젯과 음성 API 의 짧은 변환 | 바꾸지 않는다. 글만 돌려주는 경로라 표시를 받을 곳이 없다 |

### 3.3 설정

master `global_config` 에 둔다. V71 마이그레이션이 처음 값을 넣고, 이미 있으면 덮지 않는다. 코드에는 기준값과 문구를 두지 않으며 설정이 없거나 비면 그 표시를 하지 않는다.

| 키 | 처음 값 | 뜻 |
|---|---|---|
| `stt.suspect-no-speech-prob` | 0.6 | 소리 없음 확률이 이 값 이상이면 `NO_SPEECH` |
| `stt.suspect-phrases` | 자막 제공, 자막 by, 한글자막, 시청해 주셔서 감사합니다, 구독과 좋아요, 구독 좋아요, MBC 뉴스, 다음 영상에서 만나요 | 쉼표로 나눈 문구. 담기면 `KNOWN_PHRASE` |

키 이름에 `threshold`, `max-` 를 쓰지 않는다. 설정 변경 API 가 그런 키를 양의 정수로 검사해 0.6 을 받지 않는다(`PlatformSettingsService.validateValue`).

### 3.4 소비처

bp-office 는 변환 결과에서 `suspect_reason` 이 있는 구간을 의심 구간에 바로 넣어야 점검이 오른다. 지금은 구간 번호, 글, 시작만 워크플로우에 넘겨 새 칸이 닿지 않는다(`AimbaseResultPoller.numbered`). bp-office 소스는 그 레포 CR 로 고친다(7절).

## 4. 다른 테넌트

1. 변환 작업 API(`/api/v1/transcribe-jobs`)를 부르는 곳은 bp-office 뿐이다(`~/Documents/GitHub` 아래 전체 검색)
2. 위젯과 음성 API 의 짧은 변환은 이 CR 이 바꾸지 않는다. bp_wes 음성 변환 연결도 같은 사이드카를 쓰지만 받아쓴 글은 그대로다
3. 사이드카 응답과 변환 작업 구간은 칸이 더해질 뿐 기존 칸과 받아쓴 글은 그대로다

## 6. 시험과 개발기 반영

1. 단위시험: 표시 규칙(기준, 문구, 둘 다, 설정 없음, 글 없음, 값 없음), 응답 구간 옮김, 변환 작업이 표시를 붙여 저장(TC-CR160-001~012). 음성 변환 영역 42건 통과
2. dev 커밋만으로는 api 가 컴파일되지 않는다(CR-159 7.1). 개발기 실행본은 맥 작업 폴더를 빌드한 것이라 CR-159 처럼 작업 폴더를 사본으로 떠서 `./deploy.sh be` 를 친다. 10/26 23:11(CR-159 반영) 뒤 작업 폴더에서 바뀐 파일은 CR-160 것뿐이라 개발기 = 지금 실행본 + CR-160 이다
3. 맥 사이드카는 `transcribe-sidecar/deploy/install-mac.sh` 를 다시 돌려 launchd 로 다시 띄운다. bp_wes 와 같이 쓰는 사이드카라 직전에 컨타에 `[승인요청]`
4. api 재기동과 master 마이그레이션(개발기 DB 쓰기) 직전에 컨타에 `[승인요청]`
5. 실제 확인: 원문 45 녹음과 원문 42 녹음을 bp_office 변환 작업으로 다시 돌려 구간 칸을 본다

## 7. 질의

| 번호 | 누구 | 물을 것 | 상태 |
|---|---|---|---|
| 1 | 컨타 | bp-office 수정이 필요하다는 알림, 다른 테넌트 영향 없음 | 끝(23:02 컨타가 CR-015 로 넘김) |
| 2 | bp-office CR-015(컨타 경유) | 표시 구간을 의심 구간에 넣는 방법 | 끝(23:03 ①) |

질의 2. 변환 작업 구간에 `no_speech_prob`, `avg_logprob`, `compression_ratio`(숫자 또는 null), `suspect_reason`(`NO_SPEECH`, `KNOWN_PHRASE`, null)이 더해진다. bp-office 가 이것을 어떻게 받을지.

1. ① `suspect_reason` 이 있는 구간을 결과 조회가 LLM 고르기와 합쳐 의심 구간에 바로 넣는다. 같은 구간은 하나, 사유 글은 bp-office 가 코드에서 정한다(권장)
2. ② 워크플로우 입력 구간에 칸을 넘겨 LLM 이 고르게 한다(모델이 빠뜨리면 점검이 안 오른다)

덧붙여 볼 것: 녹음 전체가 소리 없는 창이라 라이브러리가 글을 비우면 변환 글이 빈 글이 되어 bp-office 가 결과 오류로 본다(`TranscriptionHandler.requireText`). 이 CR 은 글 없는 구간을 표시하지 않는다.

회신(CR-015, 23:03): ①. bp-office 결과 조회가 `suspect_reason` 이 있는 구간을 LLM 고르기와 구간 번호로 합쳐 하나만 남기고, 사유 글은 bp-office 코드 테이블에서 정한다. 변환 글이 빈 글이면 LLM 을 부르지 않고 인식 오류 점검을 올린다. aimbase 칸 모양은 위대로 둔다.

## 1. 배경 및 목적

### 1.1 발단
FlowGuard 시나리오 추출 벤치마크 실험(Claude Code CLI vs Aimbase Chat API)을 준비하던 중, Aimbase의 Chat 환경이 Claude Code(VS Code)와 **비대칭**이라는 사실이 드러났다. 주요 비대칭:

1. **작업 디렉토리 지정 불가** — BE 내장 도구(BashTool/GrepTool/FileReadTool/GlobTool)는 `WorkspaceResolver` 기반으로 동작 준비가 돼 있으나, Chat API → Orchestrator → ToolContext 경로에서 `workspacePath = "/"`로 하드코딩되어 있어 소비앱 소스 폴더(예: `bp-oms`)를 지정할 수 없음.
2. **FE 채팅 UI 부재** — `frontend/src/pages/` 아래 Chat/Playground 페이지 없음. SessionDetail에 "대화 탭 (예정)" placeholder만 존재. 대화형 상호작용이 불가능하여 벤치마크 실험 자체가 성립 안 함.
3. **SSE 이벤트 빈약** — `delta`/`done` 두 종류뿐. 도구 호출/실행 결과/thinking 블록이 스트림 중 실시간으로 FE에 전달되지 않음.

### 1.2 목적
벤치마크 실험을 가능케 하는 수준을 **넘어서**, Aimbase 자체의 대화형 사용성을 Claude Code 수준으로 끌어올리는 정식 기능으로 구현한다.

- BE: 작업 디렉토리 파이프라인 연결, SSE 이벤트 타입 확장, 워크스페이스 목록 API
- FE: `/chat` 라우트 신설, 새 대화 시작 모달, 메시지 블록 렌더러, SSE 스트림 수신 훅
- 기존 세션 재개/도구 호출/정책 엔진/감사 로그는 그대로 재사용 (신규 도구·엔진·테이블 없음)

### 1.3 비목적 (Out of Scope)
- FlowGuard 벤치마크 실험 자체 (본 CR 완료 후 별도 실행)
- 멀티턴 도구 호출 체인 visualization 개선 (기존 `ToolLineage` 탭 재사용)
- 파일 업로드/이미지 멀티모달 (향후 별도 CR)
- 모바일 반응형 (데스크톱 우선)

## 4. API 설계 (T3-2)

### 4.1 변경 엔드포인트

**`POST /api/v1/chat/completions`**
- **추가 필드**: `working_directory` (선택, string)
- **검증 순서**:
  1. 세션 메타에 `workspaceRef` 있으면 그것 사용 (BIZ-091)
  2. 없고 요청에 `working_directory` 있으면 `WorkspacePolicyEngine.validatePath()` 통과 시 사용
  3. 둘 다 없으면 `null` (기존 `"/"` 하드코딩 제거, 도구가 경로 필요 시 명시 요구)
- **에러**: 화이트리스트 위반 시 `403 FORBIDDEN`, 세션 메타 충돌 시 `409 CONFLICT`
- **SSE 응답 확장**: 기존 `delta`/`done` → 5종 (PRD-291)

### 4.2 신규 엔드포인트

**`GET /api/v1/workspaces`** (PRD-292)
- **설명**: 화이트리스트 루트 하위 디렉토리 목록
- **응답**:
```json
{
  "data": [
    {
      "name": "bp-oms",
      "path": "/Users/sykim/Documents/GitHub/bp-fulfillment-infra/bp-oms",
      "modifiedAt": "2026-04-15T10:23:00Z"
    },
    ...
  ]
}
```
- **구현**: `WorkspaceController` 신규 클래스, `Files.list(root).filter(Files::isDirectory)` 1단계만
- **권한**: 인증된 사용자 모두

## 6. 화면 상호작용 (T3-4)

### 6.1 새 대화 시작 플로우
1. 사용자 `/chat` 진입 → 사이드바 렌더, 우측은 empty state
2. `[+ 새 대화]` 클릭 → `NewChatModal` 오픈
3. 모달 내부:
   - **워크스페이스 드롭다운**: `useWorkspaces()` 호출 → `GET /api/v1/workspaces` 결과 렌더
   - **Connection 선택**: 기존 `useConnections()` 재사용
   - **모델 선택**: Connection에 연결된 모델 목록
   - **세션명** (선택, 미입력 시 자동 생성)
4. `[생성]` 클릭 → 클라이언트에서 `session_id = uuid()` 발급, 상태 관리에만 저장 (BE에는 첫 메시지 전송 시 세션 메타와 함께 전달)
5. `/chat/:sessionId`로 navigate, 빈 대화창 렌더

### 6.2 메시지 전송 플로우
1. 사용자 입력 후 `[전송]` 또는 `Cmd+Enter`
2. `useChatStream.send(content)` 호출
3. 내부적으로 `fetch('/api/v1/chat/completions', { stream: true, body: { session_id, messages: [{role:'user',content}], working_directory, actions_enabled: true, ... } })` + `ReadableStream` 리더로 SSE 파싱
4. 이벤트 수신마다 메시지 상태 업데이트:
   - `delta` → 마지막 assistant 메시지의 `TextBlock`에 텍스트 append
   - `thinking` → `ThinkingBlock` append (자동으로 추가/업데이트)
   - `tool_use_start` → `ToolUseBlock` push (`name`, `input` 표시, 로딩 spinner)
   - `tool_result` → 해당 `ToolUseBlock`의 `is_error`/`output` 업데이트, spinner 제거
   - `done` → 입력창 활성화, 전송 버튼 재활성화
5. 스트림 중 에러 시 `<ErrorBanner>` 표시, 부분 수신분은 유지

### 6.3 기존 세션 로드
1. 사이드바에서 세션 클릭 → `/chat/:sessionId` 이동
2. `useConversation(sessionId)` → `GET /api/v1/conversations/:sessionId` 호출
3. 응답의 `messages[]`를 렌더 (content 블록 타입별로 `blocks/*`에 매핑)
4. 세션 메타의 `workspaceRef`를 헤더에 표시

### 6.4 에지 케이스
- SSE 연결 중단 → 자동 재시도 없음, 에러 배너 표시 + 재전송 버튼 (사용자 명시 액션)
- 세션 메타의 workspace와 URL 상태 불일치 → 서버 메타 우선 (BIZ-091)
- 동시에 두 탭에서 같은 session_id로 전송 → 서버는 허용하지만 FE는 마지막 수신 기준으로 상태 덮어쓰기 (개선은 향후)

## 7. 실행 구조 (T3-6)

### 7.1 BE 레이어 변경점

**`ChatController.java`** — **레이어 0 방어선 (조기 차단)**
- `ChatCompletionRequest`에 `workingDirectory` 필드 추가
- 요청 수신 시점에 `WorkspaceProperties.whitelistRoots` 참조하여 400 조기 차단 (도구 실행 전 명확한 오류)
- `streamResponse()` 메서드: `OrchestratorEngine.chatStream()` 반환 스트림을 5종 이벤트로 분기 송출
  - `LLMStreamChunk.type` 기반 분기: text → `delta`, thinking → `thinking`
  - `ToolCallHandler`가 도구 호출 시작/종료 시 이벤트 발행하는 훅 추가 필요

**`OrchestratorEngine.java`**
- `chat()` 진입부에서 `ToolContext` 생성 로직 변경:
  ```java
  String workspace = resolveWorkspace(request, sessionMeta);  // 신규
  ToolContext ctx = ToolContext.builder()
      .workspacePath(workspace)   // 기존 "/" 하드코딩 제거
      ...
  ```
- `resolveWorkspace()` 헬퍼: 세션 메타 > 요청값 > null 순서
- `chatStream()`: 도구 호출 경로에 이벤트 발행 콜백 주입

**`ToolCallHandler.java`**
- `executeTool()` 전후에 `Consumer<ToolEvent>` 호출 (옵션, 스트림 모드에서만 주입)

**`WorkspaceProperties.java`** (신규) — **단일 진실 원천**
- `@ConfigurationProperties("aimbase.workspace")` — `base`, `whitelistRoots` 바인딩
- 모든 방어선(resolver, engine, controller)이 이 객체를 주입받아 참조

**`WorkspaceConfig.java`** (신규) — Spring Bean 와이어링
- `WorkspaceProperties` 활성화, `WorkspaceResolver` Bean, `WorkspacePolicyEngine` Bean 생성
- 기존 `SdkToolBeanConfig`의 Bean 정의를 이쪽으로 이동 또는 위임

**`WorkspaceResolver.java`** (수정) — **레이어 1 방어선**
- 3-인자 생성자 오버로드 추가: `(workspaceBase, whitelistRoots)`
- 기존 2-인자/0-인자 생성자는 `whitelistRoots = List.of()`로 위임 (하위 호환)
- `getWorkspaceRoot(ctx)`가 결과를 화이트리스트 안으로 클램프. 외부면 `WorkspaceAccessException`

**`WorkspacePolicyEngine.java`** (수정) — **레이어 2 방어선 (심층 방어)**
- 2-인자 생성자 오버로드 추가: `(resolver, whitelistRoots)`
- `validatePath()`에서 **resolver와 독립적으로** 최종 target 경로가 화이트리스트 안인지 재확인 (errorCode 90 신규)
- 기존 `target.startsWith(workspaceRoot)` 로직 그대로 유지 (traversal 방어)
- 빈 화이트리스트면 기존 동작 유지 (하위 호환)

**`WorkspaceController.java`** (신규, ~50 LOC)
- `GET /api/v1/workspaces` → `Files.list(root)` 기반 1단계 디렉토리 나열

**`SessionStore.java`** — 수정 없음 (메타 JSONB이므로 자동 처리)

### 10.1 하드코딩 `"/"` 제거 안전성 (2026-04-15 전수 grep 완료)

**결과: 안전. 오히려 잠재 보안 이슈 해소 효과.**

의존 지점 맵:

| 파일:라인 | 용도 | 영향 |
|---|---|---|
| `OrchestratorEngine.java:220` | 하드코딩 `"/"` 주입 | **제거 대상** |
| `ToolCallHandler.java:250` | AUTO 권한 해소 시 `toolContext.workspacePath()` 값 전달 복사 | 값 전달만, 무영향 |
| `ToolController.java:83-88` | `/tools/{name}/execute` REST에서 body의 `workspacePath` 사용 | 이미 null 허용, 무영향 |
| `WorkspaceResolver.java:26-33` | null/blank 시 `/data/workspaces/{tenantId}/{projectId}`로 폴백 | **보호 장치, 존치** |
| `AgentProperties.java:28` | aimbase-agent 독립 모듈 설정 | 본 CR 스코프 밖 |
| 테스트 코드 6개 파일 | 명시 경로(tempDir 등) 사용 | 무영향 |

**근거**:
- `WorkspaceResolver.getWorkspaceRoot()`는 `ctx.workspacePath()`가 null/blank이면 `/data/workspaces/{tenantId}/{projectId}`로 자동 폴백 (`WorkspaceResolver.java:27-33`). 따라서 `"/"` 제거 후 null을 주입해도 기존 호출자 동작은 유지됨.
- 현재 `"/"` 하드코딩은 "루트 파일시스템 전체를 워크스페이스로 취급"을 의미하며, `WorkspacePolicyEngine`의 경로별 차단에만 의존하는 위험한 상태. **Phase 1이 이 구조적 결함도 동시에 해소**.

### 10.2 폴백 경로(`/data/workspaces`)와 화이트리스트 루트 불일치

`WorkspaceResolver`의 기본 폴백은 컨테이너 내부 경로 `/data/workspaces`를 가정한다. 반면 본 CR의 화이트리스트 루트는 로컬 개발 환경 경로 `$HOME/Documents/GitHub/bp-fulfillment-infra`다. 두 값이 일관되지 않으면:

- 사용자가 `working_directory`를 명시하지 않은 채 chat 요청 → 폴백 경로(`/data/workspaces/...`)가 반환되나 **로컬에는 존재하지 않음**
- 해당 경로 기반 도구 호출은 파일 없음 오류로 실패

**대응 (Phase 1 포함)**:
1. `application.yml`에 `aimbase.workspace.base` 설정값 노출 (기본값 `/data/workspaces`)
2. `aimbase.workspace.whitelist-roots` 설정값 노출 (기본값 `${user.home}/Documents/GitHub/bp-fulfillment-infra`)
3. `WorkspaceResolver`를 Spring Bean으로 감싸 `workspaceBase`를 설정값으로 주입 (현재는 하드코딩 기본값)
4. `working_directory` 미지정 + 세션 메타 부재 시 **null 유지** (폴백 경로로 가지 않음). 도구가 경로를 필요로 하면 명시적 오류 반환. 명시 요구 원칙으로 사용자 혼란 방지.

### 10.3 심층 방어 (Defense in Depth) 원칙

본 CR은 작업 디렉토리 접근 제어를 **3개의 독립 방어선**으로 구성한다. 각 레이어가 같은 `WorkspaceProperties`(단일 진실 원천)를 참조하되, 한 레이어가 우회되어도 다른 레이어가 막도록 **독립적으로 동작**한다.

| 레이어 | 위치 | 방어 시점 | 실패 시 응답 |
|---|---|---|---|
| **L0: 인바운드 조기 차단** | `ChatController.completions()` | 요청 수신 직후, 도구 실행 전 | `400 BAD_REQUEST` |
| **L1: 경로 결정 시점** | `WorkspaceResolver.getWorkspaceRoot()` | `ToolContext → Path` 변환 시 | `WorkspaceAccessException` |
| **L2: 정책 검증 시점** | `WorkspacePolicyEngine.validatePath()` | 개별 도구 실행 직전, 각 경로마다 | `ValidationResult.fail(errorCode=90)` |

**단일 진실 원천**: `aimbase.workspace.whitelist-roots` 설정값 하나. L0/L1/L2 모두 `WorkspaceProperties` Bean을 주입받아 참조하므로 규칙 변경 시 수정 지점은 application.yml 한 곳.

**역할 분리**:
- 기존 `WorkspacePolicy.allowedRoots` 필드는 "테넌트/프로젝트별 추가 허용 경로"(정책 수준)로 원래 의미 유지 — 시스템 화이트리스트와 역할이 분리됨
- 시스템 화이트리스트는 정책 객체 외부에 존재 (설정 수준)
- 두 개념이 충돌하지 않음

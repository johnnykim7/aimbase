## 1. T1 — 요구사항

### 1.1 목적

재고조사·입고조사 등 현장 업무에서 **사진/영상을 찍어 판별**시킨다. 수량 카운팅은 단적인 예시이고, 본질은 "찍어서 뭔가 판별"이다.

### 1.2 범위 구분 — 누가 무엇을 만드는가

| 주체 | 담당 | 근거 |
|---|---|---|
| **소비앱** | 촬영 버튼·미리보기·결과 화면 | 앱마다 화면톤이 다름. `<input capture>` 수준이라 감쌀 알맹이가 없음 |
| **aimbase** | 업로드 수신 · 서버 프레임 추출 · VLM 판독 · 결과 JSON · 얇은 SDK(UI 없음) | 앱이 늘어나도 재구현되면 안 되는 부분 |

**위젯(채팅) 확장이 아니다.** 목적은 대화가 아니라 "찍어 보내는 입력 경로".

### 1.3 설계 결정 — 서버 추출을 택한 이유

최초 원본 작성본은 "브라우저에서 canvas로 프레임 추출"이었으나 **사용자 결정으로 서버 추출로 변경**.

| 항목 | 브라우저 추출 | **서버 추출 (채택)** |
|---|---|---|
| 앱 증가 시 | 앱마다 canvas·코덱 분기 재구현 | aimbase 한 곳 |
| 원본 보존 | 프레임만 남고 원본 소실 | 원본 보존 → 재판독·감사 가능 |
| 모바일 코덱 편차 | 브라우저별 대응 필요 | ffmpeg가 흡수 |
| BE 변경량 | 적음 | ffmpeg 설치 + job 필요 |

원본 보존이 결정적이다. 판독 결과에 이의가 생기면 원본으로 재판독해야 하는데, 브라우저 추출은 그 근거가 남지 않는다.

### 1.4 범위 — 포함

1. 영상 MIME 허용 (`MimeValidator` 매직넘버 확장)
2. **업로드 상한 정합** — Spring multipart / 코드 상수 / nginx 3계층 (§7-2 지뢰 1 동반 해소)
3. **`/data/aimbase` 볼륨 마운트** (§7-3 지뢰 2 동반 해소)

5. 영상 job 테이블 + 컨트롤러 (CR-133 패턴 복제)
6. 프레임 → 기존 `PAGE_IMAGES` Vision 경로 재사용

## 3. T3 — 상세 설계

### 3.1 지뢰 1 — 업로드 상한 정합 ★선행

**현황 (실측, 2026-08-06)**:

| 계층 | 값 | 위치 |
|---|---|---|
| ① nginx (호스트) | **100m** | `/etc/nginx/sites-available/aimbase:21` (운영서버, 저장소 밖) |
| ② Spring multipart | **50MB** ← 가장 작음 | `application.yml:10-11` |
| ③ 전사 job 상한 | **1GB** | `TranscribeJobController.java:38` |

**실제 버그 구간**: 요청은 ①→②→③ 순으로 검사된다. ②가 ①보다 작아서
**50~100MB 파일이 nginx는 통과하고 Spring에서 `MaxUploadSizeExceededException`으로 터진다.**
③의 1GB는 ①②에 먼저 막혀 애초에 도달 불가 — "4시간 분량" 근거로 잡혔으나 실행된 적 없다.

**조치 — 100MB 로 3계층 통일** (1GB 로 올리는 게 아니다):
```yaml
# application.yml — 50MB → 100MB (nginx 100m 과 일치)
max-file-size: 100MB
max-request-size: 100MB
```
```java
// TranscribeJobController.java — 1GB → 100MB (도달 불가였던 값 정정)
MAX_SIZE_BYTES = 100L * 1024L * 1024L;
```
```nginx
# nginx 는 현행 100m 유지 — 변경 불필요
```

**100MB 근거**: 1시간 회의녹음(m4a/opus) 50~120MB, 현장 영상 30초~2분 20~100MB,
cvilite 샘플 8MB/5.7MB. 무손실 WAV 를 가정하지 않는 한 충분하다.
더 필요해지면 nginx → application.yml → 컨트롤러 순으로 **함께** 올린다.

**주의**: nginx 설정은 저장소 밖(운영서버 `/etc/nginx/sites-available/aimbase`)이라
저장소만 보고 판단하면 안 된다. `aimbase-banpoom` 도 8280 을 프록시하며 동일하게 100m.

### 3.3 영상 MIME 허용

`MimeValidator.java` — 현재 PNG/JPEG/GIF/PDF/WEBP 5종 매직넘버만 허용(L37-57).

추가할 매직넘버:

| 포맷 | 시그니처 | 비고 |
|---|---|---|
| MP4 / MOV | `....ftyp` (offset 4) | iOS 기본. brand로 세분(`isom`,`mp42`,`qt  `) |
| WebM | `1A 45 DF A3` | Android Chrome 기본 |
| AVI | `RIFF....AVI ` | 레거시 |

```java
// MimeValidator.java 확장
private static final byte[] FTYP = {'f','t','y','p'};

static boolean isMp4(byte[] h) {
    return h.length > 12 && Arrays.equals(
        Arrays.copyOfRange(h, 4, 8), FTYP);
}
static boolean isWebm(byte[] h) {
    return h.length > 4 && h[0]==(byte)0x1A && h[1]==(byte)0x45
        && h[2]==(byte)0xDF && h[3]==(byte)0xA3;
}
```

**주의**: iOS는 `.mov`(QuickTime)로 찍어도 `ftyp` 헤더를 쓴다. Content-Type이 `video/quicktime`으로 올 수 있으므로 헤더 이중검증(`assertMatchesContentType` L67-76)에 매핑 추가 필요.

### 3.5 프레임 추출 — `FrameExtractor.java` (신규)

```java
// com.platform.vision.FrameExtractor
public List<Path> extract(Path video, int frameCount, Path outDir) {
    double duration = probeDuration(video);           // ffprobe
    // 균등 간격: 0, d/N, 2d/N, ... (N-1)d/N
    // -vf fps 대신 -ss 개별 seek 이 정확 (긴 영상에서 fps 필터는 부정확)
    for (int i = 0; i < frameCount; i++) {
        double ts = duration * i / frameCount;
        exec("ffmpeg", "-ss", String.valueOf(ts), "-i", video.toString(),
             "-frames:v", "1", "-q:v", "2",
             outDir.resolve("f" + i + ".jpg").toString());
    }
}
```

**설계 판단**:
- `-vf fps=N/duration` 대신 **프레임별 `-ss` seek** — 긴 영상에서 fps 필터는 키프레임 정렬 때문에 간격이 틀어진다
- `-ss`를 `-i` **앞에** 둬야 빠르다(입력 seek). 뒤에 두면 디코드 전체를 훑는다
- `-q:v 2` — JPEG 품질. base64 크기와 판독 정확도 균형

**참고 자산**: `cvilite/samples/preview/f0~f5.jpg`가 이미 6프레임 추출본이다. 구현 후 서버 추출 결과와 비교해 검증할 것.

영상 프레임이 그대로 얹힌다. `PdfVisionResolver`와 대칭인 `VideoFrameResolver`를 만들되, 블록 조립부는 동일 코드를 공유한다.

어댑터 직렬화는 이미 전 경로 지원:
`AnthropicAdapter:517-540` / `OpenAIAdapter:360-361` / **`OpenAICompatibleAdapter:232-233`**(CR-136이 연 자리) / `ClaudeCliRunnerClient:450-456`

### 3.9 API 설계

```
POST /api/v1/vision-jobs
  multipart/form-data
    file          (required) 영상 또는 이미지
    connection_id (required) 예: qwen-vl-7b-mac-001
    frames        (optional) 기본 6, 범위 1~20 (BIZ-112)
    prompt        (optional) 판독 지시. 미지정 시 기본 프롬프트
    output_schema (optional) structured output (CR-007) — 수량은 반드시 이걸로
  → 202 { job_id, status: "PENDING", filename, size_bytes }

GET /api/v1/vision-jobs/{job_id}
  → 200 { job_id, status, result?, result_json?, frame_count,
          duration_sec, elapsed_sec, error_message? }
```

에러 매핑(CR-133 `mapSpeechError` 준용): `PROVIDER_UNAVAILABLE→503`, `TIMEOUT→504`, `UPSTREAM_ERROR→502`, 크기초과→413.

### 3.10 얇은 업로드 SDK (UI 없음)

```ts
// packages/aimbase-vision-client
const client = new VisionClient({ baseUrl, apiKey, tenantId });
const { jobId } = await client.submit(file, {
  connectionId: 'qwen-vl-7b-mac-001', frames: 6, prompt: '...'
});
const result = await client.waitFor(jobId, { pollMs: 2000, timeoutMs: 300_000 });
```

**UI를 넣지 않는다.** 앱마다 재구현되면 안 되는 것은 UI가 아니라 **업로드 신뢰성**(대용량, 모바일 네트워크 끊김, 재시도)이다.

## 4. 구현 순서 (Phase)

| Phase | 내용 | 산출물 | 상태 |
|---|---|---|---|
| **0** | **지뢰 선처리** — 상한 정합 + 볼륨 마운트 | `application.yml`, `docker-compose.prod.yml` | ✅ **배포·검증** |
| 1 | 영상 MIME + V71 마이그레이션 | `MimeValidator`, `AttachmentService`, `V71__cr137_vision_jobs.sql` | ✅ 구현 |
| 2 | ffmpeg 설치 + `FrameExtractor` | `Dockerfile`, `FrameExtractor.java` | ✅ 구현 |
| 3 | Job 서비스·컨트롤러 (CR-133 복제) | `VisionJobService/Store/Controller/Entity/Repository/GcScheduler` | ✅ 구현 |
| 4 | 프레임 → Vision 블록 배선 | `VisionJobService.runJob()` 내부에 통합 | ✅ 구현 |
| 5 | SDK + 테스트 + 가이드 | `packages/vision-client`, 테스트 29, API 가이드 § 23 | ✅ 구현 |

**Phase 0을 먼저 한 이유**: 지뢰 2는 그때도 파일이 날아가는 상태였고, 지뢰 1은 CR-133이 이미 깨져 있을 수 있었다. 영상을 올리기 전에 해소가 필요했다.

### 구현 중 확정된 설계 변경 3건

1. **`VideoFrameResolver` 클래스를 만들지 않았다.** 설계 초안은 `PdfVisionResolver` 와 대칭인 리졸버를 두려 했으나, 실제로는 job 워커가 프레임 파일을 읽어 `ContentBlock.Image` 로 조립하면 끝이라 별도 클래스가 껍데기만 된다. `VisionJobService.runJob()` 안에 인라인했다.

2. **판독은 `OrchestratorEngine.chat()` 을 경유한다.** 어댑터를 직접 부르면 정책 평가·감사 로깅·비용 추적(BIZ-020)을 통째로 우회한다. 프레임을 이미지 블록으로 조립해 넘기면 나머지는 기존 경로가 처리한다.

3. **GC 스케줄러를 추가했다**(설계 초안에 없던 것). 원본 영상을 보존하기로 한 이상 100MB 급 파일이 무한 누적되므로 TTL 기반 정리가 필수다. `VisionJobGcScheduler` — `AttachmentGcScheduler` 와 같은 테넌트 순회 구조.

### 채팅 첨부 회귀 차단

`MimeValidator` 를 확장하자 **채팅 첨부(CR-061)도 영상을 받게 되는** 부작용이 생긴다. 그대로 두면 영상이 이미지 상한(10MB)에 걸리거나 Vision 블록 조립에서 조용히 깨진다. `AttachmentService` 에서 명시적으로 막고 `/api/v1/vision-jobs` 로 안내한다.

## 5. 영향 / 트레이드오프

### 5.1 영향 범위

| 대상 | 영향 |
|---|---|
| 기존 사진 첨부 경로 | **무변경** (CR-136 검증 완료 상태 유지) |
| CR-133 전사 job | 상한 정합으로 **개선** (>50MB 회의녹음이 비로소 동작) |
| API 이미지 크기 | +~200MB (ffmpeg) |
| 스토리지 | 영상 원본 보존 → 용량 증가. 24h TTL로 관리 |
| cv-inspection | **무변경** (건드리지 않음) |

### 5.2 트레이드오프

- **원본 보존 vs 용량**: 재판독·감사를 위해 원본을 남긴다. 24h TTL + 볼륨 마운트로 관리
- **BE 직접 exec vs 사이드카**: CR-120 결론(사이드카 경유는 중개 낭비) 따라 직접 exec
- **6프레임 고정 vs 적응형**: 우선 고정. 움직임 기반 적응 샘플링은 측정 후 판단

### 5.3 남은 리스크

- **운영 nginx 설정이 저장소 밖** — 배포 시 서버에서 직접 확인 필요
- **LM Studio 인증 없음** — 공유기 소스 IP 제한(59.8.160.12) 미확인. 미조치 시 인터넷 누구나 GPU 사용 가능
- **LM Studio는 GUI 앱** — 재부팅 시 죽음. CR-138 상시화 파트 미완
- **VLM 카운팅 한계** — 구조적. structured output으로 우회하되, 사용자에게 "수량은 코드가 센다"를 명시해야 함

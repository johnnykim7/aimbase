# CR-167: 운영 Aimbase 에 같은 목소리 음성 생성기 올리기(필요할 때만 켜기)

## 1. 배경

- 운영 chaws 의 Aimbase 에는 생성기도 작업 창구도 없다. 운영 bp-wms 는 11-03 06:48 기동 때 바구니 이름 170개를 줄 세우고 Aimbase 에 맡기다 404 로 거절당해(로그 `음성 생성 요청 거절 404` 119건), 10분 뒤 전부 기다림 상한으로 지웠다. 그래서 운영 현장 화면은 서버 음성을 받은 적이 없다
- 운영 chaws 는 m6i.2xlarge(코어 4개, 스레드 8개, AVX2, AVX512). 메모리 30GB 중 쓸 수 있는 것 14GB(11-03 07:53). 운영 3PL 컨테이너 21개가 같은 서버에 있다
- 생성기 메모리는 59 에서 지금 12.13GB, 최고 13.34GB(`/proc` VmRSS, VmHWM, 생성 413번 뒤). 그대로 올리면 운영 서비스 여유가 1GB 남짓이다
- 사용자 결정(11-03 07:48): 서버는 늘리지 않는다. 할 일이 있을 때만 싣고, 일이 없으면 메모리를 비운다. 실린 동안의 메모리도 줄일 수 있는지 59 에서 잰다

## 2. 쓰는 모양

bp-wms 와 api 가 보는 것은 CR-166 그대로다(계약 `docs/협업/계약_CR-166_같은_목소리_음성_생성_창구.md`). 달라지는 것은 세 가지다.

1. 쉬던 생성기가 받은 첫 문장은 모델을 싣는 시간만큼 더 걸린다
2. 일이 끝나고 정한 시간이 지나면 모델이 메모리에서 내려간다
3. 맡기기 503 은 「모델을 받는 중」 과 「싣기에 실패해 잠시 쉬는 중」 일 때만 난다. 「모델을 싣는 중」 에는 503 이 아니라 받아서 기다렸다 만든다

## 3. 설계

### 3.1 모델을 실을 때와 내릴 때

생성기 컨테이너 안을 프로세스 둘로 나눈다.

| 프로세스 | 하는 일 | 메모리 |
|---|---|---|
| 창구 | `/health`, `/synthesize` 를 받고 모델 프로세스를 띄우고 끝낸다. PyTorch 를 불러오지 않는다 | 7절 실측 |
| 모델 | 모델을 싣고 견본 특징을 만들고 소리를 만든다. 지금 `Engine` 그대로다. 한 번에 하나만 있다 | 7절 실측 |

| 때 | 일어나는 것 |
|---|---|
| 기동 | 창구만 뜬다. 모델 파일이 볼륨에 없으면 받는다(4.3GB, 받는 동안 `/health` 503). 모델은 싣지 않는다 |
| 문장이 옴, 모델 내려감 | 모델 프로세스를 띄워 싣는다. 끝나면 그 문장을 만든다 |
| 싣거나 만드는 동안 다른 문장이 옴 | 잠금 앞에서 기다렸다 차례로 만든다. 실패로 돌리지 않는다(BIZ-133, BIZ-139) |
| 마지막 문장이 끝나고 `TTS_IDLE_UNLOAD_SECONDS`(기본 300초) 지남 | 모델 프로세스를 끝낸다. 메모리가 서버로 돌아간다 |
| 모델 프로세스가 싣다가 또는 만들다가 죽음(메모리 상한 포함) | 그 문장은 503. `TTS_LOAD_RETRY_SECONDS`(기본 600초) 동안은 `/health` 와 `/synthesize` 가 503 이고 다시 싣지 않는다. 지나면 다음 문장에 다시 싣는다(BIZ-140) |

프로세스를 나누는 까닭.

- 같은 프로세스에서 모델을 지우면 정리 호출까지 해도 PyTorch 를 불러온 몫이 남고(7절 실측 0.63GB), 정리 호출을 빼면 3.87GB 가 남는다. 프로세스를 끝내면 창구 몫만 남는다
- 메모리 상한에 걸려 모델이 죽어도 창구는 살아 503 으로 답하고, 생성기 컨테이너 전체가 다시 뜨지 않는다
- api 에 도커 권한을 주어 컨테이너를 켜고 끄는 방법은 쓰지 않는다. 운영 3PL 컨테이너까지 만질 수 있는 권한을 api 가 갖게 된다

모델 파일은 창구가 기동할 때 받아 두고, 모델 프로세스에는 받아 둔 폴더 경로를 넘긴다. 저장소 이름으로 부르면 `from_pretrained` 가 실을 때마다 huggingface.co 에 묻는다(59 에서 망을 끄고 실으니 `OfflineModeIsEnabled`). 필요할 때 싣는 구조에서 싣기가 외부 망에 걸리면 안 된다. 모델 프로세스는 `HF_HUB_OFFLINE=1` 로 띄운다.

### 3.2 생성기 창구

`POST /synthesize` 의 요청, 응답, 오류는 CR-166 3.1 그대로다. 모델이 내려가 있으면 싣고 만든다. `GET /health` 는 다음과 같이 바뀐다.

| 상태 | HTTP | 본문 |
|---|---|---|
| 모델 파일 받는 중 | 503 | `{"status":"downloading"}` |
| 모델 파일 받기 실패 | 503 | `{"status":"failed","error":"..."}` |
| 내려감, 싣는 중, 실림 | 200 | `{"status":"ok","voices":[...],"model":"unloaded"\|"loading"\|"ready"}` |
| 싣기 실패 뒤 쉬는 중 | 503 | `{"status":"backoff","error":"...","retry_after":초}` |

api 는 `/health` 의 200 과 `voices` 만 보고 `/synthesize` 를 시간 상한까지 기다리므로 고치지 않는다(`TtsSidecarClient`). 그래서 59 는 생성기만 다시 배포하고 api 를 건드리지 않는다.

### 3.3 bp-wms 기다림 상한

bp-wms 는 작업이 RUNNING 인 것을 처음 본 때부터 10분을 잰다(`deleteExpired`, `started_at`). api 는 작업을 집을 때 RUNNING 으로 바꾸므로 싣는 시간이 이 10분에 든다. api 의 문장 하나 시간 상한도 600초다(`aimbase.tts.request-timeout-seconds`). 차례를 기다리는 동안은 RUNNING 이 아니라 재지 않는다.

견주는 값은 7절 실측에 적는다. 싣는 시간 + 한 문장 시간이 10분 안이면 된다.

### 3.4 실린 동안의 메모리 줄이기

모델 파일은 bf16 으로 저장돼 있고(`talker` 3,678MB) 지금은 fp32 로 늘려 싣는다(7,356MB). 소리 부분(`speech_tokenizer`, 650MB)은 원래 fp32 다.

| 방법 | 소리 | 재는 것 |
|---|---|---|
| A. fp32 그대로 | 기준 | 찬 디스크에서 싣는 시간, 15문장 돌린 뒤 메모리, 같은 프로세스에서 지운 뒤 남는 메모리 |
| B. fp32 + 메모리 할당기 설정(`MALLOC_*`) | A 와 비트 단위로 같아야 한다 | 같음 |
| C. B + 견본 특징을 만든 뒤 쓰지 않는 부분 비우기 | A 와 비트 단위로 같아야 한다 | 같음 |
| D. talker 의 Linear 만 8bit 로 바꾸기 | 달라질 수 있다. 사용자가 듣는다 | 같음 |
| E. bf16 그대로 싣기 | 달라질 수 있다. CR-WMS-842 에서 10배 넘게 느렸다 | 메모리와 한 문장 |

A, B 는 문장 15개를 더 만들어 오래 돌 때 늘어나는지도 본다. 59 생성기 메모리가 처음 9.8GB 에서 생성 413번 뒤 12.13GB 로 늘었다.

운영 chaws 는 코어가 4개라 59(8개) 속도를 그대로 쓸 수 없다. 59 코어 4개에 묶어(`--cpuset-cpus 0,8,1,9,2,10,3,11`) 스레드 4, 6, 8 로 잰다.

고르는 기준은 사용자가 분류대 299개와 견주어 듣는 것이다. 목소리가 달라지는 방법은 쓰지 않는다.

### 3.5 운영 chaws 생성기

`docker-compose.chaws.yml` 에 `tts-sidecar` 서비스를 더하고 api 에 `AIMBASE_TTS_SIDECAR_URL` 을 준다.

| 항목 | 값 |
|---|---|
| CPU 몫 | `cpu_shares` 를 운영 3PL 컨테이너(기본 1024)보다 낮춘다. 코어가 모자랄 때 운영 서비스가 먼저 받는다 |
| 코어 상한 `cpus`, 스레드 `TTS_THREADS` | 7절 실측으로 정해 컨타에게 올린다 |
| 메모리 상한 `mem_limit`, `memswap_limit` | 7절 실측으로 정해 컨타에게 올린다. 스왑을 쓰지 않게 둘을 같은 값으로 둔다 |
| 호스트 포트 | 열지 않는다. api 만 compose 기본 망으로 부른다 |
| 디스크 | 이미지 2.23GB, 모델 4.2GB. `/var/lib/docker` 남은 55GB(11-03 07:53) |

운영 bp-wms 는 기동할 때 저장분 없는 바구니 이름을 몰아 맡긴다(11-03 06:48 170개). 그 한 바퀴 동안은 모델이 실려 있다. 저장되고 나면 다음 기동부터는 맡길 것이 없다.

### 3.6 운영 api

- 운영 api 는 503da60(CR-162) 이고 CR-166 이 없다(`git merge-base`, 운영 bp-wms 로그 404). 운영 테넌트 `aimbase_bp_wms` 의 마지막 이력은 V73 이다
- 올릴 코드는 dev 가 아니라 **운영 실행본 6889aed + CR-166 기능 커밋 + CR-167** 을 얹은 가지다. dev 에는 운영 승인을 받지 않은 CR-161, CR-165 가 섞여 있다. 503da60 과 6889aed 의 차이는 실행기와 설치 스크립트뿐이고 api 소스는 같다
- 테넌트 V75 는 api 기동 때 돈다. V74(CR-164)를 건너뛰지만 테넌트 마이그레이션이 `outOfOrder(true)` 라 나중에 V74 가 와도 들어간다
- api 를 다시 만들 때 도는 워크플로우가 없는지 직전에 본다

### 3.7 배포

`deploy.sh` 에 `chaws-tts` 를 더한다. 다른 chaws 대상과 같이 `CHAWS_COMMIT` 을 받은 worktree 에서 생성기 소스와 compose 를 올리고, `nice` 로 이미지를 만들고, 그 서비스만 다시 만들고, 전 이미지를 태그로 남기고, 커밋을 `deployed.log` 에 남긴다. 처음에는 모델을 받느라 180초를 넘으므로 기다리는 시간을 대상마다 줄 수 있게 한다. `chaws` 묶음에는 넣지 않는다. 생성기를 다시 만들 일은 드물다.

### 3.8 설정

| 환경변수 | 기본값 | 뜻 |
|---|---|---|
| `TTS_IDLE_UNLOAD_SECONDS` | 300 | 마지막 문장이 끝나고 모델을 내리기까지. 1 이상 |
| `TTS_LOAD_RETRY_SECONDS` | 600 | 모델 프로세스가 죽은 뒤 다시 싣기까지 쉬는 시간. 1 이상 |
| `TTS_THREADS` | 8 | 연산 스레드(CR-166). 운영 chaws 값은 3.5 |

## 4. 요청서와 다른 것

1. 요청서의 「싣는 데 104.2초」 는 모델을 받는 시간까지 든 값이다. 그 기동의 모델 파일 시각이 10-31 04:13 ~ 04:15 이고 로그는 04:15:17 이다. 싣기만 잰 값은 7절에 적는다
2. 메모리는 요청서의 11.6GB 보다 크다. 59 프로세스 최고 13.34GB, 지금 12.13GB. 상한은 이 값을 보고 정한다
3. 59 는 api 를 다시 배포하지 않는다(3.2). CR-166 의 「다음 59 api 배포」 주의가 이 건에는 걸리지 않는다
4. 싣기 실패가 되풀이되지 않게 쉬는 시간을 둔다(BIZ-140). 메모리 상한에 걸린 채 줄 선 문장마다 13GB 를 다시 실으면 운영 서버가 흔들린다
5. 운영 api 는 dev 가 아니라 운영 실행본에 이 두 건만 얹어 올린다(3.6)

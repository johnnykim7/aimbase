## 1. 현재 구조 요약

### 1.1 비스트리밍 경로 `chat()`
- 흐름: `OrchestratorEngine.chat()` → `ToolCallHandler.executeLoop()` → 루프 내 `adapter.chat().get()` 반복
- 루프 내부: `finishReason == TOOL_USE` 면 `executeAndRecord()`로 도구 실행 → 결과를 메시지에 추가 → 다음 `adapter.chat()` 호출. 최종 텍스트 응답 반환.
- [ToolCallHandler.java:84-188 (기본)](../backend/platform-core/src/main/java/com/platform/tool/ToolCallHandler.java#L84-L188), [:192-318 (Enhanced + lineage)](../backend/platform-core/src/main/java/com/platform/tool/ToolCallHandler.java#L192-L318)
- 기능 전체: Hook 디스패치, Permission AUTO 해소, `concurrencySafe` 병렬, ToolResult 축약(CR-031), lineage 기록, PlanMode 차단, Circuit Breaker 등

### 1.2 스트리밍 경로 `chatStream()`
- 흐름: `OrchestratorEngine.chatStream()` → **`adapter.chatStream()` 직접 호출** → 청크만 consumer에 전달
- [OrchestratorEngine.java:469-485](../backend/platform-core/src/main/java/com/platform/orchestrator/OrchestratorEngine.java#L469-L485)
- 도구 루프 **없음**. 즉 스트리밍 요청에 `actions_enabled=true`가 와도 도구 호출이 발생하지 않음.

### 1.3 이 비대칭의 이유 (추정)
- Anthropic/OpenAI 스트리밍 API는 "텍스트 델타 단위"로 청크를 내보냄. 중간에 tool_use가 감지되면 그 턴은 끝내고 도구 결과를 주입한 후 새 스트림을 시작해야 함 — "스트림 도중 도구 실행"이 아니라 "**스트림 여러 번 연결**"이 필요.
- Aimbase 초기 구현에서 스트리밍은 "단순 텍스트 생성" 경로로만 제공됨. 도구는 비스트리밍에서 완성.

## 2. 목표 상태

**스트리밍 중에도 도구 호출·실행을 지원**하고, FE에 다음 이벤트를 추가 송출:

| 이벤트 | 데이터 | 발생 시점 |
|---|---|---|
| `tool_use_start` | `{id, name, input}` | LLM이 해당 턴을 TOOL_USE로 종료 → 도구 실행 직전 |
| `tool_result` | `{tool_use_id, output, is_error}` | 도구 실행 완료 직후 (축약된 output 포함) |

기존 이벤트(`delta`/`thinking`/`done`)는 그대로 유지. 도구 실행 후 다시 LLM 스트림이 이어지면 `delta`를 계속 송출.

## 3. 설계 옵션 비교

### 옵션 A: `ToolCallHandler` 신규 메서드 `executeLoopStream()`

**개요**: 비스트리밍 `executeLoop()`와 형제 메서드를 추가. 내부는 구조 유사하지만 매 루프 턴에서 `adapter.chat()` 대신 **`adapter.chatStream()`** 을 호출하고, 최종 텍스트를 `StringBuilder`로 누적한 뒤 finishReason/toolCalls 감지용 최종 `LLMResponse`를 구성.

**장점**
- 기존 `executeLoop()` 무변경 — 비스트리밍 경로 회귀 위험 0
- 각 모드의 "어댑터 호출 방식"이 명확히 분리됨

**단점**
- **코드 중복** — Hook 디스패치, Permission AUTO, concurrencySafe, 축약, lineage, PlanMode 가드 등 300+ LOC를 거의 그대로 복사
- 향후 비즈니스 규칙 변경 시 **두 경로 모두 수정 필수**. 유지보수 부담 누적

### 옵션 B: `executeLoop()` 자체를 "옵션 스트리밍" 모드로 확장

**개요**: `executeLoop()` 시그니처에 `Consumer<StreamEvent> streamSink` 파라미터(nullable) 추가. null이면 기존 비스트리밍, non-null이면:
- 어댑터 호출을 `adapter.chatStream()`으로 전환
- 매 청크를 `streamSink`로 흘리되 텍스트를 누적해 최종 `LLMResponse` 재구성
- 도구 실행 전후에 `streamSink.accept(new ToolUseStart(...))` / `new ToolResult(...)` 발행

**장점**
- **중복 제거** — Hook/Permission/ concurrencySafe/축약/lineage가 한 곳에서 관리됨
- 비스트리밍은 `streamSink=null`로 호출하면 기존 동작 그대로 (하위 호환)

**단점**
- 단일 메서드가 더 복잡해짐. 내부에 `if (streaming) {...} else {...}` 분기 다수
- 버그 시 두 모드 모두 영향. 단위 테스트 커버리지 확대 필요

### 옵션 C: 어댑터 레이어에서 "스트리밍형 chat()" 통합

**개요**: `LLMAdapter`에 `chat()`/`chatStream()` 외에 **`chatWithStream(streamSink)`** 메서드 추가. 이 메서드는 비스트리밍 API 호출이지만 어댑터가 "의사 청크"로 쪼개 `streamSink`에 흘림. `ToolCallHandler.executeLoop`는 이 메서드를 사용.

**장점**
- `ToolCallHandler` 무변경
- 다른 도구 루프 사용처도 자동으로 스트리밍 혜택

**단점**
- "의사 청크"라 실제 스트리밍 체감과 다름. thinking 블록도 최종 응답에만 나와 본 CR의 Phase 2-A 이벤트와 충돌
- Anthropic/OpenAI 어댑터 각각 새 메서드 구현 필요 (N개 프로바이더 × 1 메서드)
- **네이티브 스트리밍이 아닌 의사 스트리밍** → CR-045 목적(실시간 visualization)에서 퇴행

### 권장: **옵션 B**

이유:
1. **단일 진실 원천** — 도구 루프 비즈니스 규칙이 한 곳
2. **하위 호환** — 기존 호출자(`OrchestratorEngine.chat()`)는 `streamSink=null`로 전달
3. **네이티브 스트리밍 유지** — Phase 2-A와 자연스러운 연결, thinking이 진짜 시간 흐름대로 송출됨

## 4. 옵션 B 상세 설계

### 4.1 새로운 타입 — `StreamEvent` sealed interface

```java
// com.platform.orchestrator.stream.StreamEvent
public sealed interface StreamEvent {
    record TextDelta(String delta) implements StreamEvent {}
    record ThinkingDelta(String delta) implements StreamEvent {}
    record ToolUseStart(String id, String name, Map<String, Object> input) implements StreamEvent {}
    record ToolResultEvent(String toolUseId, String output, boolean isError) implements StreamEvent {}
    record Done(TokenUsage usage) implements StreamEvent {}
}
```

### 4.2 `ToolCallHandler.executeLoop()` 시그니처 확장

```java
// 기존
public LLMResponse executeLoop(

    ModelConfig config, String sessionId, ToolRegistry toolRegistry,
    ToolFilterContext toolFilter, String toolChoice, ToolContext toolContext

    LLMAdapter adapter, String resolvedModel, List<UnifiedMessage> messages,
    ModelConfig config, String sessionId, ToolRegistry toolRegistry,
    ToolFilterContext toolFilter, String toolChoice, ToolContext toolContext,
    Consumer<StreamEvent> streamSink  // nullable

// 기존 시그니처는 위 오버로드에 streamSink=null로 위임
```

### 4.3 루프 내부 분기 (한 이터레이션)

```java
// 의사 코드
if (streamSink == null) {
    LLMResponse response = adapter.chat(request).get();
    // 기존 로직
} else {
    StringBuilder textBuf = new StringBuilder();
    List<ContentBlock.ToolUse> toolUses = new ArrayList<>();
    TokenUsage usage = null;
    AtomicReference<LLMResponse.FinishReason> finish = new AtomicReference<>();

    adapter.chatStream(request, chunk -> {
        if ("thinking".equals(chunk.type())) {
            streamSink.accept(new StreamEvent.ThinkingDelta(chunk.delta()));
        } else if (chunk.delta() != null) {
            textBuf.append(chunk.delta());
            streamSink.accept(new StreamEvent.TextDelta(chunk.delta()));
        }
        if (chunk.done()) {
            usage = chunk.usage();
            finish.set(chunk.finishReason());  // ← 어댑터에서 제공 필요
            // toolUses는 어댑터가 chunk 누적 시점에 별도로 노출 필요
        }
    });

    // 재구성된 LLMResponse
    LLMResponse response = new LLMResponse(..., textBuf, toolUses, usage, finish.get());
}
// 이후 finishReason == TOOL_USE 분기는 공통.
// 도구 실행 직전에 streamSink.accept(new ToolUseStart(...))
// 실행 직후 streamSink.accept(new ToolResultEvent(...))
```

### 4.4 어댑터 계약 확장 (필수)

`LLMStreamChunk`가 **완료 청크에서 `finishReason`과 `toolCalls`를 노출**해야 함. 현재는 `done + usage`만 있음:

```java
// 현재
public record LLMStreamChunk(
    String id, String model, String delta, boolean done, TokenUsage usage, String type
) { ... }

// 확장
public record LLMStreamChunk(
    String id, String model, String delta, boolean done, TokenUsage usage, String type,
    LLMResponse.FinishReason finishReason,  // 신규, done=true 때만 값 설정
    List<ContentBlock.ToolUse> toolUses     // 신규, done=true 때만 값 설정
) {
    // 하위 호환 생성자 유지
}
```

**어댑터별 작업**:
- `AnthropicAdapter.chatStream()` — `message_stop` 이벤트에서 `stop_reason` → `FinishReason.TOOL_USE` 매핑, `content_block.start` 중 `type=tool_use`를 누적하여 최종 청크에 실어 보냄
- `OpenAIAdapter.chatStream()` — `finish_reason=tool_calls` 매핑, `tool_calls` 배열을 델타 단위로 누적
- 그 외 어댑터(Bedrock, Vertex, Ollama) — 프로바이더별 SSE 포맷 매핑

### 4.5 `OrchestratorEngine.chatStream()` 교체

```java
// 현재: adapter.chatStream 직접
// 변경 후: toolCallHandler.executeLoop(..., streamSink) 호출
//         streamSink는 LLMStreamChunk로 어댑터 컴슈머에 다시 감싸서
//         ChatController가 SSE 이벤트로 뿌리도록 브릿지
```

### 4.6 ChatController 확장

```java
// streamResponse() 확장: StreamEvent → SSE event name 매핑
switch (ev) {
    case StreamEvent.TextDelta t     -> emit("delta",            Map.of("delta", t.delta()));
    case StreamEvent.ThinkingDelta t -> emit("thinking",         Map.of("delta", t.delta()));
    case StreamEvent.ToolUseStart s  -> emit("tool_use_start",   Map.of("id", s.id(), "name", s.name(), "input", s.input()));
    case StreamEvent.ToolResultEvent r -> emit("tool_result",    Map.of("tool_use_id", r.toolUseId(), "output", r.output(), "is_error", r.isError()));
    case StreamEvent.Done d          -> emit("done",             Map.of("done", true));
}
```

## 5. 영향 범위 및 리스크

| 항목 | 영향 | 완화 |
|---|---|---|
| `LLMStreamChunk` 레코드 확장 | 모든 어댑터·소비자 컴파일 영향 | 하위 호환 생성자 유지 |
| 어댑터별 finishReason/toolUses 추출 로직 | 각 프로바이더 구현 필요 | Anthropic/OpenAI 우선, 나머지는 후속 |
| 비스트리밍 경로 회귀 리스크 | 낮음 (기존 오버로드 위임) | 기존 단위 테스트 통과 확인 |
| 도구 실행 중 스트림 공백 | 긴 도구 실행(수초~수십초) 동안 클라이언트에 아무 이벤트 없음 | `tool_use_start` 이벤트가 "작업 중" 상태 표시. 필요 시 heartbeat 이벤트 검토 |
| Hook 디스패치 타이밍 | 기존과 동일 — 스트림 발행만 추가 | 테스트 커버 |
| `concurrencySafe` 병렬 + 스트림 순서 | 동시 실행 도구의 `tool_use_start`/`tool_result` 순서가 섞일 수 있음 | 이벤트에 `tool_use_id`로 매칭 키 전달, FE에서 ID 기반 블록 매칭 |

## 6. 어댑터별 구현 난이도

| 어댑터 | finishReason 추출 | toolUses 누적 | 난이도 |
|---|---|---|---|
| Anthropic (`AnthropicAdapter`) | `message_stop.stop_reason == "tool_use"` | `content_block_start/delta/stop` 이벤트 내 `type=tool_use` 누적 | 중 |
| OpenAI (`OpenAIAdapter`) | `choices[].finish_reason == "tool_calls"` | `delta.tool_calls[].index.function.arguments` 누적 | 중 |
| Bedrock | 프로바이더 모델별 상이 (Claude via Bedrock이면 Anthropic과 동일) | 동일 | 중 |
| Vertex AI | Gemini 스트리밍 이벤트 매핑 | 프로바이더별 | 상 |
| Ollama | tool call 지원 모델 한정 | 프로바이더별 | 하(미지원 시 no-op) |
| OpenClaude (사내) | 확인 필요 | 확인 필요 | 미정 |

**본 Phase 2-B 범위 제안**: **Anthropic + OpenAI만** 1차 지원. 다른 어댑터는 non-stream 경로로 폴백(`streamSink=null`)하거나 tool 이벤트만 미발행.

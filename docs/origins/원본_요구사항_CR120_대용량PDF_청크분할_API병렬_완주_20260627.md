**발단**: CR-118/119 e2e(오산 건 opportunity-analysis) 중, 35MB 도면 fact 누락의 근본 추적

## 문제 (실측 확정)

bidding extract_facts 가 도면 PDF(As_built, 81p/35MB)를 "모든 fact 빠짐없이 sourceQuote 붙여"
전수 분석하라고 시킴 → 모델이 20p씩 9번 읽어 **컨텍스트에 누적** → Anthropic API 32MB 초과 → 실패.

### 누구도 못 피하는 구조적 한계 (실측 증명)
- **순수 claude CLI 직접 실행**(우리 Worker/MCP 전부 제거)도 동일하게 실패:
  - "Read and analyze..." (적당히) → 59초 완주 (전부 안 읽고 요약)
  - "Read **pages 1-180** and summarize" (전체 강제) → `RESULT is_error=True: Request too large (max 32MB)`
- 즉 **32MB 는 Anthropic API 물리 한계**. CLI·우리·직접호출 누구도 한 요청에 못 넘김.
- **claude.ai 는 전체를 컨텍스트에 안 넣음** (RAG 검색 + 텍스트 우선) → 32MB 회피. "전수"를 강요 안 함.

### 가드는 작동했으나 누적은 못 막음 (openclaude 기준 = 우리 포팅 동일)
- openclaude 상수(src/constants/apiLimits.ts): `PDF_AT_MENTION_INLINE_THRESHOLD=10`(통째 읽기 차단=쪼개라),
  `PDF_EXTRACT_SIZE_THRESHOLD=3MB`(이미지화 vs PDF통째 전송 결정 — 쪼개기 아님), `PDF_MAX_PAGES_PER_READ=20`.
- **3MB = "이미지냐 PDF냐", 10p = "쪼갤지" — 별개. 쪼개는 1차 기준은 페이지 10개.**
- 우리 PdfVisionResolver 도 동일 포팅(10p NEEDS_SPLIT + 20p/read). **가드는 "한 번에 통째 읽기"만 막음.**
- 그러나 모델이 20p씩 나눠 불러 **누적**하면 32MB → 가드가 못 막는 영역(openclaude 도 동일 한계).
- ※ 부수 발견: 우리 10p 가드는 `allowSplitGuard` 조건으로 ParseDocumentTool 경로만 true,
  MCP/첨부 경로(ServerMcpToolDispatcher/ChatController)는 false → 원본의 "무조건" 과 다름(별도 보완거리).

## 실측 숫자 (분할 기준의 근거)
- As_built__B949__2.pdf = **81페이지, 33.8MB**.
- 사이드카 렌더(150 DPI) base64 실측: **1.2~1.5 MB/페이지**. 20p = 24MB → **~21p 에서 32MB**.
- 운영 image-dpi=100 이면 더 가벼우나, 여러 청크 누적 시 결국 32MB.
- → 분할 기준은 "페이지 수"가 아니라 **렌더 base64 누적 ≤ 안전선(예 24MB)**. 텍스트PDF는 가벼워 많이,
  도면은 무거워 적게 — 크기 기준이 자동 적응.

## 요구 — "쪼개서 합치기" A안 (완주 보장)

**전수는 지키되 한 번에 컨텍스트에 든 양을 항상 32MB 밑으로.** 청크를 물리적으로 따로 처리해 누적 원천 차단.

### A안 = 청크별 독립 분석 후 합치기
1. `pdf_page_count` + 첫 청크 실제 렌더 크기로 **역산**(추정 금지) → 청크 경계 산출(≤24MB).
2. 각 청크(예 20p)를 **별도 LLM 호출**로 fact 추출. 원본 이미지는 그 호출에서만 → 누적 안 됨.
3. 청크 결과(텍스트 fact)만 합쳐 최종 리스트 → 전수 달성, 32MB 절대 안 침.

### CR-117 이 A를 했다 버린 3이유 → 오늘 해결책 확정
| CR-117 실패 | 해결 |
|---|---|
| ① 크기 추정 5배 빗나감(1-3p 샘플→0.32MB/p, 실제 1.5MB/p) | 첫 청크 **실측 렌더**로 역산 |
| ② 청크마다 CLI spawn(169p→22 spawn, 느림) | 청크를 **CLI 말고 API 직접 호출**(spawn 0, 병렬). 도면 비전은 API 가 직접 |
| ③ split-max-pages 40 ≠ Read 20p 한계 | 분할을 **20p(max-pages-per-read)에 맞춤** |

**핵심**: "쪼개서 합치기" 자체는 맞았고, CR-117 의 방식(추정분할 + 청크당 CLI spawn)이 틀렸던 것.
**②가 결정타** — 쪼갠 청크를 CLI 가 아니라 API 어댑터로 직접 돌리면 spawn 비용 사라짐.

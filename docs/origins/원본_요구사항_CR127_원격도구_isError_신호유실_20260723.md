# CR-127 원본 — 원격 MCP 도구의 `isError:true` 가 정상 결과로 둔갑

작성일: 2026-07-23
발견 경위: bp-wes 브리핑이 실데이터 대신 창작된 숫자를 답하는 문제를 추적하다 확인.
소비앱(WES) 측에서 "aimbase 가 인자를 전달하지 않는다" 는 가설이 제기되었으나,
실측 결과 인자는 정상 전달되고 있었고 진짜 결함은 **에러 신호 유실** 이었다.

---

## 1. 문제

`MCPServerClient.callTool()` 이 원격 도구의 `isError:true` 를 로그로만 남기고
**텍스트만 뽑아 정상 결과처럼 반환**한다.

```java
// platform-core/src/main/java/com/platform/mcp/MCPServerClient.java:290-297
if (Boolean.TRUE.equals(result.isError())) {
    log.warn("MCP tool '{}' returned an error result", toolName);   // ← 로그만
}

return result.content().stream()                                    // ← 에러여도 그대로 반환
        .filter(c -> c instanceof McpSchema.TextContent)
        .map(c -> ((McpSchema.TextContent) c).text())
        .collect(Collectors.joining("\n"));
```

호출자는 반환값이 성공인지 실패인지 구분할 수 없다. `ServerMcpToolDispatcher` 는
**예외만** `errorResult()` 로 변환하므로, 예외 없이 `isError:true` 만 온 경우
CLI 에는 `isError:false` 로 나간다.

---

## 2. 왜 위험한가 — 모델이 숫자를 창작한다

도구가 실패해도 모델은 "정상 응답" 을 받는다. 데이터가 없으니 그럴듯한 값을 지어낸다.

실제 관측 (bp-wes 전일 브리핑):

```
도구 호출 8회 → 전부 isError:true (aimbase 로그에 returned an error result 8건)
모델 응답     → 처리량 12,450 (창작)
실제 값       → targetQty 4,964
```

사용자는 화면에 그럴듯한 숫자가 뜨므로 **실패를 인지할 수 없다.**
운영 데이터로 오인해 의사결정에 쓰이면 직접적 피해가 된다.

메모리의 CR-112 / CR-119 와 같은 계열이다 — "is_error 둔갑".
그때는 CLI 스트림 경로였고, 이번은 **원격 MCP 도구 경로** 다. 같은 병이 다른 길에 남아 있었다.

---

## 3. 오진 정정 — "aimbase 가 인자를 안 넘긴다" 는 틀렸다

WES 측 분석은 "aimbase RemoteAgentToolExecutor 가 인자를 빈 채로 보낸다" 였으나
실측으로 반증된다. aimbase MCP 를 경유해 인자와 함께 호출:

```
[A] arguments={"date":"2026-07-22","center":"ALL"}
 → {"date":"2026-07-22","targetQty":5486,"processedQty":5148,"progressRate":0.9384}
   isError:false — 실데이터 정상 반환

[B] arguments={}
 → {"content":[{"type":"text","text":"text"}], "isError":false}
```

인자가 유실된다면 [A] 의 값이 나올 수 없다. 코드상으로도 인자를 버리는 지점이 없다:

```
ServerMcpConfig:181   request.arguments() → dispatcher.dispatch(...)
ServerMcpToolDispatcher:107  args == null ? Map.of() : args   (null 일 때만 방어)
RemoteAgentToolExecutor:45   client.callTool(toolDef.name(), input)  (그대로 전달)
```

즉 **인자가 실제로 비어서 온 것** 이며, aimbase 가 버린 것이 아니다.
왜 모델이 인자 없이 호출했는지는 별건(§6)이다.

`[B]` 의 `"text"` 리터럴 문자열은 WES 도구가 인자 없을 때 반환하는 값이고,
`isError:false` 라 aimbase 도 정상으로 취급한다 — 이 역시 WES 측 사안이다.

---

## 4. 수정 방향

`isError:true` 를 **전용 예외로 승격** 해 디스패처의 `errorResult()` 경로를 타게 한다.

```java
if (Boolean.TRUE.equals(result.isError())) {
    String text = extractText(result);
    log.warn("MCP tool '{}' returned an error result: {}", toolName, text);
    throw new MCPToolErrorException(toolName, text);
}
```

### 4-1. 전용 예외 타입이 필요한 이유 (중요)

`MCPToolExecutor.execute()` 는 예외를 잡아 **재연결 후 재시도** 한다:

```java
// MCPToolExecutor.java:46-65
try {
    return client.callTool(definition.name(), input);
} catch (Exception e) {
    manager.reconnect(serverId);              // ← 전송 장애 가정
    return fresh.callTool(definition.name(), input);
}
```

`isError` 를 일반 `Exception` 으로 던지면 **도구 로직 에러(잘못된 인자 등)에도
무의미한 재연결·재시도** 가 붙는다. 전송 장애가 아니므로 재시도해도 같은 에러다.

→ `MCPToolErrorException` 을 신설하고, `MCPToolExecutor` 는 이 타입을 재시도 대상에서
   제외(그대로 재던짐)한다. 전송 계층 예외만 기존대로 재연결한다.

### 4-2. 영향 범위

`callTool` 호출처:

| 호출처 | 현재 동작 | 변경 후 |
|--------|----------|---------|
| `RemoteAgentToolExecutor` (2곳) | 에러 텍스트 반환 | 예외 → 디스패처가 errorResult (**목표**) |
| `MCPToolExecutor` | 에러 텍스트 반환 | 예외, 단 재시도 제외 |
| `MCPRagClient` (6곳) | 에러 텍스트를 parseJson | 예외 전파 — 회귀 확인 필요 |

`MCPRagClient` 는 `parseJson(result)` 로 넘기므로 현재는 에러 텍스트를 파싱하다
실패하거나 이상한 값을 반환했을 것이다. 예외 전파가 더 정확한 동작이지만
RAG 회귀 테스트로 확인한다.

`health ping`(`list_document_formats`)은 이미 `catch (Exception)` 으로 감싸고 있어
영향 없다.

---

## 5. 검증 방법

- 단위: `isError:true` 결과가 `MCPToolErrorException` 으로 승격되는지
- 단위: `MCPToolExecutor` 가 `MCPToolErrorException` 은 재시도하지 않는지
- e2e: WES `get_progress` 를 인자 없이 호출 → CLI 가 `isError:true` 를 받는지
  (현재는 `isError:false` + `"text"`)
- 회귀: platform-core 전체

---

## 6. 별건 — 모델이 왜 인자 없이 호출했나

이 CR 의 범위는 "실패를 실패로 전달" 까지다. 모델이 애초에 인자를 안 넣은 원인은
따로 봐야 한다. 유력한 가설:

이 환경의 MCP 도구는 **deferred(지연 로딩)** 이라 모델이 `ToolSearch` 로 스키마를
불러와야 파라미터를 안다(CR-126 §5-1). 스키마를 못 받았거나 불완전하게 받으면
파라미터를 모른 채 빈 인자로 호출할 수 있다.

CR-127 수정이 들어가면 모델이 실패를 인지하게 되므로, 그 뒤 재호출 시 인자를
채우는지 관찰해 판단한다. 창작이 사라지는 것만으로도 피해는 차단된다.

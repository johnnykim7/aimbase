## 발단

지난 세션 마지막: "agent를 Python으로 포팅하면 사이드카와 한 덩어리로 쉽지 않냐" → TURN-TCP 재작성 비용으로 보류. 본 세션에서 이어받아 로컬 문서 분석 아키텍처를 재정리.

## 사용자가 정리한 배경 (발화 원문 요지)

1. **Agent 만든 배경/기능**: 내 로컬 PC 문서를 LLM으로 분석/활용하고 싶었음 → PC에 Agent 설치 → Agent가 문서 읽게 함(SDK Toolkit) → Claude CLI 어댑터 기능도 추가됨.
2. **Side-Car 문서 도구**: LLM API 호출 시 사이드카를 도구로 전달하면 MCP로 문서 파싱. 사이드카는 서버 설치 → 서버 내 문서/URL 처리(URL 다운로드는 실측 필요).
3. **재편 구상**: 문서 파싱용이라면 별도 사이드카로 분리, 기존 사이드카 문서도구 + Agent SDK Toolkit 통합. 기존 사이드카는 RAG 본연 유지. Claude CLI 어댑터는 별도 Agent로 분리.

## 논의 진행 (대화로 좁혀진 결론)

- "내 PC 문서를 LLM이 읽게 한다"는 결국 사이드카 기능 → 통합 검토.
- **사이드카 입력 방식 실측**: parse_document = base64 또는 URL(다운로드). read_pdf/docx 등 = base64. ingest_file = 로컬 path. → "로컬 파일시스템도 받게 수정" 결정 → (선행 완료, file_path 추가)
- **SDK Toolkit ≠ 문서용**: 14개는 파일시스템/셸(FileRead/Grep/Bash...). 문서 파싱 없음. "toolkit이 의미 없다(a: 문서 읽기는 사이드카로 흡수)".
- **메인 BE도 SDK Toolkit 사용 실측**: SdkToolBeanConfig 가 개별 도구 14개 @Bean 등록(SdkToolKit 묶음 클래스만 안 거침). → Claude 1차 "메인 안 씀" 오판 후 정정(전수 조사). grep/bash 등은 Java 가능 → SDK Toolkit, 문서 파싱은 Python → 사이드카.
- **로컬 사이드카 거취**: Grep 등 단순 툴 위해 Python 사이드카 재작성은 이상함. Python 포팅(14개 재작성+이중관리) 기각 → "한 패키지 2프로세스".
- **Docker 문제 제기(사용자)**: 실제 사용자는 Docker 없을 것 → 로컬 사이드카 Docker안 폐기.
- **핵심 통찰(사용자)**: "뒤지기(찾기)와 파싱은 다르다. 뒤지기는 agent가, 파싱은 사이드카가." → 파일을 서버 사이드카로 base64 보내도 file_path 보내도 기능 동일(네트워크/시간만 차이).
- **발화 추적**: "내 PC /Users/sykim/aaa 에서 PDF 찾아 분석해줘"
  - 라우팅(어느 agent?) → user_ref 매핑(CR-075, 같은 매핑) ✅
  - 찾기(Glob/Grep) → 로컬 agent 도구 ✅
  - 파싱 → 로컬 파일 byte → 서버 사이드카 ❌ **빈 구멍**
- **사용자 통찰**: "기존엔 Runner와 로컬이 같이 있어서 문제 안 됐는데 지금은 Runner 따로 / 로컬 agent 따로라 문제." → 정확. Runner+도구 동거 시 CLI·파일 같은 PC라 로컬/서버 구분 불필요했음.

## 브리핑 원문

### 주제
- CR-177 ~ CR-189 13건을 origin/dev 그대로 운영(chaws)에 올리기로 했다. IR-002 가 계획을 짜며 배포 전에 막히는 것 4건을 찾았다. 이 창이 그 4건을 고친다.
- 배포 자체는 IR-002 창(aimbase-75491)이 한다. 이 창은 고침과 확인까지 하고 컨타에 완료 보고한다.

### 고칠 4건
1. 위젯 빌드 결과를 dev 에 다시 커밋한다. 지금 커밋된 위젯 파일은 CR-185 마지막 고침(31ced554) 전 판이다. 운영 빌드 작업 폴더에는 위젯 빌드 결과가 없어 커밋된 파일이 그대로 jar 에 들어간다. origin/dev 소스로 빌드한 결과가 59 에서 확인한 위젯과 같은 동작인지 대조한다(59 위젯은 git 밖에서 빌드되어 파일 단위로는 다를 수 있다).
2. dev 의 `docker-compose.chaws.yml` 에 CS 실행기 `AIMBASE_RUNNER_MAX_PROCESSES: "2"` 를 되살린다. 운영 가지(4b6a4b08)에만 있고 dev 에서 빠졌다(CR-173 14절). 빠진 경위를 보고 다른 줄도 같이 빠졌는지 운영 가지와 대조한다.
3. 되돌릴 판을 미리 만든다. 운영 판 f7c02f4 에 5300d984(높은 판 번호 무시, CR-182)를 얹은 판을 만들고, 이번 배포 뒤처럼 높은 마이그레이션 판이 있는 DB 로 로컬에서 기동되는지 확인한다. 판을 어디에 두는지(가지 이름, 커밋)를 보고에 적는다.
4. 운영 앞단 nginx(ai.banpoom.co.kr)에 세 길을 연다: `/share/`, `/api/v1/workflows/runs/`, `/api/v1/chat/voice/stream` 의 웹소켓 업그레이드. 설정 고친 안을 만들어 `nginx -t` 로 검사할 수 있게 준비하고, 운영 적용은 컨타에 `[승인요청]` 으로 올린다. 운영 nginx 설정 파일이 어느 레포(bp-infra 등)에 있는지 먼저 본다.

### 지킬 것
- 운영 서버와 운영 DB 는 읽기만 한다. 운영 nginx 적용과 재적재는 승인 뒤에만 한다.
- 소스 수정 전에 `[규모]` 를 선언한다. 1, 2 는 빌드 결과와 설정 파일이고 3 은 되돌림용 가지다.
- 운영 배포, 운영 재기동은 이 창이 하지 않는다(IR-002 몫).
- 고객 테넌트(AXOPM, bidding_system, axopm_companyA) 의 키와 연결은 쓰지 않는다.
- 작업 폴더는 origin/dev 에서 만든 자기 워크트리를 쓴다. 메인 폴더는 쓰지 않는다.
- 남의 레포 소스는 고치지 않는다. nginx 설정이 bp-infra 에 있으면 인프라 파일 예외로 고칠 수 있다.

# CR-124 원본 — MCP SDK 2.0.0 업그레이드 (프로토콜 2025-11-25 협상 실패 해소)

작성일: 2026-07-21
발단 세션: bp-wes 원격 도구 CLI 노출 작업(CR-121/122/123) 후속으로 발견

---

## 1. 발단 — 어떻게 발견됐나

bp-wes 소비앱이 등록한 원격 도구 8종(`get_progress`, `get_bottleneck` 등)을 Claude CLI 러너가
호출하지 못하는 문제를 추적하는 과정에서 드러났다. 앞선 3건을 차례로 해소했는데도 증상이 남았다.

| 순번 | 해소한 문제 | 결과 |
|---|---|---|
| CR-121 | 원격 도구가 `/mcp/sse` 에 노출되지 않음 (Spring 빈 vs ToolRegistry) | 노출 110개 확인 |
| CR-122 | 테넌트 DataSource 기동 로드 실패 (BCrypt 저장↔평문 사용) | 테넌트 7/7 로드 |
| CR-123 | 커넥션 config 변경이 어댑터 캐시에 반영 안 됨 | `toolMode=AIMBASE` 전파 확인 |
| **CR-124** | **MCP 프로토콜 버전 협상 실패** | **미해결 — 본 CR** |

CR-123 까지 끝내 `toolMode=AIMBASE` 로 워커가 뜨는 것까지 확인했으나, CLI 의 MCP 상태가
`status=pending` 에서 고정되고 도구가 0개인 증상이 남았다.

## 2. 근본 원인 (운영 로그 실측 확정)

aimbase BE 로그:
```
INFO  i.m.server.McpAsyncServer : Client initialize request - Protocol: 2025-11-25
WARN  i.m.server.McpAsyncServer : Client requested unsupported protocol version: 2025-11-25,
                                  so the server will suggest the 2024-11-05 version instead
```

- **클라이언트**: Claude Code CLI 2.1.197 → `2025-11-25` 요구
- **서버**: aimbase, MCP Java SDK **0.17.0** → `2024-11-05` / `2025-03-26` / `2025-06-18` 만 지원
  (`McpSchema.LATEST_PROTOCOL_VERSION = "2025-06-18"` — jar 디컴파일 실측)
- 서버가 `2024-11-05` 를 역제안 → CLI 가 수용하지 않음 → 핸드셰이크 미완료

CLI 요청 5회 전부 동일하게 재현되는 **결정적 실패**(간헐 아님).

### 서버는 정상임을 증명한 대조 실험

러너 컨테이너 안에서 러너와 **동일한 키·헤더**로 수동 프로브(프로토콜만 `2024-11-05` 명시):

```
event:endpoint  → data:/mcp/message?sessionId=...        (SSE 정상)
initialize      → HTTP 200 + result 정상 수신
tools/list      → 도구 110개 반환 (get_progress / get_bottleneck / get_current_time 포함)
```

즉 **SSE·인증·도구 노출·CR-121 수정 전부 정상**이며, 실패 지점은 프로토콜 버전 협상 단 하나다.

## 3. 영향 범위 — 소비앱 문제가 아니다

- bp-wes 가 만든 도구/등록 방식과 무관. 소비앱 코드로는 해결 불가
- **AIMBASE 모드를 쓰는 순간 어느 소비앱이든 동일하게 발생**한다
- 지금까지 표면화되지 않은 이유: 다른 러너(bidding/axopm/workmap)가 전부 **NATIVE 모드**라
  MCP 연결 자체를 시도하지 않았다(`mcp_servers=[]`). bp-wes 가 처음 AIMBASE 를 써서 드러났다
- **현재 aimbase 는 AIMBASE 모드가 사실상 동작 불가 상태** (어느 러너든 MCP 도구 0개)

## 4. 해결 경로 — SDK 2.0.0 이 유일

외부 조사 결과:

- MCP Java SDK **2.0.0** 이 `2025-11-25` 스펙을 지원 (모든 transport 에 추가)
- **1.x 대는 미지원** — 1.1.3 도 `2024-11-05/2025-03-26/2025-06-18` 만 지원
  ([issue #715](https://github.com/modelcontextprotocol/java-sdk/issues/715))
- 따라서 0.17.0 → **2.0.0** 직행 외에 선택지가 없다

### 2.0.0 주요 Breaking Change

> ⚠️ 아래 표는 최초 작성 시 릴리스 노트 기준이었다. §6 실측으로 1행이 정정됐다.

| 변경 | aimbase 영향 |
|---|---|
| ~~서버측 SSE transport deprecated~~ → **`mcp-spring-webmvc` 아티팩트 자체가 2.0.0 에 없음(실측)** | `WebMvcSseServerTransportProvider` 사용 불가 — **Streamable HTTP 전환 필수** |
| `JsonSchema` → `Map` (inputSchema) | `McpToolConversion` / `AimbaseAdminMcpConfig.schema()` / `MCPServerClient.buildSchema` |
| `CallToolResult` 생성자 4-arg 화 | `ServerMcpToolDispatcher` 축약 생성자 호출부 다수 |
| sealed interface 제거 (JSONRPCMessage/Request/Result) | 패턴매칭 코드 |
| lenient deserialization | 하위호환 개선(위험 낮음) |

**주의**: `McpSchema.JsonSchema` 클래스 자체는 2.0.0 에도 남아있고 `Tool.Builder.inputSchema()` 가
`JsonSchema` / `Map` 양쪽 오버로드를 제공한다. 다만 `Tool.inputSchema()` **게터의 반환 타입이
`Map<String,Object>` 로 바뀌어** 이를 읽는 쪽(`MCPServerClient.buildSchema`)이 깨진다.

## 6. 선행 확인 사항 → **✅ 5건 전부 실측 완료 (2026-07-22)**

> 아래는 추정이 아니라 **2.0.0 jar 디컴파일 + Claude CLI 실 핸드셰이크 프로브** 결과다.

| # | 질문 | 실측 답 |
|---|---|---|
| ① | 2.0.0 서버측 SSE 계속 쓸 수 있나 | **아니오. `mcp-spring-webmvc` 아티팩트가 2.0.0 에 아예 없음**(0.18.3 에서 끊김, BOM 미포함) |
| ② | CLI 가 Streamable HTTP 지원하나 | **예. `"type":"http"` 로 실제 연결·도구노출 성공** |
| ③ | addTool/removeTool/notifyToolsListChanged | **3개 전부 2.0.0 `McpSyncServer` 에 생존** — CR-121 로직 유지 가능 |
| ④ | Spring AI 정합성 | webmvc 모듈 소멸 → `RouterFunction` 빈 → **Servlet 등록**으로 전환 필요 |
| ⑤ | agent·BE 동시 배포 | `inputSchema` 타입이 양쪽 공유 → **동시 배포 필요** |

### ★★ 최중요 정정 — "SDK 2.0.0 올리면 해결"은 **틀렸다**

2.0.0 에 `2025-11-25` 가 추가된 것은 사실이다:
```
io.modelcontextprotocol.spec.ProtocolVersions
  MCP_2024_11_05 / MCP_2025_03_26 / MCP_2025_06_18 / MCP_2025_11_25
```

**그러나 SSE transport 는 2.0.0 에서도 `2024-11-05` 단 하나만 광고한다**(바이트코드 실측):
```
HttpServletSseServerTransportProvider.protocolVersions()
    0: ldc "2024-11-05"; invokestatic List.of(Object)     ← 단일값 하드코딩
HttpServletStreamableServerTransportProvider
    → protocolVersions() 오버라이드 없음 → McpServerTransportProviderBase 기본값 상속
    → 4종 전부(2025-11-25 포함)
```

즉 **SDK 만 2.0.0 으로 올리고 SSE 를 유지하면 증상이 100% 그대로 재현된다.**
오히려 협상 가능 버전이 0.17.0(3종) → SSE 2.0.0(1종)으로 **좁아진다.**
`2025-11-25` 획득 조건은 SDK 버전이 아니라 **transport 교체**다.

### CLI 실측 프로브 (2026-07-22, 로컬 CLI 2.1.109)

**(A) Streamable HTTP `"type":"http"` → 성공**
```
{"mcpServers":{"probe":{"type":"http","url":"http://127.0.0.1:8899/mcp"}}}
→ CLIENT_PROTOCOL_VERSION=2025-11-25        (프로브 서버가 그대로 수용)
→ CLI 가 mcp__probe__probe_ping 도구를 실제로 인식·나열
```

**(B) SSE + 서버가 `2024-11-05` 강제 → 운영 증상 그대로 재현**
```
{"mcpServers":{"sseprobe":{"type":"sse","url":"http://127.0.0.1:8898/sse"}}}
→ SSE_CLIENT_ASKED=2025-11-25
→ 서버가 2024-11-05 역제안 → CLI 도구 0개 (결과 없음)
```
(B) 가 현재 운영 상태와 동일 = **근본 원인 확정 + 해결책 검증 동시 완료.**

CLI zod 스키마에서도 transport 유니온 확인:
`y.enum(["stdio","sse","sse-ide","http","ws","sdk"])` — `http` = Streamable HTTP 정식 지원.

> 로컬 CLI 는 2.1.109, 운영은 2.1.197. 둘 다 `2025-11-25` 를 요구하므로 결론 동일.
> (운영 로그의 클라이언트 요청 버전이 `2025-11-25` 로 이미 실측돼 있음 — §2 참조)

   - 3곳: `ServerMcpConfig`★ / `AimbaseAdminMcpConfig`★ / `AgentMcpServer`★
3. **엔드포인트 등록 방식** — `RouterFunction<ServerResponse>` 빈 → **`ServletRegistrationBean`**
   (2.0.0 provider 는 `jakarta.servlet.http.HttpServlet` 상속체) — 2곳
4. **스키마 타입** — `McpSchema.JsonSchema` → `Map<String,Object>`
   (`McpToolConversion` / `AimbaseAdminMcpConfig.schema()`·`schemaReq()` / `MCPServerClient.buildSchema`)

6. **러너 MCP config** — `"type":"sse"` → `"type":"http"`, URL `/mcp/sse` → Streamable 단일 엔드포인트
   - `ClaudeCliAdapterConfig.java:131,135` (CR-072 주석도 함께 갱신)
7. **Security** — `/mcp/**` permit 규칙을 새 엔드포인트 형태로 재작성
8. **CR-121 회귀 방지** — 주기 동기화(`addTool`/`removeTool`/`notifyToolsListChanged`)와
   기동 순서 가드가 새 transport 위에서 그대로 동작하는지 확인 (API 는 생존 확인됨)

## 6-3. 잔여 3건 처리 완료 (2026-07-22)

§6-2 에서 "미검증"으로 남겼던 3건을 순서대로 처리했다. 모두 워크트리 프로토타입 기준.

### ① Spring Security 필터체인 — **변경 불필요 (실측 확인)**

Streamable 요청은 하위경로 없이 `POST /mcp` 로 오는데, 기존 매처가 이미 이를 커버한다.
`AntPathRequestMatcher` 로 실제 판정하는 테스트를 붙여 확인:
```
"/mcp/**"       vs "/mcp"        → true
"/admin-mcp/**" vs "/admin-mcp"  → true
```
`Cr124SecurityPathMatchTest` 2 PASS. **`SecurityConfig` 수정 없음.**

### ② `McpTenantSessionFilter` — **실제로 깨져 있었고, 수정함**

기존 필터는 `/admin-mcp/sse` · `/admin-mcp/message` **두 하위경로 문자열에만** 반응한다.
Streamable 은 둘 다 존재하지 않으므로 **테넌트 전파가 조용히 끊긴다**(예외도 안 남).
→ `/admin-mcp` 이하 전체를 대상으로 바꾸고, `tenant_id` 가 있으면 갱신·없으면 최근값 사용.

추가로 **요청 종료 시 `TenantContext` 정리**를 넣었다. Streamable 은 요청마다 스레드가
재사용될 수 있어 필터가 심은 값이 다음 요청으로 샐 수 있기 때문이다.

`Cr124TenantFilterStreamableTest` 4 PASS (전파 / 후속요청 재사용 / 누수없음 / 무관경로 무영향).

### ③ 러너 config + **BE→agent 클라이언트 경로 (조사 때 못 본 것)**

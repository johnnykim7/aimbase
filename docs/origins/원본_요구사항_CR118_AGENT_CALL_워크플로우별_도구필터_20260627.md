# CR-118 원본 요구사항 — AGENT_CALL 스텝의 워크플로우별 도구 필터(ToolFilterContext) 배선

날짜: 2026-06-27
출처: CR-117(빈응답/32MB) 작업 중, CLI 어댑터가 `builtin_file_read` 를 "No such tool" 로 반복 호출하는 노이즈를 추적하다 발견

## 발단 (사용자 발화)

- (CLI 도구 노이즈 정리 논의 중, 전역에서 builtin_* 를 빼자는 제안에) **"이게 다른 워크플로우/기능에 builtin_* CLI 호출이 있으면 영향 — 이걸 워크플로우마다 설정하도록 되어있지 않나요?"**
- (미구현 확인 후) **"원래 의도는 지금 얘기한 방식이었는데 안 되어 있으면 별도 CR로 따주고 다른 세션에서 작업하자."**

## 실측으로 확정한 현 코드 상태 (2026-06-27 소스)

워크플로우 AGENT_CALL 스텝의 도구 노출은 **2단계**로 결정된다:

1. **전역 정책** — `mcp.cli-exposed-tools`(master global_config 단일 값). `ToolRegistry.getToolDefs(filter)` 가
   builtin 도구 중 `McpExposurePolicy.resolve(executor) != CLI` 인 것을 제외(ToolRegistry.java:103-106).
2. **요청별 필터** — `ToolFilterContext filter`(allow/exclude 이름 목록 + readOnly/permission/capability).
   `getToolDefs(filter)` 의 `filter.isToolAllowed(name)`(ToolRegistry.java:112) 등으로 추가 축소.

→ **워크플로우(AGENT_CALL)마다 도구를 좁히는 메커니즘(ToolFilterContext)은 이미 존재한다.**

### 그런데 AGENT_CALL 은 그 필터를 config 에서 안 받는다 (미배선)

- `SubagentRunner.executeAgent`(SubagentRunner.java:331) 가 `buildToolFilter(typeConfig)` 로 toolFilter 를 만든다.
- `buildToolFilter`(SubagentRunner.java:574-584)는 **AgentType(AgentTypeRegistry) 기준만** 본다. allowedTools 가 null(=GENERAL)이면 필터 미적용 → 전역 노출 전부 통과.
- **AGENT_CALL config(워크플로우 스텝 정의)의 도구 목록은 어디서도 안 읽는다.** 즉 워크플로우가 "이 에이전트는 Read/parse_document/pdf_* 만" 처럼 도구를 좁힐 방법이 현재 없다.

## 요구 (CR 범위)

1. **AGENT_CALL config 에 도구 필터 필드 추가** — 예 `tools`(또는 `allowed_tools`)/`exclude_tools`/`read_only`.
   `AgentCallStepExecutor.buildRequest` 가 이를 읽어 `ToolFilterContext` 로 변환 → `SubagentRequest` 로 전파.
2. **SubagentRunner 가 AGENT_CALL 필터와 AgentType 필터를 병합** — 둘 다 있으면 교집합(더 좁은 쪽). 한쪽만 있으면 그것 적용. 둘 다 없으면 현행(전역만).
3. **CLI 경로 일관** — `getToolDefs(filter)` 결과가 곧 CLI `--allowedTools`(ClaudeCliRunnerClient:247) 로 가므로,
   워크플로우 필터가 CLI 노출에도 자동 반영(별도 배선 불필요, CR-104 불변식 활용).

## 동기 (왜 필요한가 — CR-117 에서 드러난 실제 문제)

- CLI 어댑터(`cli-runner-bidding-001`) 경로에서 CLI 가 `builtin_file_read` 를 호출 → allowedTools 에 없어 "No such tool available: builtin_file_read" 실패 → Read 폴백(중복·재시도 노이즈).
- builtin_*(grep/glob/safe_edit 등 8개)이 전역 노출에 남아 CLI 를 헷갈리게 함(builtin 시리즈 추론).
- **전역에서 builtin_* 를 빼는 단순안은 다른 워크플로우/SDK agent 경로에 영향**. 사용자 지적대로 **워크플로우별 필터**가 정답 — extract_facts 는 필요한 도구만 노출하면 builtin_* 혼란이 그 워크플로우 한정으로 사라지고 전역/타 워크플로우 무영향.

## CR-117 과의 경계 (별개)

- **CR-117**: 32MB 빈응답 자식 감지/재시도(은폐) + 32MB 회피(근본). 이번 세션에 구현·배포. 32MB 회피는 "에러 기반 더 잘게 재시도"로 착지(FOREACH 정밀 분할은 과잉이라 철회).
- **CR-118(본 CR)**: AGENT_CALL 워크플로우별 도구 필터 배선. builtin_* CLI 노이즈를 전역 변경 없이 워크플로우 단위로 정리. 32MB 와 무관(노이즈는 Read 폴백으로 동작은 함).

## 부품 존재 (배선만 누락)

- `ToolFilterContext`(이름 allow/exclude + readOnly/permission/capability) — 완성품.
- `ToolRegistry.getToolDefs(ToolFilterContext)` — filter 적용 로직 완성(ToolRegistry.java:91-140).
- `SubagentRequest`/`ChatRequest.toolFilter` 전파 경로 — CR-093 에서 AgentType 용으로 이미 배선됨.
- **막힌 곳**: AgentCallStepExecutor 가 config→ToolFilterContext 변환을 안 함 + SubagentRunner 가 config 필터와 AgentType 필터 병합 안 함.

## 미해결 / 설계 시 결정 필요

- config 필드명 컨벤션(`tools` vs `allowed_tools`) + exclude 지원 여부.
- AgentType 필터와의 병합 규칙(교집합 vs config 우선).
- 멀티 에이전트(`agents[]`) 경로도 각 에이전트별 필터 받을지.

## 발단

세션 시작 메시지 (사용자 원문):

> parse_document를 써야 하는 이유: PDF/문서 첨부는 바이너리라 grep/read로 못 본다. URL→다운로드→텍스트추출(OCR 폴백 포함)을 해주는 게 parse_document다. 이게 없으면 AGENT가 첨부 본문을 못 읽고 빈칸을 환각으로 채운다.
>
> 빼는 대신 개발할 Tool: parse_document를 정식 ToolRegistry 등록 Tool(ParseDocumentTool.java, @Component implements EnhancedToolExecutor)로 만든다. 입력=url(또는 작업장 파일경로), 동작=다운로드+텍스트추출+OCR폴백(기존 PdfTextExtractor/MCPRagClient.parseDocument 재사용), 출력=텍스트를 작업장 .txt로 FileWrite. 그러면 AGENT_CALL/TOOL_CALL이 실제로 쥘 수 있는 도구가 된다.
>
> pdf reader가 필요하다고 하네요 tool형태로

## 토론 진행 — 사용자 핵심 발언 (원본)

### 1. 네이밍 지적

> 그런데 네이밍이 ParseDocumentTool이면 기존 txt, xlxs, docx등등 다른 문서는 어떻게 하나요?

→ 사이드카 `parse_document`가 PDF/DOCX/PPTX/XLSX/CSV/HTML/TXT/MD 8종 지원. 네이밍 그대로 유효.

### 2. 기존 도구 존재 의심

> 그런데 기존에는 문서 분석툴이 없었다는건가요?

→ 1차 답변에서 "사이드카 parse_document 하나만 있었다"고 답함 (부정확).

### 3. 기존 도구 존재 시점 지적

> parse_document --> 여기에만 있었다고요? 저건 어제/엊그제 개발한 사이드카라.. 그렇다는 얘긴 없었다는 얘긴데 기존엔 그럴리가?

→ git log 실측 결과 **Apache Tika 3.1.0 기반 `TikaDocumentParser`가 BE에 이미 존재** ([backend/platform-core/src/main/java/com/platform/rag/TikaDocumentParser.java](../../backend/platform-core/src/main/java/com/platform/rag/TikaDocumentParser.java)). 단 RAG 인제스션(`IngestionPipeline`) 내부 의존성일 뿐 ToolRegistry 미등록. 1차 답변 정정.

### 4. 용도 구분 확정

> 음... 헷갈려서 그러는데 기존에는 Tika인가 이걸로되어있었다 이걸..그냥 말그대로 Rag등을 위해 문서 올리면 그 파싱용이지 llm자율주행 툴은 아니다?

→ 정확. Tika 사용처는 `IngestionPipeline` 단 1곳. AGENT가 쥐는 Tool은 0개.

### 5. 통합 그림 직관

> 아... 이해 완전 이해함.. 자그럼 어떻게 가는게 젤 좋을까요? 딱 생각해도.. 통합된 하나가되어야할거 같은데 그러면.. Tool로서 사용하면서 밑단에는 라이브러리 형태가 되던 해야하겠네요?

→ 사용자 정공 직관. `DocumentParser` 인터페이스가 이미 있어서 Tool/라이브러리 2계층 구조 가능.

### 6. 외부 라이브러리 공통화 직관

> 아니 내말은,. docx, pdf, xlxs등 실제 파서.는 공통이지않냐

→ 정확. 우리 코드에는 포맷별 분기 없음. Tika는 `tika.parseToString(input)` 한 줄, 사이드카는 `_TYPE_MAP` 매핑만. 진짜 파싱은 Apache Tika / unstructured / PDFBox / POI 외부 라이브러리가 함.

### 7. OCR 위치 의심

> ocr_image는 tika에 없어서 별도 로 만든거죠?

→ 부정확한 전제. Apache Tika에 `TesseractOCRParser`가 정식 포함되어 있음. 우리는 `tika-core`만 의존해서 활용 못 하는 상태. CR-092는 사이드카 인프라 반쪽(`pytesseract` import 0건, `read_pdf(ocr_enabled)` 파라미터 미사용) 을 메꾸는 방향으로 진행됐고, BE Tika OCR 옵션은 검토에서 빠짐.

### 8. 핵심 지적

> 그럼 제생각엔 실측을 안하고 ocr이 없다고해놓고 만든것 같습니다. 완전 고질병입니다.

→ origins CR-092 원본 재확인 결과:

- 단 BE Tika OCR 활용 가능성 비교는 origins/T3-15 어디에도 없음
- 부분 실측 후 대안 비교 없이 단정 → CLAUDE.md "범위 추정 금지" 룰 위반에 해당

### 9. 정리 시도

> 1) Tika로 Low레벨 문서 파서는 공통으로 간다?? 오케이인가요?
> 2) LLM Tool로 쓸지, Rag등 정형화된 기능으로 사용하지는 Wrapping 한다.
> 3) 기존에 실수로 만든 ocr_image 등은 헷갈리니 삭제한다?

→ 3가지 모두 정공. 단 3번은 단순 삭제 ≠ 가능 (사이드카 `ocr_image_bytes` + `ocr_pdf_bytes` + Dockerfile 바이너리 + V65 마이그레이션 등 5계층 의존).

### 10. 개념 재확인

> 저 툴들은 라이브러리인가요?

→ "Tool"이라는 단어가 3계층에서 다른 뜻으로 사용됨. AGENT가 쥐는 진짜 Tool은 `OcrImageTool.java` 하나뿐. 나머지(`MCPRagClient.ocrImage`, 사이드카 `@mcp.tool ocr_image`, Python `ocr_image_bytes`)는 호출 체인의 부속.

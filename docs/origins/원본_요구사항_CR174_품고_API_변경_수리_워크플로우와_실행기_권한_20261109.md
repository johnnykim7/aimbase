## 할 것

1. 웹훅 입력 형식을 정해 `[계약]` 으로 컨타에게 보낸다. 피호출자인 Aimbase 가 주인이다. 3PLGW 가 넘길 것은 변경 종류, 표본 위치, 레포와 커밋, 계약 버전, 회신 주소다.
2. 수리 워크플로우를 정의한다.
   - Claude Code 단계: HYBRID 로 bash 와 git 을 쓴다. bp-3plgw 레포를 작업 폴더에 받고, 개인정보 제거 표본과 마지막 정상 표본을 놓고 어긋난 자리를 찾는다. 이름만 바뀐 경우는 새 계약 버전 제안, 구조나 화면이 바뀐 경우는 코드 수정과 단위 시험, 표본 재생 시험 통과까지. 결과는 계약 제안 또는 PR 이다.
   - 검증 단계: 3PLGW 의 제안 검증 API 를 부른다(계약은 컨타에게서 받는다).
   - 승인 대기: HUMAN_INPUT 을 BO2 화면의 승인이 풀 수 있어야 한다. 바깥에서 승인을 넣는 API 가 있는지 보고 없으면 만든다. 시한은 설정값.
   - 반영 단계: 승인되면 3PLGW 에 계약 활성화를 요청하거나 PR 머지를 진행한다. 거절이나 시한 초과는 3PLGW 에 결과만 돌려준다.
3. 실행기 권한: bp-3plgw 레포 읽기, 가지 밀어 올리기, PR 생성(gh). 운영 DB 쓰기 권한은 주지 않는다. 비밀값은 서버의 env 파일에만 둔다.
4. 같은 변경에 수리는 한 번이다. 실패하면 사람 처리로 넘기고 반복하지 않는다. 계정 로테이션과 한도 소진 때의 동작을 확인한다.
5. 개발기에서 끝까지 돌릴 수 있게 한다. 59 에 Aimbase 개발기가 있는지 먼저 보고, 없으면 어떻게 시험할지 `[승인요청]`.

## 4. T1 요약 설계 초안 (컨타 scratchpad 설계전_품고API변경자동대응_20261109/T1_요약설계.md)

# 품고 API 변경 자동 대응 T1 요약 설계 (초안)

작성 2026-11-09. 설계 주인 bp-3plgw. 확정 전 초안이라 레포에 두지 않는다.

## 1. 목표

품고가 예고 없이 화면이나 내부 API 를 바꿔도 주문 수집과 송장 수집이 오래 멈추지 않게 한다.
변경을 수집 당일 안에 잡고, 사람 손 없이 고쳐 시험하고, 사람 승인 한 번으로 운영에 반영한다.

## 2. 지금 상태 (2026-11-09 실측)

- 수집기는 품고 VISE 화면을 브라우저로 조작한다. 화면 요소 56개가 코드에 박혀 있다. 글자 하나 바뀌어 전량 실패한 전례가 있다(입고요청서 placeholder, CR-257).
- 주문·송장은 품고 응답 JSON 을 3PLGW 가 필드 이름 스무 개쯤으로 풀어 쓴다(ViseOrderJsonFlattener 외). 이름이 바뀌면 값이 빈 채로 들어가고, 일부는 예외로 멈춘다.
- 장애 알림은 수집이 아예 실패했을 때만 메일로 나간다(notifier, CR-3PLGW-021). 값이 빈 채로 들어오는 조용한 변경은 잡지 못한다.
- 운영 서버 chaws 에 수집기, 3PLGW, Aimbase 실행기(계정 work01·02·03)가 같이 떠 있다.
- bp-notification 에 문자 발송(/api/v1/messages/sms)과 앱 푸시 발송(FCM, 기기 토큰 등록)이 있다. BO2 앱에 푸시 수신 등록이 있다(features/push).

## 3. 흐름

```

            구조·화면 바뀜: 코드 수정, 단위 시험, 표본 재생 시험 통과까지. PR 생성

[5 반영]  승인: 계약 활성화(다음 틱부터) 또는 PR 머지 뒤 운영 배포
            거절·시한 초과: 사람 처리로 남기고 수집은 멈춘 채 주기 알림
```

## 4. 구성 요소와 레포

### bp-3plgw (주인)

- 계약(contract): 원천별로 필드 경로 목록, 상태 코드 값 집합, 필수 칸(주문번호·송장번호·바코드 등), 화면 요소(선택자·placeholder·탭 라벨). 버전을 매겨 DB 에 둔다. 1판은 지금 코드에서 뽑는다.
- 감지: 응답 키 집합과 상태값을 계약과 대조한다. 새 키, 사라진 키, 새 상태값은 「형식 변경」. 필수 칸 빈 비율이 기준(설정값)을 넘으면 「값 이상」. 화면 요소를 못 찾으면 「화면 변경」(DOM 덤프 보관). 수집기가 계약을 틱 시작 때 받아 간다(수집 간격 설정을 받는 길과 같다).
- 표본 보관: 어긋난 응답과 마지막 정상 응답을 개인정보 제거본으로 보관한다(json-ingest 의 거름 목록 재사용).
- 수리 요청: Aimbase 웹훅 호출. 변경 지문으로 중복 호출을 막는다.
- 승인 API: 제안 계약 목록, 승인, 거절, 이전 버전 되돌리기.
- 재생 시험: 보관 표본으로 flattener 와 수집기 source 를 돌려 보는 시험 도구. 자동 수리와 사람 검토가 같이 쓴다.
- 매핑 설정화: flattener 의 필드 이름과 수집기 선택자를 계약에서 읽게 바꾼다. 코드에 남는 것은 계약을 읽는 틀뿐이다.

### aimbase

- 수리 워크플로우: webhook 트리거, Claude Code 단계(HYBRID, bash 와 git), 검증 요청 단계(3PLGW API), HUMAN_INPUT 승인 대기, 반영 단계.
- 실행기 권한: bp-3plgw 레포 읽기와 가지 밀어 올리기, PR 생성. 운영 DB 쓰기 권한은 주지 않는다(제안만 하고 활성화는 3PLGW 가 승인 뒤에 한다).
- 작업 폴더: /data/workspace 아래 3PLGW 체크아웃.

### bp-notification

- 변경 없음. 앱 푸시와 문자 발송을 쓴다.

### bp-backoffice2

- 품고 전용 메뉴에 「연동 수리 승인」 화면: 감지 내역, 제안 내용(바뀐 필드 전후, 표본 채움률, PR 링크), 승인·거절·되돌리기. 앱과 웹이 같은 화면이다. 앱은 푸시를 누르면 이 화면이 바로 열린다.
- 알림 수신자 지정: 보충 알림처럼 사람마다 고른다.

### bp-infra

- PR 머지 뒤 3PLGW 와 수집기가 운영에 자동 배포되는지 확인하고, 없으면 붙인다.

## 5. 설정값 (코드에 박지 않는다)

필수 칸 빈 비율 기준, 승인 시한, 재알림 주기, 수신자, 중복 호출 쿨다운, 수리 시도 상한.

## 실측으로 확정한 현상 (2026-06-18)

run a614183f, extract_facts(AGENT_CALL) 스텝:
- worker가 `[CLI-STDIN] writing user line: textLen=31544` 전송 후 **`[CLI-INIT]` 한 번도 못 찍고 정확히 600초 침묵 → "turn timeout after 600s" → shutdown → 즉시 재spawn 무한 반복**.

- claude 프로세스 9개 잔존(2개는 9시간 좀비). timeout shutdown 로그는 찍히나 프로세스 안 죽음 = 좀비 누적.

## 근본 원인 (미완전 확정 — 유력 가설)

worker 경로 vs 직접 경로의 유일한 미검증 차이 = **여러 worker가 같은 컨테이너에서 동시 생존(좀비 누적)**. 메모리 project_opportunity_timeout_env_pollution 결론(좀비 누적이 새 CLI 첫토큰 생성 방해)과 일치하나 메커니즘은 미확정. **간헐 1%는 근본 차단 못 할 수 있음을 전제로, "걸렸을 때 자력 복구" 장치가 본 CR의 목표.**

## 현재 cancel 한계 (실측)

- 진입점: `POST /api/v1/workflows/runs/{runId}/cancel` (WorkflowController.java:150) — 소비앱이 이미 사용.
- WorkflowEngine.cancelRun: pending_approval=즉시 cancelled, **running=requestCancel 표식만 → 백그라운드 DAG/cyclic 루프가 스텝 경계(WorkflowEngine.java:630/1033)에서만 isCancelRequested 검사**.
- **스텝 안에서 hang worker(600s)를 기다리며 막혀 있으면 표식 확인 기회가 없어 cancel 즉효 안 됨** (이번 케이스).
- worker kill 부품은 존재(ClaudeCliWorkerPool.shutdownForRun:257, SubagentRunner future.cancel(true):210)하나 cancel 신호가 이 경로로 전파 안 됨.

## 요구 (CR 범위)

1. **강제 취소(force) — 기존 cancel API 강화**: 협조적 표식이 안 먹는 hang 상황에서, 해당 run의 CLI worker를 즉시 kill + run terminal(cancelled) 처리. **소비앱이 쓰는 같은 엔드포인트**에 force 경로 추가(별도 엔드포인트 신설 금지). 협조적→실패시 force 승격 or 파라미터.
2. **재실행**: cancelled/failed run을 같은 입력으로 다시 돌리기 (FE 버튼 + 소비앱 연동 가능 API).
3. (선택) **hang 자동 손절**: worker가 N초간 CLI-INIT/토큰 0이면 600s 안 기다리고 자동 kill+재시도.

우선순위: 1 → 2 → 3.

### 근본 원인 (소스 실측 3지점)

1. **빈 응답 = 가짜 성공** — `SubagentResult` (record):
   - `status=COMPLETED, output="" 또는 null, exitCode=0` 이면 `isSuccess()` 가 `true` 반환 (SubagentResult.java:49 `return status == COMPLETED && exitCode == 0`).
   - output 비어 있어도 성공으로 통과.

2. **AgentCallStepExecutor 가 빈 output 미검사** — `executeSingleAgent` (AgentCallStepExecutor.java:83-86):
   ```java
   if (result.status() == FAILED || result.status() == TIMEOUT) {
       throw new RuntimeException("AGENT_CALL failed: " + reason);
   }
   return toResultMap(result, startMs);   // ← COMPLETED + 빈 output 도 그대로 정상 반환
   ```
   FAILED/TIMEOUT 만 예외 승격. COMPLETED 면 output 이 비어도 검사 없이 성공.

3. **FOREACH 자식은 executeWithRetry 를 우회** — `ForeachStepExecutor.runOne` (ForeachStepExecutor.java:251):
   ```java
   Map<String, Object> r = bodyExecutor.execute(withItemId(bodyStep, index), itemCtx);
   ```
   bodyExecutor.execute() 직접 호출 → WorkflowEngine.executeWithRetry(retryMaxAttempts) 가 적용되는 건 **컨테이너 step(extract_facts)뿐**, 자식 12개 각각은 retry 없음.
   - 자식이 예외를 던져도 on_item_error=fail 이면 부모 step 전체가 FAILED → 부모 재시도 시 **12개 전체 재실행**(이미 성공한 11개 낭비).
   - on_item_error=continue 면 그 자식만 빈 결과로 건너뜀(현재 동작과 유사, 재시도 없음).

### 부품은 이미 존재 (배선만 누락)
- 재시도+CLI `--resume` 이어하기: `SubagentRunner` 가 `request.resumeSessionId()` 지정 시 childSessionId 재사용 → Pool 의 살아있는 Worker 재사용 + `--resume` (SubagentRunner.java:122-126). 현재 단일 AGENT_CALL timeout retry(CR-106)에서만 enableResume=true. FOREACH 자식 경로는 enableResume 미지정.
- WorkflowEngine.executeWithRetry(WorkflowEngine.java:975) — retryMaxAttempts 만큼 재시도 루프. 자식엔 미적용.

- **CR-116**: worker hang(STDIN 후 CLI-INIT 못 찍고 600s 침묵) → **강제 취소 + run 재실행**. run/worker 레벨 자력 복구. (미착수)
- **CR-117(본 CR)**: 자식 turn 이 **정상 종료했으나 응답 텍스트가 비어 있는 것**을 실패로 인지 → **자식 단위 재시도/이어하기**. step 레벨. hang(무응답 600s)과 빈 응답(도구는 끝났는데 텍스트 0)은 다른 현상.
- 두 CR 은 보완 관계: CR-116=run 멈춤 복구, CR-117=자식 빈 결과 복구.

## 요구 (CR 범위)

1. **빈 응답 감지** — AGENT_CALL 결과가 status=COMPLETED 이어도 output(+structuredData) 이 비어 있으면 실패로 판정. 단, "도구만 쓰고 끝내는 게 의도된 에이전트"와 구분 필요(정책/설정).
2. **자식 단위 재시도** — FOREACH 자식(또는 단일 AGENT_CALL)이 빈 응답이면 그 자식만 CLI `--resume` 으로 이어하기 재시도. 부모 step 전체 12개 재실행 금지.
3. **재시도 상한 + 최종 처리** — N회 재시도 후에도 빈 응답이면 그 자식을 FAILED 로 확정(빈 결과를 후속 스텝에 빈 값으로 흘리지 않음 — CR-111 "B 값유실" 차단).
4. (FE) 자식 running 상태에 "모델 응답 대기 중…" / "도구 실행 중…" 문구 + 빈 응답 확정 자식 경고 배지.

우선순위: 1 → 2 → 3 → 4.

## 미해결 / 설계 시 결정 필요

- **"빈 응답 = 실패" 판정 기준**: output 길이 0 만? structuredData 도 비어야? extract_facts 는 fact 텍스트를 내야 하므로 빈 응답=실패가 맞으나, 도구 결과만으로 끝나는 에이전트 타입이 있으면 오탐. → AGENT_CALL config 에 `require_text_output`(기본 true) 플래그 제안.
- **빈 응답이 hang 인지 정상 종료인지**: 실측상 도구는 끝났는데 그 뒤 turn 이 텍스트 0 으로 종료. CLI stream-json 에서 텍스트 델타 없이 result 만 온 경우(메모리 CR-112 is_error 둔갑과 인접) 의심 — 설계 시 Worker 레벨에서 "텍스트 0 + 도구 후 종료"를 어떻게 받는지 추가 실측 필요.
- **재시도 멱등 키**: FOREACH 자식 step_id 는 `extract_facts.body[3]` — CR-106 의 resumeSessionId 결정적 키 생성에 이 step_id 를 태울 수 있는지 확인 필요.

## [후속 실측 2026-06-27 — 진범 확정 + 근본 해결책 추가]

위 §"미해결 / 빈 응답이 hang 인지 정상 종료인지" 빈칸을 운영 로그+로컬 CLI 재현으로 풀었다. **결론: 빈 응답은 hang/지연이 아니라 API 32MB 한계 초과를 CLI 가 `is_error:true(subtype=success)` 로 둔갑한 것.**

### 진범 (운영 agent 로그 직접)
- run **39ccf645** body[3] = `As_built__B949__1.pdf` **169p · 18.8MB**(스캔 도면).
- CLI 본체 Read 가 한 turn 에 `pages=1-20/21-40/41-60/61-80/81-100` **5청크 = 100p** 연달아 적재(101-169 미시도). 100p 이미지 누적이 Anthropic **단일요청 32MB 한계** 초과.
- 로그: `[CLI-RESULT] is_error=true (subtype=success, latency=96184ms): ...대용량 PDF...20페이지씩 분할...Request too large (max 32MB). Try with a smaller file.`
- **개별 Read(20p≈3.6MB)는 32MB 안전. 한 turn 5번 누적이 초과의 진짜 메커니즘.**

### 왜 100p 를 한 turn 에 발사했나 (인과 확정)
- **로컬 claude CLI 직접 재현(청킹 지시 0)**: 180p PDF 를 "읽고 요약해" 만 주면 CLI 가 **스스로** 1-20 → 21-40 읽고 **40p 에서 "충분합니다" 하고 멈춰 정상 응답**(62초, is_error=false). 32MB 근처도 안 감. → **CLI 자율은 적정선에서 멈춘다.**
- 그런데 우리 extract_facts 프롬프트가 *"마지막 페이지까지 20p 씩 나눠 한 번씩, **거부됐다고 건너뛰지 말 것**"* 으로 **완주를 강제** → CLI 자율 정지를 깨고 100p 강제 적재 → 32MB.
- **인과**: CLI 가 40p 에서 멈추면 뒷부분(41p~) **누락→환각** 위험. 그걸 막으려 "완주하라" 지시 넣음 → 이번엔 100p 누적 32MB 로 **통째 빈 응답**(전부 잃음). 부분 누락 고치려다 전체 상실.

### 본질적 딜레마 (한 에이전트로는 해결 불가)
| 방식 | 응답 | 완주(환각 방지) |
|------|------|----------------|
| CLI 자율(40p 멈춤) | ✅ | ❌ 뒷부분 누락=환각 |
| "완주하라" 강제 | ❌ 32MB 통째 실패 | (시도했으나 실패) |
| **페이지 청크를 자식으로 분할** | ✅ | ✅ 전부 봄 |

한 turn/한 에이전트는 32MB 안에 169p 를 못 담는다(물리 한계). **유일 출구 = 169p 를 여러 자식이 분담 완주.**

### 근본 해결책 (사용자 결정: aimbase 플랫폼화, 소비앱 영역 아님)
**완주가 목표(응답 유무 아님) — 169p 전부 본 위에서 나온 fact 만 환각 없음.**

- **(B) FOREACH 자동 페이지 분할 [근본·필수]** — FOREACH 가 파일 1개를 받으면 aimbase 가 `pdf_page_count`+페이지별 렌더 용량 추정 → **목표 청크 용량(예: 자식당 ~15MB = 32MB 절반)에 맞춰 페이지 범위 동적 산출** → 청크당 자식 1개, 각자 "이 범위만 완주" → 자식 결과를 **파일 단위로 병합**(verify 스텝이 "파일별 fact" 로 받게). 작은/텍스트 파일은 자식 1개(현행 유지).
  - 분할 기준 = **페이지 수 고정(X) → 용량 기준(O)**. 도면은 페이지당 무게 제각각이라 "40p 고정"도 더 무거운 도면에서 또 터짐.
- **(A) 도구 레벨 누적 가드 [안전벨트]** — `PdfVisionResolver`/dispatcher 가 한 run·한 turn 페이지 이미지 누적 바이트 추적, 32MB 근접 시 강제 중단("여기까지, 다음 turn"). (B) 로 쪼개도 초대형 도면 재발 대비 최후 방어선. 비용 작음(누적 카운터 1곳).
- **(A)만으론 부족**: 한 자식이 40p 에서 멈춰 여전히 환각. **(B) 가 필수, (A) 는 병행.**

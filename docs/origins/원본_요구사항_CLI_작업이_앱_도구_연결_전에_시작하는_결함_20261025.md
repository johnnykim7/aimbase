## 3. 요청자가 짚은 원인(확인 요청)

CLI 가 MCP 연결을 기다리지 않고(non-blocking) 첫 턴을 시작한다. 모델이 첫 턴에 앱 도구를 찾을 때 aimbase-server 가 아직 pending 이면 지연 도구를 불러올 수 없고, 모델은 그 자리에서 포기하는 설명문을 낸다. 연결이 먼저 끝나느냐에 따라 성공과 실패가 갈린다.

CLI 바이너리에서 본 것(동작은 미확인):
- `MCP_CONNECTION_NONBLOCKING` 환경변수가 있다. 값이 거짓이면 non-blocking 을 끈다: `o=yl(process.env.MCP_CONNECTION_NONBLOCKING)?!1:ct(process.env.MCP_CONNECTION_NONBLOCKING)||(e.nonBlocking??!1)`
- mcp-config 서버 항목에 `alwaysLoad` 를 보고 서버를 나눠 다루는 코드가 있다
- `MCP_CONNECT_TIMEOUT_MS`, `MCP_TIMEOUT` 도 있다

`ClaudeCliCommandBuilder` 주석대로 이 환경의 MCP 도구는 전부 지연 로딩이고 ToolSearch 로 불러와야 한다. ToolSearch 를 봉인하지 않은 것은 맞다. 문제는 불러올 때 서버가 아직 붙지 않았다는 것이다.

Aimbase CR-146(앱 재기동 뒤 /mcp 가 옛 실행기를 부르는 결함)과는 다르다. 그것은 호출이 실패하는 것이고, 이것은 호출 전에 연결이 안 된 것이다. 앱 재기동과 상관없이 10:13 KST, 10:16 KST 처럼 재기동 없는 때도 났다.

## 4. 요구

1. AIMBASE 모드 CLI 작업은 aimbase-server 가 connected 가 된 뒤에 첫 메시지를 보낸다. 방법은 Aimbase 가 고른다(환경변수, mcp-config 설정, 워커가 연결 상태를 확인하고 보내기 등). 정해 둔 시간 안에 연결되지 않으면 그 단계를 실패로 끝낸다
2. 단계가 필요한 MCP 서버 없이 끝났으면 COMPLETED 로 돌려주지 않는다. 지금은 exit_code 0, COMPLETED 와 설명문이 나가서 소비앱은 목차 0건만 보고 원인을 모른다. 1번만으로 막히는지, 2번도 필요한지는 Aimbase 가 판단한다
3. 반영 대상은 AWS 우진 전용 Aimbase 의 agent(필요하면 api) 컨테이너. 지금 이미지를 롤백용 태그로 남긴다. 남의 미완성 작업이 운영에 섞이지 않게 한다. 운영 반영은 사용자 승인
4. 옛 서버(59.8.160.12) 반영은 따로 승인요청

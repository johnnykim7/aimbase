## 🎯 발번할 CR 2건

### CR-065 | SubWorkflow 자식 run 분리 생성

**출처**: `docs/T3-9_CR-058_ChatWidget_설계서.md § 9-1` (line 779~783)

**현재 상태 (우회)**:
- `SubWorkflowStepExecutor`가 서브워크플로우를 **인라인 실행**
- 자식 run이 `workflow_runs`에 별도 레코드로 저장되지 않음
- UI 자식 표시는 `workflow.step` SSE 이벤트 payload의 `sub_workflow_id`로만 대체
- DB 스키마(`parent_run_id` 컬럼)는 이미 적용되어 있어 승격 가능

**원안 (요구)**:
- `WorkflowRunEntity`를 자식용으로 별도 생성
- `parent_run_id` + `parent_step_id` 설정하여 실존 트리로 저장

**해결의 핵심 난점**:
- 자식 run을 별도 레코드로 만들려면 `SubWorkflowStepExecutor`가 `WorkflowEngine.doExecuteAsync()` 경로를 **재진입**해야 함
- 현재 구조에서 executor 레이어에서 엔진 재호출은 **순환 의존** 유발
- → 별도 리팩토링 필요 (의존 구조 재설계)

**해결 후 확보되는 기능**:
- 자식 run 전용 `stepResults` 기록
- 자식 run 개별 재시도
- 위젯 트리 UI에서 자식 단위 제어 가능

**영향 모듈**:
- `workflow/step/SubWorkflowStepExecutor.java` (핵심 수정)
- `workflow/WorkflowEngine.java` (doExecuteAsync 진입점 정리)
- `domain/WorkflowRunEntity.java` (parent_run_id 이미 존재 — 활용만)
- `api/WorkflowController.java` (자식 run 조회/재시도 API 신설 검토)
- 기존 SSE 이벤트 호환성 유지 필요 (위젯이 이미 소비 중)

**영향도**: Medium (리팩토링 + 회귀 위험 있음)

**권장 Phase**:
- Phase 0: 현 구조 의존 그래프 분석 + 리팩토링 전략 결정
- Phase 1: `WorkflowEngine` doExecuteAsync 재진입 가능 구조로 분리
- Phase 2: `SubWorkflowStepExecutor`에서 자식 `WorkflowRunEntity` 생성
- Phase 3: 자식 run API (조회/재시도)
- Phase 4: 위젯 UI에 재시도 버튼 (별도 FE 작업, CR-058 위젯 SDK 업데이트)
- Phase 5: 회귀 테스트 (기존 SSE 이벤트 포맷 유지 검증)

**착수 시점 판단 기준**:
- 위젯 트리 UI에서 "자식 run 재시도"·"개별 조회" 요구가 실사용에서 제기될 때
- 현재는 화면 표시 자체는 되므로 **긴급하지 않음**

**완료 기준**:
- [ ] 자식 run이 `workflow_runs` 별도 레코드로 저장됨
- [ ] `parent_run_id` 기반 트리 조회 API 동작
- [ ] 자식 run 개별 재시도 API 동작
- [ ] 기존 인라인 SSE 이벤트 포맷 호환성 유지 (위젯 기존 코드 무수정 동작)
- [ ] 회귀 테스트 PASS

### CR-066 | Tenant Flyway 자동 재실행

**출처**: `docs/T3-9_CR-058_ChatWidget_설계서.md § 9-4` (line 795~798)

**현재 상태 (우회)**:
- `db/migration/tenant/V*.sql` 신규 마이그레이션이 **기동 시점에 기존 활성 테넌트에 자동 적용되지 않음**
- `LocalDevInitializer`는 `@Profile("local")` 이라 운영 경로 없음
- `TenantOnboardingService`는 **신규 테넌트 등록 시점만** 호출됨
- 배포 가이드 `docs/guides/aimbase-ops-guide.md § 2-5`에 **수동 절차**로 문서화

**문제**:
- 테넌트 수 × 배포 횟수만큼 수동 `flyway migrate` 실행
- "A 테넌트는 V54 적용됐는데 B 테넌트는 누락" 같은 사고 가능
- 테넌트 수 늘어날수록 실수 확률 선형 증가

**해결안 후보** (설계 시 결정 필요):
1. **기동 시점 일괄 migrate**: `ApplicationReadyEvent` 훅에서 `tenants` 테이블 전체 순회 → 각 DB에 `Flyway.migrate()`
   - 장점: 배포 직후 자동 반영
   - 단점: 기동 시간 증가 (테넌트 수에 비례), 실패 시 기동 차단 리스크
2. **Admin API**: `POST /api/v1/platform/tenants/migrate` (Master DB only)
   - 장점: 명시적 제어, 실패 격리
   - 단점: 여전히 수동 트리거 (배포 시 관리자가 호출해야 함)
3. **조합**: 기동 시점 자동 + Admin API 재실행 + 상태 조회 API (`GET /tenants/{id}/migrations`)

**영향 모듈**:
- `config/FlywayMultiTenantConfig.java` (핵심 수정)
- `tenant/TenantOnboardingService.java` (재실행 가능 구조로 정리)
- `api/platform/TenantController.java` (Admin API 신설 시)
- 신규: `tenant/TenantMigrationRunner.java`
- 신규: `domain/master/TenantMigrationLogEntity.java` (감사 로그 — 선택)

**영향도**: Medium
- 기동 시점 적용을 택하면 장애 전파 리스크 (마이그레이션 실패가 기동 실패로)
- Admin API 택하면 안전하지만 여전히 수동

**권장 Phase**:
- Phase 0: 해결안(1/2/3) 중 선택 + 실패 격리 전략 결정 (사용자 승인)
- Phase 1: `TenantMigrationRunner` 구현 (테넌트 목록 순회 + 격리된 Flyway 실행)
- Phase 2: Admin API `POST /api/v1/platform/tenants/migrate` + 감사 로그
- Phase 3: (선택) 기동 시점 자동 훅 — 실패 격리 필수
- Phase 4: 운영 가이드 § 2-5 개정 (수동 → 자동)
- Phase 5: 통합 테스트 (3테넌트 환경에서 V55~V56 일괄 적용 + 1개 의도적 실패 격리)

**착수 시점 판단 기준**:
- 테넌트가 **10개 이상**으로 증가할 때
- 마이그레이션 누락 사고 **1회라도 발생**하면 즉시
- 현재는 수동 절차로 운영 중이라 급하진 않으나 **선제 대응이 합리적**

**완료 기준**:
- [ ] `TenantMigrationRunner`로 활성 테넌트 일괄 migrate 동작
- [ ] Admin API `POST /platform/tenants/migrate` 동작 (호출자 감사 로그 기록)
- [ ] 실패 격리: 1개 테넌트 실패 시 나머지 진행, 결과 요약 반환
- [ ] 운영 가이드 § 2-5 자동 절차로 갱신
- [ ] 회귀 테스트 (신규 테넌트 등록 경로 기존대로 동작)

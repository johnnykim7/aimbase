## 1. 왜

bp-office 는 개발 작업 상태를 받는 창구를 만든다(아래 2절). 받은 상태는 Leo(개발 및 기술 AI 역할) 보고 자료로 저장하고 개발 흐름 화면에 붙인다. 지금 bp-office 와 Aimbase 의 관계는 bp-office 가 워크플로우를 부르고 결과를 조회해 가져가는 한 방향뿐이다.

Aimbase 소스와 가이드를 읽어 본 결과(2026-10-28, 실행하지 않고 소스로 맞춤):

1. 바깥으로 보내는 통로는 있다. 워크플로우 `TOOL_CALL http_request` 단계가 연결의 `config.auth`(`type=API_KEY`, `in=header`, `name=X-Service-Token`, `value_env=<환경변수 이름>`)로 머리값을 싣고 JSON 본문을 보낸다.
2. 보낼 내용이 없다. 개발 작업 항목(작업 번호, 기능 이름, 단계, 상태, 증빙 주소)이 Aimbase 에 표로도 API 로도 없다.
3. 보낼 때가 없다. 워크플로우 실행이 끝나거나 실패할 때 바깥을 부르는 자리(완료 웹훅)가 없고, 단계의 `onFailure` 는 엔진이 분기에 쓰지 않는다(`workflow/WorkflowEngine.java:1317` 은 `onSuccess` 만 본다). 실패한 작업의 상태는 워크플로우 안에서 보고할 수 없다.

그래서 설정만으로는 안 되고 Aimbase 소스 변경이 필요하다.

## 2. bp-office 받는 창구

- `POST {bp-office}/api/v1/inbound/dev-agent-status`
- 머리값 `X-Service-Token`. 값은 bp-office 가 Aimbase 에만 따로 준다. 값은 메시지, 문서, 커밋, 로그에 쓰지 않는다
- 본문 JSON

| 칸 | 필수 | 뜻 |
|---|---|---|
| workItemId | Y | Aimbase 쪽 작업 번호. 100자 이하 |
| featureName | Y | 기능 이름. 300자 이하 |
| stage | Y | 그 작업의 단계 이름(예: 기능, 실증, 배포). 50자 이하. bp-office 는 이름을 해석하지 않고 그대로 보여 준다 |
| status | Y | 그 단계의 상태(예: 진행, 완료, 실패). 50자 이하. 위와 같다 |
| evidenceUrl | N | 증빙 주소. http, https 만. 빈 글은 없음으로 본다 |
| reportedAt | Y | 상태가 바뀐 시각. 오프셋이 붙은 ISO-8601 |

- 같은 `workItemId` 와 `reportedAt`(UTC 로 맞춘 값)은 한 번만 처리한다. 다시 보내면 200 에 `duplicate: true` 로 답한다. 4xx 로 돌려주지 않으니 재시도가 실패로 끝나지 않는다.
- 모양이 틀리면 400(오류 코드 8026)이고 bp-office 가 그 본문을 격리해 남긴다. 다시 보내도 같은 결과다.
- 받은 상태는 bp-office 개발 흐름의 단계를 바꾸지 않는다. 사람이 증빙을 붙이고 단계를 옮긴다.

## 3. 바라는 것

방식(표, API, 엔진 구조)은 Aimbase 가 정한다.

| 순번 | 무엇 | 지킬 것 |
|---|---|---|
| 1 | 개발 작업 상태의 원천. 작업 번호, 기능 이름, 단계, 상태, 증빙 주소, 바뀐 시각을 Aimbase 가 가진다 | 아래 4절 ①. 원천을 Aimbase 에 두지 않는 쪽이면 이 요청 전체가 달라지니 먼저 회신한다 |
| 2 | 상태가 바뀔 때 등록된 주소로 보내는 자리. 진행, 완료, 실패를 모두 보낸다 | 머리값 값은 환경변수 참조로 둔다. 본문은 2절 모양으로 짤 수 있어야 한다. `reportedAt` 은 상태가 바뀐 시각이다. 다시 보낼 때 새 시각을 만들면 bp-office 가 중복을 못 거른다 |
| 3 | 실패해도 2 가 돈다 | 지금은 단계가 실패하면 뒤 단계가 돌지 않아 실패 상태를 못 보낸다(`onFailure` 미사용) |
| 4 | `http_request` 가 가리는 머리값에 연결 `auth.name` 으로 정한 이름을 더한다 | 지금 `X-Service-Token` 이 `auditPayload` 에 평문으로 들어간다(`HttpRequestTool.java:49, 260`) |
| 5 | 개발기에서 bp-office 개발기 창구로 한 번 보내 본다 | bp-office 토큰은 bp-office 가 따로 전한다. 회신에 보낸 시각과 workItemId 만 적는다 |

## 4. 정할 것

1. ① Aimbase 에 개발 작업 항목과 상태 변경 알림을 만든다(권장). 사용자 결정 「기존 개발 에이전트 = Aimbase」 를 그대로 따른다
2. ② 개발 작업을 실제로 돌리는 다른 도구가 bp-office 창구를 직접 부른다(잃는 것: 사용자 결정을 다시 받아야 하고 Aimbase 실행 기록이 남지 않는다)

## 5. 참고(bp-office 가 요청하지 않는 것)

조사 중 본 것이다. 고칠지는 Aimbase 가 정한다.

- 관리 MCP 설명문은 `webhook`, `schedule` 트리거를 안내하지만 엔진이 읽지 않는다(`AimbaseAdminMcpConfig.java:67`).
- `docs/guides/aimbase-api-guide.md:747` 의 「4xx/5xx 도 CONDITION 분기」 는 워크플로우 안에서 소스와 다르다. `http_request` 는 200 ~ 399 만 성공으로 본다.

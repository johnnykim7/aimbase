# CR-142 원본 요구사항 — RAG 사이드카 테넌트 DB 라우팅

## 발생 맥락
- 2026-08-20. 지식소스 업로드 파일이 사이드카에서 파싱되지 않는 문제를 추적하던 중 파생.
- 외부(또는 협업자) 전달 사항 2건으로 접수:
  1. `.env` 의 `DB_NAME` 대소문자 오타 (`aimbase_axopm_companya` → `aimbase_axopm_companyA`)
  2. (구조) 사이드카가 단일 `DB_NAME` 고정 — 테넌트별 라우팅 없음
- 1번은 **본 CR 범위 밖**. 즉시 조치 완료(아래 "선행 조치" 참조). 본 CR 은 2번만 다룬다.

## 전달받은 원문
> **1. .env의 DB_NAME 대소문자 오타**
> `DB_NAME=aimbase_axopm_companya` → `aimbase_axopm_companyA`
> BE는 tenantId 대소문자를 보존해 DB를 생성하는데 .env만 소문자입니다.
>
> **2. (구조) 사이드카가 단일 DB_NAME 고정**
> `python-sidecar/src/rag_pipeline/config.py:10`. 테넌트별 라우팅이 없어, 다른 테넌트가 파일 RAG를
> 쓰면 임베딩이 axopm DB로 섞입니다. 지금은 axopm만 써서 드러나지 않은 상태입니다.

### DB_NAME 대소문자 (당일 조치)
- 전달 내용 사실 확인됨. **다만 "오타" 수준이 아니라 운영에서 살아있는 장애였다.**

  `FATAL: database "aimbase_axopm_companya" does not exist`.

## 핵심 판단

### 전달 내용 중 정정 1건
> "다른 테넌트가 파일 RAG를 쓰면 임베딩이 **axopm DB로 섞입니다**"

정확히는 **`.env` 가 가리키는 딱 한 DB** 로 간다. 조치 전에는 그 DB 가 존재하지 않아
전부 실패했고(오염이 물리적으로 불가능), 대소문자를 고친 지금부터 비로소 진짜로 axopm DB 로
섞이기 시작한다. → **선행 조치가 본 CR 의 위험을 활성화시켰다.** 순서상 본 CR 이 뒤따라야 한다.

### DB 이름은 사이드카가 "조립"하면 안 된다 ★
- 사이드카에서 `"aimbase_" + tenant_id` 로 만들면 **방금 터진 대소문자 버그를 그대로 재생산**한다.
- `shopai-store-a` 처럼 하이픈이 든 ID 도 있어 조립 규칙은 더 위험하다.
- 정본(`tenants.db_name`)은 이미 master DB 에 있으므로 **BE 가 해석한 값을 그대로 전달**한다.
  규칙이 한 곳(BE)에만 존재하게 만드는 것이 이 CR 의 핵심.

## 할 일 (3개)

1. **사이드카 `get_connection()` 을 요청 스코프 인지형으로**
   - `contextvars.ContextVar` 로 현재 요청의 DB명 보관, `get_connection()` 이 이를 우선 사용.
   - **미지정 시 기존 `settings.DB_NAME` 으로 폴백** → stateless 34개 도구 및 기존 호출 경로 무영향(점진 이행).
   - DB 접촉 도구 진입부에서 `tenant_db` 인자를 받아 ContextVar 에 set / 종료 시 reset.

2. **BE `MCPRagClient` 가 테넌트 DB 좌표 주입**
   - `TenantContext.getTenantId()` → `tenants.db_name` 해석값을 도구 인자 `tenant_db` 로 전달.
   - 대상: `ingest_file`/`ingest_document`/검색·캐시·템플릿 계열(DB 접촉 도구).

3. **사이드카 화이트리스트 가드**
   - 넘어온 DB명을 허용 목록/정규식으로 검증. 임의 문자열로 임의 DB 접속 차단.
   - 미검증 통과 시 신뢰경계가 BE→사이드카 인자로 넓어짐.

## 검토했지만 뺀 대안
- **테넌트별 사이드카 컨테이너 분리** — 격리는 완벽하나 테넌트 7개 = 컨테이너 7개,
  BGE-M3 모델 메모리가 배수로 증가. 비현실적.
- **사이드카가 master DB 를 직접 조회해 스스로 해석** — 사이드카에 master 접근권을 부여하게 되어
  신뢰경계가 넓어짐. BE 가 이미 아는 값을 재조회할 이유 없음.

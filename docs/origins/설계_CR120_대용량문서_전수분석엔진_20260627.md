> **이 문서는 설계 origin이다.** 요구사항 origin은 `원본_요구사항_CR120_대용량PDF_청크분할_API병렬_완주_20260627.md` 참조.
> 2026-06-27 설계 확정(ChatGPT 협업 논의 포함) — plan 파일(`~/.claude/plans/jaunty-fluttering-pixel.md`)에서 origin으로 보존.

## Context (왜 만드는가)

운영 `extract_facts` 워크플로우가 대용량 PDF(예: 81p/33.8MB, 169p)에서 멈춘다. 진범은 **32MB = Anthropic API 요청당 물리 한계** — Claude CLI/Code/claude.ai/GPT 누구도 한 컨텍스트에 다 못 넣는다(실측 확정). 우리 extract_facts는 "모든 fact 빠짐없이"를 요구해 모델이 20p씩 누적해 읽다 32MB를 친다.

기존 대화형 AI는 이 문제를 **회피**한다(RAG로 일부만 검색, 전수 안 함). 그러나 공고문·계약서 분석은 **파일이 아무리 커도 전수 완독**이 필요하다. CR-117/119가 "쪼개서 합치기" 방향은 맞췄으나 방식(추정 분할 + 청크마다 CLI spawn)이 틀려 실패했다.

**CR-120 = 32MB를 애초에 안 치게**, 자율주행(에이전트) **바깥**에서 결정론적으로 문서를 청크 분해 → 청크마다 독립 처리(전수) → 계층 Reduce → 누락 검증하는 **범용 엔진**. FACT 추출은 이 엔진을 쓰는 **소비앱(분석 동작)** 중 하나일 뿐.

### 합의된 5대 원칙
1. **분해는 자율주행이 하면 안 된다** — 결정론적 전처리(우리 코드)로 청크화.
2. **청크가 작으면 실행 백엔드 무관** — AGENT_CALL/LLM_CALL/CLI/API 다 됨. CLI 2중 자율주행도 작은 청크는 안 죽음.
3. **Reduce도 재귀** — 청크 결과 단순 concat 불가(그것도 한도 침). 한도 안쪽 묶음씩 정리 → 넘치면 재귀(계층 트리).
4. **분석 동작 = 소비앱** — 엔진은 유형(추출/요약/검증) 모름. 동작이 map/reduce instruction 제공. 프롬프트는 DB(소스에 박기 금지, CR-036 정책).
5. **즉석 전수형 RAG** — 일반 RAG(top-k 검색)와 달리 모든 청크 강제 등록·완주 + 상태관리로 누락 통제.

### ★ 본질: 3-x 분석 유형은 무한 확장 (이 설계의 중심)

대용량 문서를 **1) 읽고 2) 분석**하는 행위는 공통이고, 갈리는 건 **3) 무엇을 만드느냐(3-x)**다. 3-x는 현재 보이는 것만 해도:

| 유형 | 동작 | 예 | reference 필요? |
|---|---|---|---|
| 추출(extract) | 정해진 항목을 있는 그대로 뽑음 | fact 추출, 금액/일정/제출서류 | ✗ |
| 요약(summarize) | 내용 압축 | 공고문 개요 | ✗ |
| **검증·대조(verify)** | 기준과 대조해 틀린/빠진 곳 찾음 | 계약 리스크, 누락 조항 탐지 | **✓ (기준 입력 필수)** |
| 생성(generate) | 문서 기반 새 산출물 | 질문 생성, 제안서 초안 | ✗ |
| 분류(classify) | 부분을 카테고리 태깅 | 조항 유형 분류 | ✗ |
| ... (3-6, 3-7 ...) | 새 목적이 생길 때마다 추가 | translate 등 | 동작별 |

**핵심**: 유형은 5개든 50개든 정해진 수가 없다. **엔진은 유형을 모르고, 유형이 늘어나도 엔진 코드는 안 바뀐다.**
- 새 유형 추가 = `DocumentAnalysis` 구현 클래스 1개(코드 추가 OK) + DB 프롬프트 row 2개(프롬프트는 **소스에 박지 않고 DB**, CR-036) + (선택) UI 드롭다운 1개.
- 엔진/레지스트리/인터페이스는 **무수정**. → 사실상 무한 확장.
- 유형 중 **검증·대조(verify)만 구조적으로 특수**: "틀렸다"고 하려면 비교 기준이 있어야 함 → `needsReference()=true`로 reference_input을 매 청크에 같이 주입. 나머지 유형은 "문서+instruction"이면 충분.

이 본질을 코드로 구현한 것이 아래 `DocumentAnalysis` 인터페이스 + `AnalysisActionRegistry`다.

- **스텝 자동등록**: `@Component`+`supports()` → `WorkflowEngine.java:86` 생성자가 `List<StepExecutor>`→Map 자동 등록. WorkflowEngine **무수정**.

- **텍스트/이미지 판별 + 크기판정 + NEEDS_SPLIT**: `PdfVisionResolver.resolve(...)` 이미 구현 — 재사용. 멀티모달 변환은 `PdfVisionResolver.PageImage` 재사용.
- **프롬프트 DB**: `PromptTemplateService.getTemplateOrFallback(key, fallback)` + `renderTemplate(tpl, Map)` `{{var}}`. 키 패턴 `workflow.split.*` → `largeinput.{action}.{map|reduce}`. 테이블 `prompt_templates`(V46/V55 scope cascade).
- **JSONB 엔티티**: `@Type(JsonBinaryType.class) @Column(columnDefinition="jsonb")` (WorkflowRunEventEntity 패턴).
- **레지스트리**: `AdapterRegistry` 패턴(생성자 `List`→Map by id + `@PostConstruct`) — 정적 빌트인+String키 디스패치라 분석 동작에 적합.
- **LLM 호출**: `ConnectionAdapterFactory`/`ModelRouter`→`LLMAdapter` (프로바이더 중립). `LlmCallStepExecutor.callLlm` 패턴.

## 실행 흐름 (LargeInputStepExecutor.execute)

```
1. config 해석(context.resolveMap) + Policy.resolve(step>wf>system)
   - needsReference 동작인데 reference_input 없으면 throw
   - AGENT_CALL/CLI + auto → force로 정규화
2. 소스 로딩: source_file → AttachmentService.readBytes → LargeInputSource
              input(텍스트) → 단일 텍스트 소스 래핑
3. LargeInputJobEntity 저장 (status=DECOMPOSING)
4. 분해: LargeInputDecomposerService.decompose(source, mode) → List<LargeInputChunk>
   - mode=off 또는 작은 입력 → 청크 1개 (분해 생략)
   - job.chunks JSONB 저장, total_chunks
5. status=PROCESSING — 동적 FOREACH 합성 후 ForeachStepExecutor 위임:
   - items = chunks
   - body.type = LLM_CALL (또는 agent_call)
   - body.config = action.buildMapInstruction(params) 렌더 + {{chunk}} 주입 + output_schema→response_schema
   - 이미지형 청크: pdfToImages(pages=range) → PageImage 멀티모달 블록 주입
   - 병렬(max_parallel) + item_retry_max + action.validateChunkResult 위반시 재시도→FAILED
   - chunk_results JSONB 증분 저장, completed/failed 카운터
6. status=REDUCING — HierarchicalReduceService.reduce(성공결과, action.buildReduceInstruction)
   - 한도 안쪽 묶음씩 LLM 정리 → 넘치면 재귀, reduce_tree JSONB 기록
7. status=VERIFYING — CoverageVerifier.verify(job) → coverage_report
   - full_coverage 미충족 + require_full_coverage → step FAILED(throw) + report를 error에
8. status=COMPLETED — 결과 Map:
   { output:"", structured_data: reduced, coverage_report, total_chunks, completed, failed, job_id }
```

## 청크 경계 계산 (분해기 핵심)

### 텍스트형 vs 이미지형 판별
```
sample = PdfTextExtractor.extract(bytes)          // 32KB 절단 OK (판정용)
charsPerPage = sample.text().length() / max(1, sample.pages())
type = charsPerPage >= TEXT_PER_PAGE_THRESHOLD(예 200자/p) ? TEXT : IMAGE
```
MVP는 전체 평균 단일 type. 혼합 PDF 페이지별 type은 확장 자리.

### 이미지형 경계 (실측 역산, 추정 금지)
```
totalPages = pdfPageCount(base64)
샘플 = pdfToImages(base64, "1-3", dpi, 3) → avgBase64PerPage = Σ base64 / 렌더수
budget = 24MB (base64 기준, 설정 chunk_budget_bytes)
pagesPerChunk = clamp(floor(budget / avgBase64PerPage), 1, maxPagesPerRead)
페이지 경계 슬라이스 → 각 chunk = {pageStart, pageEnd, IMAGE, estBytes}
작으면(totalPages<=maxPagesPerRead && 누적<=budget) → 청크 1개
```
CR-117의 5배 빗나감은 1장 추정 탓 → **첫 3장 샘플 평균 역산**으로 해소.

### 텍스트형 경계
```
fullText = MCPRagClient.parseDocument(base64,"pdf")   // 절단 없는 경로 (PdfTextExtractor 32KB 우회)
charBudget = chunk_budget_chars(예 40,000자)
페이지 경계 유지하며 누적 char가 budget 넘기 직전 분리. page_range 메타 보관.
```

## 검증 (CoverageVerifier)

| 검증 | 강제력 | 방식 |
|---|---|---|
| full_coverage | 결정론적 강제 | completed==total && 모든 chunk ok. 미충족+require → step FAILED |
| 빈응답 | 검증→재시도→정직표시 | structured_data 없음/빈출력 → require_text_output 재시도 → 끝내 빈응답이면 청크 FAILED |
| output_schema | best-effort | response_schema로 구조화 강제, 파싱 실패 청크 FAILED |
| source_ref | 메타 보존 | page_range 기록 → coverage_report에 처리/누락 페이지 명시 |

coverage_report 예:
```json
{ "total_chunks":12, "completed":11, "failed":1,
  "failed_chunks":[{"index":7,"page_range":"29-32","reason":"empty_response_after_retry"}],
  "coverage_ratio":0.917, "full_coverage":false }
```
누락을 숨기지 않음(CR-119). require_full_coverage=false면 부분결과+report 반환(완료), true면 FAILED.

## 상태관리 — JSONB 1테이블

```sql
CREATE TABLE large_input_jobs (
    id BIGSERIAL PRIMARY KEY,
    job_id UUID NOT NULL UNIQUE,
    run_id UUID NOT NULL,
    step_id VARCHAR(100),
    analysis_action VARCHAR(64),

    status VARCHAR(30) NOT NULL,           -- DECOMPOSING/PROCESSING/REDUCING/VERIFYING/COMPLETED/FAILED
    total_chunks INT, completed INT DEFAULT 0, failed INT DEFAULT 0,
    chunks JSONB, chunk_results JSONB, reduce_tree JSONB, coverage_report JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_lij_run ON large_input_jobs(run_id);
CREATE INDEX idx_lij_status ON large_input_jobs(status);
```

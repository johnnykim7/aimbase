# 테넌트 분당 요청 한도가 플랜과 이어지지 않는 결함 - Aimbase

## 배경

- 2026-11-14 Lexflow 서면 초안 시험 중 운영 Aimbase(59.8.160.12, aimbase.banpoom.co.kr)에서 lexflow 테넌트 요청이 429 로 거절됐다. 응답 머리 `X-RateLimit-Limit: 60`, `Retry-After: 6`.
- 구독 조회 결과 lexflow 테넌트는 `plan=pro`, `api_rpm_limit=60` 이었다. 11:33 사용자 승인으로 `PUT /platform/subscriptions/lexflow {"apiRpmLimit": 300}` 을 했고, Lexflow 연동키 응답 머리가 300 으로 바뀐 것을 봤다.
- 요청 쪽이 본 원인 후보다. 확정은 이 레포가 한다.
  - 테넌트 생성(`TenantOnboardingService.createSubscription`, 172~177행)은 플랜만 넣는다. 한도는 엔티티 기본값 60(`SubscriptionEntity.java:40`)이 된다.
  - 구독 변경 API(`PlatformController.updateSubscription`)도 플랜을 바꿀 때 한도를 건드리지 않는다.
  - 플랜별 한도(free 60, starter 300, pro 1000, enterprise 0)는 `V12__add_api_rpm_limit.sql` 의 주석과 그 시점 한 번의 UPDATE 에만 있다. 코드에는 플랜과 한도를 잇는 곳이 없다.
  - 플랜 이름이 갈린다. 화면(`frontend/src/types/tenant.ts:40`, `Tenants.tsx`, `Subscriptions.tsx`)은 free, standard, enterprise 이고, V12 는 free, starter, pro, enterprise 이며, 운영 lexflow 행은 pro 다.
- 같은 증상의 앞 건: 11-03 chaws `bp_wms` 를 60 에서 600 으로 손으로 올렸고(CR-167 7.8절), 그 값을 화면과 API 로 바꾸게 한 것이 CR-169 다. CR-169 는 값을 바꾸는 길만 냈고, 처음 값이 플랜을 따르지 않는 것은 남았다.

## 영향

- 어떤 플랜으로 만든 테넌트도 분당 60 으로 시작한다. 실행 시작과 상태 조회가 모두 이 수에 들어가므로, 소비앱이 3초마다 조회하면 동시 실행 3건에서 429 가 난다.
- 다른 테넌트도 같은 상태일 수 있다. 요청 쪽은 lexflow 한 행만 봤다.

## 할 일

1. 이 레포 절차대로 설계(CR 문서, 설계서, 시험항목). 플랜과 한도를 어떻게 이을지(플랜별 기본값을 설정으로 두고 생성과 플랜 변경 때 채울지, 한도를 플랜과 무관한 테넌트 값으로 둘지)는 ① 권장과 함께 사용자에게 올린다. 플랜별 값은 코드에 박지 않는다.
2. 플랜 이름을 화면, 마이그레이션, 데이터 사이에서 하나로 맞춘다.
3. 59 와 chaws 의 기존 테넌트 구독을 플랜과 한도로 대조해 보고한다. 값을 고치는 것은 사용자 승인 뒤에 한다. lexflow 는 300 으로 이미 바꿨으니 되돌리지 않는다.
4. 운영 반영은 이 레포 `deploy.sh` 로, 사용자 승인 뒤에 한다.

## 2. 확정된 아키텍처 관점 (이번 논의의 핵심 결론)

### 2-1. aimbase = "AI 이용의 마스터", 모델 소유의 마스터는 아님

사용자 질문: *"플랫폼화로 aimbase가 모든 AI 및 ML, 딥러닝 관련된 마스터가 되느냐"*

결론 — **관장(Govern) O / 소유(Own) X**:

- **관장**: 어떤 모델을 부를지, 정책·감사·비용·라우팅 = aimbase가 쥔다
- **소유 아님**: 학습·라벨링·데이터셋·GPU 스케줄링은 밖(cv-inspection)에 둔다
- 모델이 밖에 있어야 마스터가 성립한다. 다 삼키면 그냥 거대한 단일 시스템.

> **한 줄: aimbase는 AI를 소유하지 않고 관장한다. 모델은 밖에, 통제는 안에.**

### 2-2. 4층 구도

```
① 사람·소비앱  ─── 묻고 시킨다
        ↓
② aimbase      ─── AI 이용의 마스터
                   (창구·정책·감사·비용·모델 라우팅·대화·워크플로우)
        ↓ 부른다
③ 판별 계층    ─── cv-inspection(운영) / cvilite(실험)
                   도메인 판정 규칙 · 학습 · 라벨 · 데이터셋
        ↓ 쓴다
④ 모델 런타임  ─── Qwen-VL · Whisper · RT-DETR
                   GPU · 프로세스 상주 · 서빙
```

**층별 소속 판단 기준**:

| 층 | 기준 |
|---|---|
| ② aimbase | "다른 테넌트(WMS·MALL)도 쓰나?" → 예면 여기 |
| ③ 판별 | "도메인 지식이 필요한가?" → 예면 여기 |
| ④ 런타임 | "GPU·프로세스를 붙들고 있나?" → 예면 여기 |

### 2-3. 워크플로우가 갈래를 정한다

```
입력(사진/영상)
  ├─ 스텝: Qwen-VL 판독   → LLM 커넥션
  ├─ 스텝: RT-DETR 검출   → cv-inspection 호출 (도구/MCP)  ※ 동기 호출구 미존재
  ├─ 스텝: WMS 대조       → DB
  └─ 스텝: 판정·기록      → 워크플로우 로직
```

aimbase 입장에선 셋 다 "부를 수 있는 것". 어느 걸 쓸지는 워크플로우 정의가 정한다 = 개발이 아니라 설정.

### 2-4. cv-inspection의 3중 정체 (모순 아님)

- WMS와 Kafka 직결로 자기 일 함 → **독립 플랫폼**
- aimbase 워크플로우가 호출 → **사이드카**
- Gemini 호출을 aimbase 통해 하게 되면 → **소비앱**

보는 방향에 따라 역할이 다를 뿐. 마스터-관장 구조에서 자연스러움.

## 4. 발번

### CR-136 — OpenAI 호환 어댑터 멀티모달(이미지 블록) 전달 ★선행 필수

**문제**: `OpenAICompatibleAdapter.toMessage()`가 `ContentBlock.Text`만 필터링, 이미지 블록 유실(§3-6).

**범위**:
- `toMessage()`에서 `ContentBlock.Image`를 OpenAI `image_url` 파트로 변환
  (`data:image/<mime>;base64,<data>` — 이번 세션 curl 검증 포맷 그대로)
- OpenAI Java SDK 멀티파트 content 빌더 사용
- 텍스트-only 메시지는 기존 동작 유지(회귀 방지)
- 단위 테스트: 이미지 블록 포함 메시지가 멀티파트로 변환되는지

**영향**: 이 어댑터를 쓰는 모든 커넥션(vLLM/Ollama/LM Studio/DeepSeek/LocalAI). 텍스트 경로 무변경.

**왜 선행인가**: 사진이든 영상 프레임이든 결국 이미지로 들어간다. 어떤 조합이 이기든 공통 전제.

**검증**: 운영 커넥션 등록 후 위젯에서 사진 1장 → Qwen 판독 응답 확인.
(§3-2 rack 이미지로 하면 "라벨은 맞고 개수는 틀림"이 재현되어야 정상 — 이미지가 실제로 전달됐다는 증거)

### CR-137 — 모바일 사진/영상 업로드 + 서버 프레임 추출

> **2026-08-05 개정.** 최초 작성본은 "브라우저에서 프레임 추출 + 위젯 UI"였으나,
> 사용자 결정으로 **서버 추출 + 소비앱 자체 UI**로 변경. 변경 근거는 아래 "설계 결정" 참조.

**범위 구분 — 누가 무엇을 만드는가**:

| 주체 | 담당 |
|---|---|
| 소비앱 | 촬영 버튼·미리보기·결과 화면 (앱마다 화면톤이 다르므로 앱 몫) |
| aimbase | 업로드 수신 · 서버 프레임 추출 · VLM 판독 · 결과 JSON · 얇은 업로드 SDK(UI 없음) |

**설계 결정**:

1. **위젯(채팅) 확장이 아니다.** 목적은 대화가 아니라 "현장에서 찍어 보내는 입력 경로".
   촬영 UI는 `<input type="file" accept="video/*" capture="environment">` 수준이라
   위젯으로 감쌀 알맹이가 없고, 앱 화면에 녹아야 한다.
2. **프레임 추출은 서버(ffmpeg)에서 한다.**
   - 붙일 소비앱이 계속 늘어난다 → 앱마다 재구현되면 안 되는 것을 aimbase가 가진다
   - 브라우저 추출은 앱마다 canvas 코드·코덱 분기를 반복 구현하게 됨
   - 원본 영상이 서버에 남아 재판독·감사 가능 (브라우저 추출은 프레임만 남고 원본 소실)
3. **UI 없는 얇은 SDK만 제공.** `upload(file) → jobId → poll(result)`.
   앱마다 재구현되면 안 되는 것은 UI가 아니라 **업로드 신뢰성**(대용량, 모바일 네트워크 끊김).
4. 네이티브 비디오 입력(Qwen만 지원)은 채택 안 함 — Claude/GPT 이식성 없음(§5 참조).
   프레임 샘플링은 어느 모델로도 갈아끼울 수 있다.

**구현 범위**:
1. 영상 MIME 허용 — `MimeValidator` 매직넘버 확장 (현재 PNG/JPEG/GIF/PDF/WEBP 5종만, §7-1)
2. **업로드 상한 정합** — Spring multipart / 코드 상수 / nginx 3계층 한 값으로 (§7-2 지뢰 동반 해소)
3. **`/data/aimbase` 볼륨 마운트** (§7-3 지뢰 동반 해소)
4. API 컨테이너에 ffmpeg 설치 + Java 프레임 추출 (`-vf fps=`)
   - 기본 6프레임 (cvilite 기준, §3-4), 균등 간격, 프레임 수 조절 가능
5. 영상 job 테이블 + 컨트롤러 — CR-133 `transcribe_jobs` 패턴 복제 (§7-4)
6. 프레임 → **기존 `PAGE_IMAGES` Vision 경로 재사용** (PDF 페이지 분할과 구조 동일, §7-5)
7. 얇은 업로드 SDK (UI 없음)

**기반**: CR-061(파일 업로드/이미지 Vision) 재사용. 영상 MIME·프레임 추출·job이 신규.

**의존**: CR-136 (이미지가 실제로 모델에 전달되어야 의미 있음)

**당초 보류 이유**: cvilite에서 `yolo_vlm` case가 stub 상태 → 먼저 측정하고 결론이 나온 뒤 승격.
→ **2026-08-06 측정 완료. 결론은 승격 안 함.**

#### 측정 결과 [사실·확인함] (2026-08-06, cvilite `yolo_vlm` 구현 후 4회 실행)

`cases/yolo_vlm.py`를 `QwenOnlyCase` 상속으로 구현(모델·프롬프트·temperature·max_tokens 동일,
**검출기 유무만 변수**). yolov8n(COCO 사전학습), conf 0.25, conf 상위 6 crop, 검출 0건 시 원본 폴백.

| 샘플 | case | 지연 | 정확도 |
|---|---|---|---|
| sample1 | qwen_only | 31.3s | 1.0 |
| sample1 | **yolo_vlm** | 40.8s | 1.0 |
| sample2 | qwen_only | 31.8s | 0.5 |
| sample2 | **yolo_vlm** | 20.2s | 0.5 |

- **정확도 이득 0** (양쪽 동일). 지연은 엇갈림(+30% / −36%) → §5 표의 "빠름·높음" 가설 **재현 실패**
- **검출기가 상품을 못 잡는다**: sample1 crop 6장이 **전부 `person`**(커피 상품 0건),
  sample2는 `traffic light` 0.855 / `cell phone` 0.879 등 **확신 있는 오검출**이 상위 crop 점유.
  → sample1 acc=1.0은 사람 몸통만 보고 맞춘 **우연**
- **crop이 판단 근거를 잘라먹는 실패 모드 신규 발생**: sample2에서 포장이 crop 밖으로 밀려
  `packaging_damaged` **true→false 반전**(qwen_only는 맞혔음)

#### 보류 확정 사유

1. **검수는 위치 문제가 아니라 상태 문제** — ROI는 "물체가 어디 있나"를 좁히는 기법인데,
   반품 검수가 보는 것은 "물체 상태가 어떤가"(손상·오염·마모). 좁히면 근거가 사라진다.
2. **카운팅 해법이 아님** — 세기(Count) 실패의 해법은 §3-2가 이미 정했다:
   **나열시키고 코드로 센다**(CR-007 구조화 출력 → `len()`). 검출기를 부를 이유가 아니다.
3. **선결 조건이 aimbase 밖** — COCO 가중치로는 창고 물품이 안 잡힌다. 쓰려면 검출기 파인튜닝이
   선결이고 그건 cv-inspection 영역(§2-1 "모델은 밖에, 통제는 안에"). aimbase CR로 성립 안 함.
4. **"자르면 좋아진다" 자체가 두 방식 모두에서 미실증** — `qwen_agent`(VLM 자율 crop, acc 0.25)에
   이어 `yolo_vlm`(검출기 crop, 이득 0). 자르는 주체를 바꿔도 결과는 같았다.

#### 재검토 트리거 (아래가 운영에서 실제 확인되면 다시 연다)

- 물체가 너무 작아 프레임에서 라벨 판독 자체가 안 됨 (해상도 문제)
- 한 프레임에 물체 수십 개라 나열조차 신뢰 불가
- 지연이 SLA 초과라 crop으로 비전 토큰을 줄여야 함

**현재 셋 다 운영 데이터로 확인된 바 없음** → 확인 안 된 문제에 대한 선제 최적화이므로 착수 안 함.

**혼동 주의 2건**:
- `qwen_agent` 반증(§3-4)의 "VLM 자율 crop"과 다름 — 자르는 주체가 검출기. 단 결과는 양쪽 다 무이득
- **"어떤 프레임을 고를까"(시간축)는 CR-139가 아니라 CR-137** — CR-139는 고른 프레임 안
  "어디를 자를까"(공간축). 축이 다르다

#### 산출물

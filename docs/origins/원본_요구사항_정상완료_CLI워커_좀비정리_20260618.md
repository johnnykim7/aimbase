# 원본 요구사항 — 정상 완료 시 CLI worker 결정적 정리 (CR-114)

## 발화 맥락 (2026-06-18)

CR-109(timeout 시 worker 정리) 후속 운영 추적 중 발견. 운영 agent 컨테이너에 8시간 생존한 좀비 worker(0cb2ae03)의 정체를 추적하다 정상 완료 경로의 미정리 분기를 확정.

## 사용자 진단 (그대로 인용)

> cancelIfTimeout(CR-109)은 timeout/실패 경로에서만 cancel을 보냅니다 (ClaudeCliAdapter:100,121). 정상 완료 경로에는 worker 정리 호출이 없습니다. WorkflowEngine에도 run이 completed로 끝날 때 runner cancel/shutdownForRun을 부르는 훅이 안 보입니다 — cancelRun(사용자 명시 취소)만 있습니다.
>
> 즉:
> - run이 completed로 정상 종료 → agent 컨테이너의 CLI worker는 아무도 안 닫음 → pool에 8시간 생존 (= 0cb2ae03 좀비의 정체)
> - worker는 firstTurnDone + pool에 살아남아 다음 같은 runId 호출을 기다리는데, completed run은 다시 호출될 일이 없음 → 영구 좀비
>
> CR-109가 못 본 경로가 맞습니다. CR-109는 "timeout 시 정리"만 다뤘고, "정상 완료 시 정리"는 범위 밖이었습니다.

## CR-109와의 경계 (사용자 정리)

| 기준 | 판단 |
|------|------|
| CR-109 범위 | 실패/timeout 경로의 worker 미정리 (catch에서 shutdownForRun). 이미 운영 배포·커밋 완료(d76ed57)된 닫힌 CR |
| 이번 누수 경로 | 정상 완료(success) 경로의 worker 미정리 — CR-109가 전혀 손대지 않은 다른 분기 |
| 증상 동일성 | 좀비라는 결과는 같으나 원인 경로가 다름 (timeout vs completed) |
| 수정 위치 | run 종료 시 worker 정리 — CR-109의 어댑터 catch와 다른 레이어 |

별도 CR로 가야 하는 핵심 이유: CR-109는 이미 커밋·배포된 닫힌 CR. 거기에 "정상 완료 정리"를 끼워넣으면 이력이 섞이고, 변경 이력 카드의 "A+C 경로" 정의와 안 맞음. 이번 건은 **"run 생명주기 종료 시 worker 결정적 정리"**라는 별도 주제.

## 사용자 결정

- 별도 CR로 발번 진행 (CR-114)
- 정리 레이어: **SubagentRunner 스텝 단위 정리** (worker pool key=childSessionId를 정확히 아는 유일한 지점)

## 실측으로 확정한 사실 (2026-06-18 소스 직접 확인)

1. **좀비 정체**: worker는 `runId`(=`request.sessionId()`=`childSessionId`) 키로 `ClaudeCliWorkerPool.runs` 맵 등록(ClaudeCliWorkerPool.java:107). pool에서 빠지는 유일한 정상 정리 메서드는 `shutdownForRun(runId)`(ClaudeCliWorkerPool.java:257).
2. **정상 완료 미정리**: `RunnerService.runTurn`은 catch(예외) 경로에서만 `shutdownForRun` 호출(RunnerService.java:114-137). 정상 완료 경로 정리 0건 + TTL/idle timeout 없음 → 영구 좀비.
3. **WorkflowEngine 정리 훅 껍데기**: execute/executePlatform/resume 모두 finally에서 `shutdownCliWorkers(runId)` 호출(WorkflowEngine.java:231)하나 그 메서드는 no-op(WorkflowEngine.java:95-97, CR-071). WorkflowEngine은 RunnerClient 의존성 없음.
4. **runId 불일치**: WorkflowEngine의 runId=workflowRunId vs worker pool key=childSessionId — 다름. 그래서 WorkflowEngine finally에서는 worker key를 모름 → SubagentRunner 레이어 선택.
5. **멀티턴 재사용 없음**: SubagentRunner.executeAgent는 orchestratorEngine.chat() 1회 호출 후 결과 반환(SubagentRunner.java:335). 한 AGENT_CALL=한 chat=한 worker. 재사용은 timeout retry 시 deterministic childSessionId `--resume` 경로뿐(정상완료 정리와 무관) → 정상완료 직후 childSessionId cancel 충돌 없음.
6. **cancel 부품 존재**: `ClaudeCliRunnerClient.cancel(endpoint, runId, runnerApiKey)`(ClaudeCliRunnerClient.java:163), RunnerService.cancel→shutdownForRun(RunnerService.java:76-86), RunnerController POST /v1/cancel(RunnerController.java:140-153). 호출만 추가하면 됨.

# 검사 반복(EVALUATOR_LOOP)에 코드 대조 결과를 더하는 기능 - Aimbase

## 배경

- 운영 59(aimbase.banpoom.co.kr) lexflow 테넌트의 `lexflow-draft` 는 두 단계다. `guide`(TOOL_CALL skill_read, 서면 작성법 파일 하나 읽기) 다음 `final`(EVALUATOR_LOOP, 최대 2회, 작성 LLM 과 검사 LLM, 통과 판정 JSONPATH_MATCH `$.passed`).
- 검사 기준 1은 「사건자료와 작성법에 글자 그대로 없는 법조문은 지적」이다. 2026-11-14 서면 61종 시험에서 검사 LLM 이 자료 밖 조문 3건을 통과시켰다(내용증명 민법 제598조, 침해금지가처분신청서 상표법 제107조, 부당해고 구제신청서 근로기준법 제23조, 제27조).
- 검사 LLM 에게 조문 목록을 먼저 적고 하나씩 출처를 대게 한 시도(2026-11-14 22시)도 실패했다. 목록 798개 가운데 조문은 16개였고, 내용증명은 민법 제387조, 제598조를 목록에서 빠뜨린 채 통과했다. 글자 대조는 LLM 검사로 보장되지 않는다.
- 같은 판정을 코드로 하면 잡힌다. 위 3건은 lexflow 쪽 판정 스크립트(정규식으로 「○○법 제N조」를 뽑고 공백을 지운 사건자료, 작성법 글자에 있는지 대조)가 찾은 것이다.
- 요청 쪽이 본 범위의 Aimbase: EVALUATOR_LOOP 의 통과 판정은 SCORE_THRESHOLD, JSONPATH_MATCH, LLM_JUDGE 뿐이고(`EvaluatorLoopStepExecutor.java` 260~262행), 회차 안에서 코드를 돌릴 자리가 없다. 스킬 스크립트 실행 도구(`SkillRunTool`, skill_run)는 있다. 확정은 이 레포가 한다.

## 요청

- 검사 반복의 회차마다 작성 결과에 코드 대조를 돌려, 찾은 위반을 그 회차 판정에 더한다. 위반이 있으면 그 회차는 통과가 아니고, 위반 내용이 다음 작성에 넘어가는 지적(`loop.feedback`)에 들어간다.
- 대조 코드가 받을 것: 그 회차 작성 결과(구조화 출력), 워크플로우 입력(`input.case`, `input.docType`), 앞 단계 결과(`guide.output`). 대조 코드 자체는 요청 쪽(lexflow)이 스킬로 올린다. 엔진은 부르는 자리와 입출력 규약을 정한다.
- LLM 검사는 그대로 둔다. 판례, 날짜, 금액, 구성 순서 같은 나머지 기준은 계속 LLM 이 본다.
- 회차 기록(`iterations`)에 코드 대조 결과가 남아 무엇을 잡았는지 나중에 볼 수 있어야 한다.
- Lexflow 연동은 그대로다. 단계 id, 단계 이름(「작성법 선택」, 「작성과 대조 검사」), 결과 자리(`stepResults.final.structured_data`), 최대 반복 횟수를 바꾸지 않는다.

## 할 일

1. 이 레포 절차대로 설계(CR 문서, 설계서, 시험항목). 아래는 ① 권장과 함께 사용자에게 올린다.
   - 설정 모양과 순서(코드 대조를 LLM 검사 앞에 둘지 뒤에 둘지, 코드가 위반을 찾으면 그 회차 LLM 검사를 건너뛸지).
   - 대조 코드가 실패하거나 시간을 넘을 때 처리(스텝 실패로 끝낼지, 그 회차는 LLM 판정만 쓸지).
2. 로컬에서 시험한다. 시험용 스크립트로 위반 있음, 위반 없음, 스크립트 실패, 시간 초과를 본다.
3. 운영 반영은 이 레포 `deploy.sh` 로, 사용자 승인 뒤에 한다. 59 의 `lexflow-draft` 운영 워크플로우는 건드리지 않는다(시험은 로컬이나 별도 워크플로우).
4. 끝나면 회신한다. 워크플로우 설정 예시와 대조 스크립트가 지킬 입출력 규약(받는 값, 내는 JSON 모양, 시간 한도, 실행 환경에 있는 언어). lexflow 쪽 스크립트 작성과 `lexflow-draft` 반영은 요청 쪽이 한다.

## 대화 원본 (발췌)

**사용자**: pdf파일을 그냥 넘기는것도 해봤어요? docx는 llm이 툴로 읽으라고 지시가오고?

**Claude**: 둘 다 안 해봤습니다. (…) PDF 쪽은 검증 가치가 있습니다. CR-099에서 검증한 건 "유저 메시지에 실린 document 블록"이 CLI까지 가는 경로였고, 이번 케이스는 **도구 결과(tool result)에 실린 비전 블록**이 서버 MCP → CLI로 돌아가는 경로라서 메커니즘이 다릅니다.

**사용자**: 해봐야죠

**Claude**: (e2e 실행 — 운영 agent 컨테이너, override 로 server MCP env 임시 주입, 어댑터 풀경로)
- ② 자율 도구 선택 PASS — 자연어만으로 CLI 가 `builtin_file_read(as_base64:true)` → `parse_document(content)` 체인 스스로 선택, 마커 TEAL-7781-AUTONOMY 회수 (CLI 세션 jsonl 실측)
- ① PDF content 패스 **FAIL** — `parse_document(content, file_type=pdf)` 응답:
```json
{"mode":"inline_pdf","source":"file:local.pdf","note":"The PDF content has been provided to you as a separate message above. Read it directly; do not call parse_document again for this file."}
```
CLI 답변: "no separate message with the parsed text is visible to me" — 쪽지만 도착하고 PDF 본체는 미도착.

**사용자**: (설명 중 "쪽지만 돌려주고 서버가 끼워넣는다" 부분에 대해) → 여기가 뭔가 이상한데요?

**Claude**: (코드 실측 후 정정)
- 도구는 쪽지+소포를 **둘 다** 돌려줌 — `ParseDocumentTool.buildVisionResult` 가 `ToolResult` 에 `output`(inline_pdf 쪽지) + `newMessages`(PDF base64 document 블록) 동봉 (ParseDocumentTool.java:227-228)
- API 경로: 도구 루프가 ToolResult **객체**를 받아 `ToolCallHandler` 가 `newMessages` 를 user 메시지로 변환·주입 (ToolCallHandler.java:866 `injectedSink.add(UnifiedMessage.ofUserContent(...))`, :972 `toContentBlocks(toolResult.newMessages())`) → 정상
- CLI 경로: `ServerMcpToolDispatcher.dispatch` 가 `tool.execute(args)` **String 반환 인터페이스**를 타고 그 문자열만 `McpSchema.CallToolResult` 로 직렬화 (ServerMcpToolDispatcher.java:96-116) → `newMessages` 를 실을 칸이 없어 **dispatch 단계에서 소포 유실**
- 정확한 원인: 루프 주체 문제가 아니라 **dispatcher 결과 직렬화가 newMessages 를 버리는 전송 채널 문제**
- MCP tool result 는 표준상 멀티모달 content 블록을 실을 수 있으므로, dispatcher 가 newMessages → MCP content 블록 변환하는 정공안이 유력. 단 claude CLI 가 tool result 안의 document/image 블록을 실제로 읽는지 사전 실측 필요

**사용자**: cr 95에게 수정하라고하면되나요/

**Claude**: CR-095 수정이 아니라 신규 CR 발번이 맞습니다. CR-095(비전 메커니즘)는 자기 범위(API 도구 루프)에서 정상이고, 수정 대상은 `ServerMcpToolDispatcher`(CR-072 산출물) — "CR-095 메커니즘 × CR-072 채널"의 통합 갭이며 CR-100 시나리오가 처음 드러낸 것. 스코프:
1. dispatcher 가 `newMessages` 를 MCP 멀티모달 content 블록으로 변환 (정공) — claude CLI 의 tool result 멀티모달 수용 여부 사전 실측 필수
2. 실측 결과 CLI 가 못 받으면 MCP 채널 한정 폴백: PDF 도 사이드카 텍스트추출(+스캔본 OCR, CR-092 자산) 로 글자 반환

## 요구사항 요약

- **문제**: CLI(서버 MCP) 경로에서 `parse_document` 의 PDF 비전 결과(`ToolResult.newMessages` 의 document/image 블록)가 CLI 에 전달되지 않아 로컬 PC PDF 분석 불가. 비-PDF(DOCX 등)는 정상.
- **원인(실측)**: `ServerMcpToolDispatcher` 가 String execute 결과만 직렬화 — `newMessages` 운반 채널 부재.
- **해소 방향**: ① dispatcher 의 MCP 멀티모달 content 변환(정공, CLI 수용 실측 선행) ② 불가 시 MCP 채널 한정 사이드카 텍스트/OCR 폴백.
- **검증 기준**: CR-100 어댑터 풀경로 e2e 의 PDF 케이스(마커 PDF → 마커 verbatim 회수) PASS.

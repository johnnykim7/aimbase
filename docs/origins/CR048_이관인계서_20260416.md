## 1. 배경

OpenClaude 전수 대조 결과, Aimbase가 **컨텍스트·토큰 효율** 영역에서 3가지 최적화가 누락됨. 특히 MCP 도구 수백 개 보유 테넌트에서 매 턴 수천 토큰이 낭비되는 상황.

## 2. 코드 검증 결과

### 2-1. Deferred Tool 스키마 런타임 주입 (#2) — 🔴 MISSING
- **현재**:
  - `ToolSearchTool.java:56-69` — `toolRegistry.searchTools()` 결과를 **텍스트로 반환만** 함
  - 다음 LLM 호출에 검색된 도구의 **스키마가 자동 주입되지 않음**
  - ContextAssemblyEngine은 항상 전체 tool defs를 태움
- **OpenClaude**: `tools/ToolSearchTool/ToolSearchTool.ts` — 검색 결과가 dynamicTool로 등록되어 **다음 턴부터 스키마 포함**
- **영향**: MCP 도구 100개 테넌트 기준 매 턴 5000~10000 토큰 낭비 (영구 cache prefix는 도움되지만 부분적)

### 2-2. Tool Result Storage 치환 (#6) — 🟡 PARTIAL
- **현재**: `ToolCallHandler.java:287-309` — 임계치(81920B) 초과 시 `compactorRegistry.compact()` 로 **인라인 truncate만**
- **ToolResultCompactorRegistry.java:34-53** — tool별 지능적 요약은 함
- **결정적 갭**: 원본을 외부 저장소에 보관하지 않음. 요약본만 남기므로 **복구 불가**
- **OpenClaude**: `toolResultStorage` 에 원본 저장, 체인에는 `[ref: result-id, summary]` stub 주입. 필요시 ReadToolResult로 복구 가능

### 2-3. Adaptive Thinking 동적 조정 (#7) — 🟡 PARTIAL
- **현재**: `AnthropicAdapter.java:130-160` — DISABLED/ENABLED/ADAPTIVE 3-mode enum
- **ADAPTIVE는 budget=0** (자동), ENABLED는 고정 config 값
- **요청별 동적 재계산 없음** — 태스크 복잡도·이전 실패·도구 호출 수 기반 조정 로직 부재
- **OpenClaude**: `adjustThinkingBudget()` 런타임 호출, `query.ts` 에서 턴 상황 반영

## 3. 구현 범위

### PRD-A: Deferred Tool 스키마 런타임 주입
1. **SessionToolRegistry 신설**
   - sessionId별 "활성 도구" 목록 관리 (ConcurrentHashMap 또는 Redis)
   - 초기 상태: 기본 도구(Read/Edit/Grep/Bash 등) + ToolSearch만
2. **ToolSearchTool 로직 수정**
   - 검색 결과를 SessionToolRegistry에 add
   - 응답 텍스트에 "이제 다음 도구들이 활성화됨: X, Y, Z" 안내
3. **ContextAssemblyEngine 수정**
   - tool defs 조립 시 SessionToolRegistry 조회
   - 활성화된 도구만 스키마 포함
4. **비활성 도구 처리**
   - 이름+간단 설명만 텍스트로 system prompt에 삽입 (검색 가능하도록)
   - "이 도구를 쓰려면 ToolSearch로 먼저 로드하세요" 힌트
5. **캐시 prefix 불변 유지**
   - 활성 도구 변경 시에도 system prompt 앞부분은 고정, 뒷부분만 변동
   - Anthropic cache_control 규칙 준수

### PRD-B: Tool Result Storage 치환
1. **DB 테이블 신설** (또는 Redis)
   ```sql
   CREATE TABLE tool_result_storage (
     result_id VARCHAR(64) PRIMARY KEY,
     session_id VARCHAR(100) NOT NULL,
     tool_name VARCHAR(100),
     full_content TEXT NOT NULL,
     summary TEXT,
     size_bytes INT,
     created_at TIMESTAMPTZ DEFAULT NOW(),
     expires_at TIMESTAMPTZ
   );
   ```
2. **ToolCallHandler.java:287-309 로직 변경**
   - 임계치 초과 시:
     1. 원본을 tool_result_storage에 저장
     2. 체인에는 `{type: "tool_result_ref", id: "res_abc123", summary: "..."}` stub 주입
3. **ReadToolResult 신규 도구**
   - 모델이 `read_tool_result(result_id)` 호출 시 원본 반환
   - 권한: 본인 세션의 result_id만 접근 가능
4. **만료 정책**: 24시간 TTL (세션 TTL과 일치)
5. **Redis vs Postgres**: 용량 작으면 Redis(빠름), 크면 Postgres(압축 가능)

### PRD-C: Adaptive Thinking 동적 조정
1. **AdaptiveThinkingPolicy 인터페이스**
2. **조정 입력**:
   - 이전 턴에서 tool_use 횟수 (많으면 복잡)
   - 이전 턴에서 에러·재시도 발생 (있으면 복잡)
   - 사용자 질문 길이·복잡도 지표
   - 과거 세션 평균 thinking budget
3. **조정 공식 (초안)**:
   ```
   base_budget = 4000 (default)
   if last_turn_tool_calls >= 3: budget *= 1.5
   if last_turn_had_errors: budget *= 2.0
   if user_question_length > 500: budget *= 1.3
   cap at 32000
   ```
4. **AnthropicAdapter.java:130-160 주입점**
   - `resolveThinkingMode()` 결과가 ADAPTIVE면 policy 호출해 동적 budget 계산
5. **측정**: thinking budget vs 응답 품질 상관관계 로깅 (A/B용)

## 4. 결정 필요 사항

1. **Deferred Tool 기본 활성 세트**: Read/Edit/Grep/Bash/TodoWrite/ToolSearch — 이 6개 맞나?
2. **Tool Result Storage**: Redis vs Postgres — 어느 쪽?
3. **Storage TTL**: 24시간 vs 세션 종료 시 삭제 vs 영구?
4. **Adaptive Thinking 공식**: 제안한 공식 OK? 다른 지표 추가?
5. **비활성 도구 설명 주입 방식**: 이름+설명만 텍스트 vs 아예 언급도 생략?

- **토큰 절감**: 턴당 평균 input token 감소율 (Deferred Tool)

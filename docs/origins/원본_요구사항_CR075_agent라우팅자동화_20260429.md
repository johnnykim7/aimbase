## 발단

위젯 채팅 호출이 401로 실패. 디버깅 중 사용자가 본질을 짚음:

> "그런데 에이전트를 띄울때마다 매번.. 소비앱에게 알려줘야하나요?"

CR-071 설계서에서 `X-Aimbase-Agent-Id` 헤더 의무화 + "자동화는 별도 CR" 로 분리한 결정이 있었으나, 그 별도 CR이 발번 안 된 채 운영 흐름에 부닥침.

---

## 본질 토론 (소크라테스식 대화로 도출)

대화에서 사용자가 짚은 단계:

1. **agent의 본 목적은?**
   - "PC에서 뭔가 작업을 하기 위함"
   - ToS 우회는 부수 효과지 본질이 아님 ("어떻게 하다보니 ToS가 우회된 것")

2. **agent의 작업 대상은?**
   - 그 PC에 있는 산출물 (문서, 코드 등)

3. **작업 지시 도구는?**
   - 위젯, 서버 스케줄러, 다른 PC의 Claude Code(MCP) 등 다양
   - 공통점: 모두 Aimbase를 거침

4. **라우팅 키 후보 — MAC 같은 PC 고유값?**
   - 가장 확실하지만 "그 PC에서만"이라는 전제 — 다른 PC/서버 케이스 못 다룸
   - 사용자: "다른 PC나 서버에서 명령 내릴 비즈니스 모델은 아직 생각하지 않음"
   - 그래도 범용성 위해 다른 키 검토

5. **라우팅 키 결정 — 사용자 ID**
   - 사용자: "사용자 아이디를 라벨로 사용하면?"
   - 이미 위젯 토큰 `user_ref` 클레임에 존재 — 새 식별자 불필요
   - 사용자 자기 PC의 agent → 자기 위젯이 자기 PC와 만남. 자연스러운 1:1

6. **익명 위젯 사용자**
   - 사용자: "로그인 안한 사용자는 어차피 agent 활용 못함. AI 서비스는 CLI가 아닌 API로 사용해야 함"
   - → API 어댑터(`AnthropicAdapter`)로 폴백

7. **한 사용자 다중 PC**
   - 사용자: "단 하나만 사용하도록"
   - 사용자: "agent는 무조건 덮어쓰게 해주세요"
   - → 신규 등록 시 이전 ACTIVE 자동 DEREGISTER

## 트레이드오프

- **헤더 명시 케이스 보존** — 디버깅/특수 라우팅을 위해 헤더 우선 폴백 유지. 운영에서 위젯은 안 보내면 됨.
- **단순 덮어쓰기** — 사용자가 두 PC를 동시에 켜둔 채 둘 다에서 일하는 케이스는 잠깐 마찰 발생. 비즈니스 정책으로 그 케이스가 들어오면 그때 라벨에 PC suffix 추가 등 확장.
- **multi-agent 라우팅(라운드로빈/sticky)** 은 YAGNI — 활성 1개 정책이 본 단계 충분.

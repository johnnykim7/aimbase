## 2. 역할 판단 (합의됨)

**aimbase가 맞다.** 근거:

- 회의녹음 전사는 "긴 입력 → 분할 → 병렬처리 → 병합" 파이프라인으로, CR-120 LARGE_INPUT 이 문서로 이미 푼 구조와 동일하다.
- 전사 뒤에 붙는 작업(요약, 액션아이템 추출, 회의록 포맷팅)이 결국 LLM 작업이라 aimbase 안에 있는 것이 자연스럽다.
- STT 추상화(`SpeechService`)가 이미 존재한다(CR-060).

**경계**: 엔진(whisper 추론)은 aimbase 밖 사이드카. aimbase 는 커넥션 타입 + 워크플로우 스텝 + 정책/과금/테넌트 격리만 담당.

**실시간 스트리밍 STT 는 범위 밖.** 배치 전사만 다룬다.

## 3. 실측 결과 (2026-07-29 수행)

### 3.1 하드웨어 판단

| 대상 | 결과 | 판정 |
|---|---|---|
| 59 운영서버 | Ryzen 7 5800X 16스레드, **GPU 없음**, **load average 17.9(포화)** | ❌ 탈락 |
| 로컬 맥 | **M1 Ultra 20코어 / RAM 64G / 디스크 184G 여유** | ✅ 채택 |

> 59서버는 이미 CPU 포화 상태라 배치 전사를 얹을 여유가 없다.
> (참고: load 17.9 는 메모리에 기록된 "운영서버 침해정황(채굴 프로세스)"과 무관하지 않을 수 있음 — 별도 확인 필요)

### 3.2 백엔드 선택 — MLX 필수

동일 샘플, M1 Ultra, large-v3 기준:

| 샘플 | CPU (faster-whisper) | **MLX (lightning-whisper-mlx)** |
|---|---|---|
| 37초 | 1.9x | 4.2x |
| **10분33초** | **0.51x (20.5분)** | **14.5x (43.7초)** |
| 다중화자 35초 | — | 7.0x |
| 잡음 35초 | — | 9.7x |
| **1시간 회의 환산** | **약 2시간** | **약 4분** |

**핵심 발견 2건:**

1. **faster-whisper 는 Apple Silicon GPU 를 못 쓴다.** 백엔드인 CTranslate2 가 CUDA/CPU 만 지원(`get_supported_compute_types('cpu')` → `{int8, int8_float32, float32}`, `get_cuda_device_count()` → 0). M1 에서도 CPU 로 돈다.
2. **긴 오디오에서 방향이 갈린다.** CPU 는 0.51x 로 실시간보다 느려지고 MLX 는 배치 효율로 14.5x 가 나온다. 짧은 샘플(2배 차이)만 보면 오판한다.

→ **도커 컨테이너는 사실상 불가.** Docker Desktop for Mac 은 GPU 패스스루가 안 돼 MLX 를 못 쓰고, 그러면 0.51x(1시간 회의 = 2시간)가 되어 배치로도 실용성이 없다. **맥 네이티브 실행이 유일한 선택.**

### 3.3 품질

한국어 전사 정확도 양호. 다중 화자·잡음 조건에서도 텍스트 정확. 한국어 발음의 "지피유/씨피유/에이치티티피에스"를 GPU/CPU/HTTPS 로 정확히 복원.

**⚠️ 검증 한계**: 실측은 전부 macOS `say` 합성 음성이다. 실제 회의녹음(자연 발화, 겹침, 원거리 마이크)은 속도·정확도 모두 이보다 나쁠 수 있다. **실제 파일 재검증 필요.**

### 3.4 확인된 기능 한계 — 화자 분리 없음

3명이 말해도 **한 덩어리 텍스트**로 나온다. 화자 라벨이 필요하면 pyannote 등 diarization 을 별도로 붙여야 하며, 추가 모델 + 추가 시간이 든다. 회의록 용도에서 실제로 걸릴 지점.

## 4. 1단계 완료분 (구현 완료, 검증 완료)

### 4.1 산출물 — `transcribe-sidecar/`

| 파일 | 역할 |
|---|---|
| `src/app.py` | FastAPI 사이드카. `POST /transcribe`, `GET /health` |
| `run.sh` | 기동 로직 단일 지점. OS별 껍데기(plist/systemd/Docker)는 이것만 호출 |
| `deploy/com.aimbase.transcribe.plist` | 맥 상주(launchd) 설정. **아직 미설치** |
| `requirements.txt` | 의존성 |
| `.env` | 인증 키 (600, gitignore) |

### 4.2 백엔드 전환 설계

`WHISPER_BACKEND` 환경변수로 전환. 기본 `auto` → Apple Silicon 이면 `mlx`, 그 외 `faster`.
리눅스 이관 시 코드 수정 없이 `faster` 로 떨어진다. **OS별 스크립트 두 벌 유지 부담을 `run.sh` 한 벌로 눌렀다.**

### 4.3 네트워크 — 해결됨

```
59서버 BE ──HTTP──> 110.11.139.2:8291 (공유기) ──> 192.168.0.7:8291 (맥 사이드카)
```

- 맥은 사설 IP(192.168.0.7)지만 공유기 공인 IP(110.11.139.2) 보유
- **ipTIME 공유기에 8291 포트포워딩 추가 완료** (규칙 5번)
- **e2e 검증 성공**: 59서버 → 맥 사이드카 전사 요청 → 결과 반환 (35초 오디오 / 10.4초)

> TURN·리버스 SSH 터널 모두 불필요. 포트포워딩으로 해결됨.

### 4.4 인증 — 완료

- `X-Api-Key` 헤더 검증, `hmac.compare_digest` 상수시간 비교
- **fail-closed**: `TRANSCRIBE_API_KEY` 미설정 시 기동 자체를 거부
- `/health` 는 무인증 (모니터링용, 노출 정보는 모델명 수준)
- 검증: 인터넷 경유 키 없음 → 401, 틀린 키 → 401, 올바른 키 → 200

**API Key**: `transcribe-sidecar/.env` 의 `TRANSCRIBE_API_KEY` 참조 (git 미추적 — 문서에 원문을 남기지 않는다).
커넥션 config 의 `api_key` 와 같은 값이어야 한다.

### 4.5 사이드카 API 스펙

```
POST /transcribe
  Header: X-Api-Key: <key>
  Body(multipart): file=<audio>, language=ko|auto, beam_size=5(선택)
  →  {
       text, language, duration, elapsed, speed_ratio,
       segments: [{start, end, text}, ...]
     }

GET /health   (무인증)
  →  {status, backend, model, device, loaded}
```

## 5. 2단계 범위 (미구현 — 본 CR 의 실제 구현 대상)

### 5.1 기존 STT 배선을 재사용할 수 없는 이유 (실측 근거)

기존 CR-060 배선은 **위젯 마이크 입력(짧은 발화) 전용**이다:

| 제약 | 값 | 위치 | 회의녹음 기준 |
|---|---|---|---|
| 최대 길이 | **60초** | `ChatSttController.java:127` | 1시간 = 60배 초과 |
| HTTP 타임아웃 | **120초** | `WhisperSpeechService.java:59` | 4분 소요 → 초과 |
| Rate limit | 60초 윈도우 | `SttRateLimiter.java:24` | 배치에 부적합 |
| 호출 방식 | 동기 blocking | `SpeechService.transcribe()` | 4분 스레드 점유 |

> 이 값들은 **위젯을 보호하려고 일부러 건 제한**이다. 회의녹음 때문에 60초→3600초로 풀면 위젯 방어가 같이 사라진다. → **경로를 분리한다.**

`SpeechService` 인터페이스 자체는 재사용 가능(구현체 추가만).

### 5.2 필요한 구조

```
[업로드] → POST /api/v1/transcribe-jobs      (즉시 job_id 반환)
              ↓ 비동기 워커
           맥 사이드카 호출 (X-Api-Key, 4분)
              ↓
           transcribe_jobs 테이블 (PENDING→RUNNING→DONE/FAILED)
              ↓
[폴링]   → GET /api/v1/transcribe-jobs/{id}
```

CR-120 의 `large_input_jobs` 와 동일 패턴 — 선례 참고 가능.

### 5.3 작업 항목

1. **`LocalWhisperSpeechService implements SpeechService`** — 사이드카 HTTP 호출. 기존 인터페이스 재사용, 타임아웃만 길게(예: 30분)
2. **`transcribe_jobs` 테이블 + Flyway** (tenant DB 경로)
3. **비동기 job API 2개** — 등록/조회
4. **커넥션 타입에 STT 백엔드 선택** — `openai` / `local-sidecar`. 사이드카 URL·API Key 를 커넥션 config 에 저장
5. **테넌트 격리·감사로깅·비용집계** — BIZ-020 준수

### 5.4 신규 BIZ 후보

- 회의녹음 전사 최대 길이 (예: 4시간)
- 사이드카 호출 타임아웃 (예: 30분)
- 배치 전사 동시 실행 상한

> 최신 BIZ 는 BIZ-110. 신규는 BIZ-111 부터.

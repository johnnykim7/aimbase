# CR-119 원본 요구사항 — 32MB API 거부의 timeout 둔갑 (스트림 경로 CR-112 누락)

**발번일**: 2026-06-27
**발단**: CR-118 e2e(오산 건 opportunity-analysis run 4185860e) 중 발견

## 사용자 발화 (핵심)

> "저런 멈추는 것들이 단지 프롬프트 실수라고 한다면.. 다음 다른 소비앱을 만들 때마다 항상 비슷한 사례가 발생할 거 같은데요"

> "예 발번도 하고 수정도 하고 얼릉얼릉 진행합시다."

## 문제 (실측 확정)

운영 run 4185860e의 extract_facts FOREACH item[3] = `As_built__B949__2.pdf` (35MB, 180p) 가
3회 재시도 모두 실패하고 **빈 응답**으로 끝났는데, extract_facts step 은 `on_item_error=continue` +
`max_failed_ratio` 미설정이라 **그 도면 fact 통째 누락된 채 "완료"로 둔갑** → 다음 스텝 진행.

### 근본 원인 체인 (소스 + 운영 로그 실측)

1. CLI 가 180p 누적 Read → Anthropic API `Request too large (max 32MB)` →
   CLI 가 `is_error:true (subtype=success)` result 이벤트로 둔갑 발행 (CR-112 패턴).
   - 운영 로그 01:09:00: `[CLI-RESULT] is_error=true (subtype=success, latency=110328ms): ...20페이지씩 나눠서 순차적으로 읽겠습니다. Request too large (max 32MB). Try with a smaller file.`
2. **비스트림 경로**(ClaudeCliWorker:594)는 CR-112 로 `is_error=true → 예외 승격(errText 보존)` 처리됨.
3. **그러나 스트림 경로**(ClaudeCliRunnerClient.chatStream → handleStreamEvent:482 result 분기)는
   **is_error 를 안 보고 정상 처리** → result 못 받고 stream 끊김 → ClaudeCliRunnerClient:167 이
   **"Runner stream ended without result event (turn truncated — likely agent async timeout)"** 로
   **새 메시지 생성 → 32MB 정보 소실**.
4. ClaudeCliAdapter:111: `cli_runner_unreachable:UNKNOWN:...turn truncated...timeout`.
5. AgentCallStepExecutor: 메시지에 "timed out" → `isTurnTimeoutFailure=true`,
   `isPayloadTooLargeFailure=false`(too large 단어 없음) → **resume**(같은 35MB 파일 재전송) →
   또 32MB → 무한 반복 → 빈 응답.

추가 발견: ClaudeCliRunnerClient.chatStream 의 stream 루프 catch(Exception)(156) 가
handleStreamEvent 의 의도적 예외까지 삼켜 parse 스킵과 구분 못 함 → is_error 승격을 추가해도 먹힘.

### 왜 "프롬프트 실수"가 아니라 플랫폼 구조 결함인가 (사용자 핵심 지적)

- 32MB 는 Anthropic API 물리 한계. 소비앱은 어댑터의 페이지 base64 누적 방식·32MB 한계를 모름 → **추상화 누수**.
- 어느 소비앱이든 "큰 PDF 읽어 분석" 시키면 동일 함정(누적 32MB → 둔갑 → 무한 resume → 무응답) 재발.
- 플랫폼은 pdf_page_count/누적크기/32MB 한계를 아는 위치 → 막을 수 있는데 모델 자율에 맡겨 실패.
- CR-117 이 만든 "에러 기반 32MB 재시도(fresh+힌트)" 가 **메시지 둔갑(스트림 경로 CR-112 누락) 때문에 안 탔다**.

## 요구

1. **스트림 경로 CR-112 이식**: ClaudeCliRunnerClient.handleStreamEvent result 분기에서
   `is_error=true` 면 errText("Request too large..." 등) 보존해 예외 승격.
   → 상위 isPayloadTooLargeFailure 가 32MB 류로 정확 분류.
2. **stream 루프 try 분리**: parse 예외만 스킵, handleStreamEvent 의도적 승격은 전파.
3. **32MB > timeout 우선**: AgentCallStepExecutor 가 too-large 면 timeout 처럼 보여도 resume 금지(fresh+힌트).
4. (운영/소비앱) `max_failed_ratio` 적용으로 누락 둔갑 차단 — 별도 권고(코드 아님, config).

## 경계

- CR-117 = 32MB 빈응답 에러기반 재시도(설계). CR-119 = 그 에러기반이 **스트림 경로 둔갑으로 안 탔던** 버그 수정.
- CR-118 = 워크플로우별 도구 필터 (무관, 같은 e2e 세션에서 파생).
- 근본 회피(어댑터가 누적 크기 감시해 자동 압축/윈도우 제한)는 더 큰 범위 — 후속 검토.

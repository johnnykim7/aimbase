## 1. 외부 보고 원문 (소비앱 측 진단)

> 종합 결과로 확정됐습니다. Aimbase의 이 리소스들은 테넌트 격리가 안 되어 있습니다 — X-Tenant-Id 헤더는 요구하지만 값과 무관하게 같은 결과를 줍니다:
>
> | 리소스 | bidding_system | default | nonexistent_xyz | 격리 여부 |
> |--------|----------------|---------|-----------------|-----------|
> | mcp-servers | 1개(bidding-agency-mcp) | 동일 1개 | 동일 1개 | 격리 안 됨 (전역) |
> | tools | 86개 | 86개 | — | 전역(내장 도구라 당연) |
> | workflows | requirement/document 2개 | 동일 2개 | — | 격리 안 됨 |
>
> "bidding-system의 MCP 등록이 aimbase에서 bidding-system tenant에 등록된 거죠?"
> → 아니요. MCP 서버 등록(bidding-agency-mcp)은 bidding_system 테넌트에 귀속·격리된 게 아니라, Aimbase 전역에 등록돼 있습니다. 어느 테넌트 헤더로 조회해도 동일하게 보입니다.
>
> 우려점:
> - 다른 테넌트(앱)도 같은 Aimbase 인스턴스에서 이 MCP 서버와 워크플로우를 보고 호출할 수 있습니다.
> - 이건 Aimbase 플랫폼의 멀티테넌시 설계 이슈입니다(mcp-servers/workflows 저장 시 tenant_id로 필터링하지 않는 듯).
>
> 위와 같다고 합니다. 신규 CR 로 보완해주세요

## 2. 실측 검증 (코드 + 운영 DB + 운영 런타임)

CLAUDE.md 최우선 룰("구현·동작 여부 판단 시 소스코드 실측 필수")에 따라 외부 보고를 코드/운영DB/운영런타임으로 직접 검증. **외부 보고의 진단은 반증됨.**

### 2-1. mcp/workflow는 Database-per-Tenant로 물리 격리되어 있음 (외부 진단 반증)

- `MCPServerRepository`는 `com.platform.repository`(master 아님) 패키지 → `TenantRepositoryConfig`가 테넌트 라우팅 DataSource에 바인딩 (master 제외 전 패키지가 `tenantEntityManagerFactory`).
  - `backend/platform-core/src/main/java/com/platform/repository/MCPServerRepository.java:9-13`
  - `backend/platform-core/src/main/java/com/platform/config/TenantRepositoryConfig.java:11-19`
  - `backend/platform-core/src/main/java/com/platform/config/TenantDataSourceConfig.java:33` (주석에 workflows를 "테넌트별 테이블"로 명시)
- 운영 DB(localhost:5432) 실측:
  - `aimbase_master` DB에 `mcp_servers`/`workflows` 테이블 **자체가 없음** → 전역 공유될 물리적 위치가 존재하지 않음.
  - 테넌트별 DB는 **서로 다른 데이터**:
    - `aimbase_bidding_system`: mcp 1개(bidding-agency-mcp), workflow 2개(bid-document-generation / requirement-extraction)
    - `aimbase_flowguard_dev`: mcp 0개, workflow 1개(fg-dsl-generate)
    - `aimbase_axopm_companyA`: mcp 4개, workflow 15개
    - `aimbase_shopai-store-a` / `aimbase_test_tenant`: 둘 다 0개
  - → "어느 테넌트 헤더로 조회해도 동일"은 운영 데이터와 배치. "tenant_id 컬럼 누락으로 전역 공유" 진단도 아키텍처(Database-per-Tenant, BIZ-003)와 배치.

### 2-2. 운영 인증은 켜져 있고, 헤더만으로는 접근 불가 (외부 관찰 재현 불가)

- `application.yml:61` — `security.enabled: ${SECURITY_ENABLED:true}` (기본 true)
- 운영 서버 `.env.prod`에 `SECURITY_ENABLED` 키 **0개** = 미설정 = 기본 true 적용 (SSH 실측).
- 운영 런타임 실측 (http://59.8.160.12:8280):
  - 토큰 없이 `X-Tenant-Id: bidding_system` 헤더만 → **HTTP 401**
  - 헤더 없이 → **HTTP 401**
  - → "X-Tenant-Id 헤더만으로 200 / 어느 테넌트든 동일 결과"는 운영에서 재현 불가.
  - (외부 관찰은 tools 86개 같은 내장 도구 전역 엔드포인트와 혼동했거나, JWT를 함께 보냈을 가능성. 추가 단서 필요.)

### 2-3. 그럼에도 발견된 진짜 약점 — 헤더-토큰 테넌트 불일치 무검증

- `TenantResolver`는 X-Tenant-Id 헤더 문자열을 **무검증으로 신뢰**하여 TenantContext에 설정.
  - `backend/platform-core/src/main/java/com/platform/tenant/TenantResolver.java:134-136`
- `JwtAuthenticationFilter`는 access 토큰의 `tenant_id` claim을 추출하지만, **헤더 값과 대조하지 않음.**
  - `backend/platform-core/src/main/java/com/platform/auth/JwtAuthenticationFilter.java:99` (claim 추출), 헤더 대조 로직 없음.
- 결과: A 테넌트로 인증된 토큰을 가진 사용자가 `X-Tenant-Id: B`를 보내면, 인증은 통과하면서 라우팅은 B 테넌트 DB로 향할 수 있음 (cross-tenant 사칭). 이것이 외부 보고가 가리키려던 진짜 위험의 코드 레벨 형태.
- `MCPController` / `WorkflowController`에는 테넌트 소유권 검증 가드가 없음 (인증 통과 = 라우팅된 테넌트 DB 전체 접근).

## 3. CR 방향 (사용자 결정)

- 사용자 선택: **"헤더 신뢰 경계 강화 CR"** (2026-05-29)
- 외부가 적은 "tenant_id 컬럼 추가"는 **채택하지 않음** — 잘못된 처방(이미 DB-per-Tenant 물리 격리). 
- 핵심 목표: **JWT 토큰의 tenant_id claim과 X-Tenant-Id 헤더 값의 일치를 강제**하여 헤더 단독 신뢰로 인한 cross-tenant 사칭을 차단.

# CR-125 원본 — admin MCP 테넌트 컨텍스트 전역 단일 필드 교차 오염

작성일: 2026-07-22
발견 경위: CR-124(MCP SSE→Streamable HTTP 전환) 작업 중 `McpTenantSessionFilter` 를 수정하다 확인

> **이것은 CR-124 가 만든 결함이 아니다.** CR-124 이전부터 존재하던 설계 문제이며,
> 범위 밖이라 그대로 두고 별도 발번했다.

---

## 1. 문제

`McpTenantSessionFilter` 가 현재 MCP 세션의 테넌트를 **전역 단일 필드**로 들고 있다.

```java
// platform-core/src/main/java/com/platform/mcp/admin/McpTenantSessionFilter.java
/** 현재 MCP 세션의 테넌트. SSE 연결 시 설정. */
private static volatile String currentMcpTenant = null;

public static String getCurrentMcpTenant() {
    return currentMcpTenant;
}
```

동작 흐름:

1. admin MCP 접속 시 URL 쿼리로 테넌트를 받는다 — `?tenant_id=axopm_companyA`
2. 필터가 그 값을 `currentMcpTenant` 에 저장하고 테넌트 DataSource 를 준비한다
3. 이후 도구 호출에서 `AimbaseAdminMcpConfig` 가 `getCurrentMcpTenant()` 로 읽어
   `TenantContext` 에 심는다

**필드가 하나뿐이라 사용자를 구분하지 못한다.**

---

## 2. 왜 위험한가

서로 다른 테넌트가 admin MCP 를 **동시에** 사용하면:

```
t0  사용자 A 접속 (?tenant_id=tenant_A)   → currentMcpTenant = "tenant_A"
t1  사용자 B 접속 (?tenant_id=tenant_B)   → currentMcpTenant = "tenant_B"   ← A 값 덮어씀
t2  사용자 A 가 도구 호출                  → getCurrentMcpTenant() = "tenant_B"
                                          → A 의 요청이 B 의 DB 로 라우팅
```

**Database-per-Tenant 격리(BIZ-003) 위반**이다. 조회면 타 테넌트 데이터 노출,
쓰기면 타 테넌트 DB 오염으로 이어진다.

지금까지 표면화되지 않은 이유는 admin MCP 를 사실상 단일 사용자로만 써왔기 때문이다.
동시 사용이 없으면 덮어쓰기도 없다.

---

## 3. CR-124 에서 이미 처리된 부분 (혼동 방지)

CR-124 에서 같은 파일을 고치면서 **요청 간 누수**는 차단했다:

```java
} finally {
    // Streamable 은 요청마다 스레드가 재사용될 수 있어, 이 필터가 심은 값은
    // 같은 요청 범위에서 되돌린다(누수 방지).
    if (tenantSet) {
        TenantContext.clear();
    }
}
```

**남은 것은 `currentMcpTenant` 필드 자체의 연결 간 덮어쓰기**다. 이건 요청 정리로
해결되지 않는다 — 값이 필드에 남아있는 것이 정상 동작이기 때문이다.

---

## 4. 해결 방향 (안)

### 안 A — MCP 세션 단위 보관 (권장)

Streamable HTTP 는 `Mcp-Session-Id` 헤더로 세션이 식별된다(CR-124 운영 프로브에서
`Mcp-Session-Id: ea9b84ed-...` 확인). 이를 키로 쓴다.

```
static Map<String, String> sessionTenant = new ConcurrentHashMap<>();

initialize 요청   : tenant_id 파라미터 → sessionTenant.put(mcpSessionId, tenantId)
이후 요청         : sessionTenant.get(요청의 Mcp-Session-Id) → TenantContext
세션 종료(DELETE) : sessionTenant.remove(mcpSessionId)
```

- 장점: 동시 사용자 완전 분리. Streamable 의 세션 개념과 정합
- 확인 필요: initialize 응답에서 세션 ID 가 발급되므로 **최초 요청 시점엔 아직 없다**.
  그 요청에서 어떻게 매핑할지(응답 헤더 가로채기 vs 첫 도구 호출 시 지연 바인딩) 설계 필요
- 확인 필요: 세션 종료 누락 시 맵 무한 증식 → TTL 또는 상한 필요

### 안 B — 요청 단위 헤더 결정

쿼리 파라미터 의존을 버리고 매 요청 `X-Tenant-Id` 헤더로 결정한다.

- 장점: 상태 자체가 없어 덮어쓰기 문제가 원천 소멸. 기존 `TenantResolver` 와 일관
- 단점: 클라이언트 설정 변경 필요(`.mcp.json` 의 `headers` 에 추가) — 소비앱 영향
- 참고: CR-086(X-Tenant-Id 신뢰경계 강화)와 함께 검토해야 함

## 6. 검증 방법 (제안)

단위 테스트로 **동시 두 테넌트** 시나리오를 재현한다:

```
세션1(tenant_A) 수립 → 세션2(tenant_B) 수립
→ 세션1 로 도구 호출 → TenantContext 가 tenant_A 여야 한다 (현재는 tenant_B 로 깨짐)
```

CR-124 에서 추가한 `Cr124TenantFilterStreamableTest` 를 확장하는 형태가 자연스럽다.

## 7. 관련

- CR-124 — 본 결함이 발견된 작업. 요청 간 누수 차단은 여기서 완료
- CR-086 — X-Tenant-Id 헤더 신뢰경계 강화(안 B 채택 시 연계)
- BIZ-003 — Database-per-Tenant 격리
- CR-122 — 스케줄러 TenantContext 누락(같은 계열: 테넌트 컨텍스트 전파 결함)

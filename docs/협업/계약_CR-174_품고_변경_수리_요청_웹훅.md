# 계약 · CR-174 품고 변경 수리 요청 웹훅 (bp-3plgw 에서 Aimbase 로)

|---|---|
| 정하는 쪽 | Aimbase CR-174 (피호출자) |
| 부르는 쪽 | bp-3plgw 「품고 API 변경 자동 대응」 수리 요청, 승인 전달 |
| 날짜 | 2026-11-09 |
| 설계 | Aimbase `docs/CR-174_품고_API_변경_수리_워크플로우와_실행기_권한.md` 4절, `docs/T3-2_API_설계.md` 「실행 종료 회신 `_callback`」 |
| 상태 | 초안. 59 반영 전 |

## 1. 부르는 법

- 주소: Aimbase 주소 뒤에 `/api/v1/workflows/poomgo-change-repair/run`. 59 는 Aimbase 개발기 api(`http://59.8.160.12:8280`, Aimbase compose 망 안이면 `http://aimbase-api:8080`), 운영은 chaws 망 `aimbase-apps` 의 `http://aimbase-api:8080`
- 인증: 테넌트 `bp_3plgw` 의 소비앱 키 `X-API-Key: <키>`. `X-Tenant-Id: bp_3plgw` 도 함께 보낸다. 테넌트 판별이 키 검사보다 앞서 돌아 키만으로는 400 `X-Tenant-Id header is required` 로 거절된다(59 실측). 키 값은 Aimbase 설치 때 `secrets/bp-3plgw-api-key` 로 나오고 3PLGW 서버 env 파일에만 둔다
- 본문: JSON. 아래 2절 칸을 평평하게 싣는다(`input` 으로 한 번 더 싸지 않는다)
- 같은 변경(`change_id`)은 한 번만 부른다. Aimbase 는 다시 돌리지 않는다

## 2. 수리 요청 `POST /api/v1/workflows/poomgo-change-repair/run`

```json
{"schema_version": "1",
 "change_id": "ord-20261109-7f3a",
 "change_kind": "FORMAT",
 "source": "ORDER",
 "detected_at": "2026-11-09T05:12:00+09:00",
 "summary": "주문 응답에 새 키 2개, 사라진 키 1개",
 "repo": {"url": "https://github.com/therecommerce-develop/3plgw.git", "base_branch": "dev", "commit": "a1b2c3d"},
 "contract": {"version": 12, "url": "http://59.8.160.12:8187/api/v1/internal/poomgo-repair/contracts/12"},
 "samples": {"broken_url": "http://59.8.160.12:8187/api/v1/internal/poomgo-repair/changes/ord-20261109-7f3a/samples/broken",
             "last_good_url": "http://59.8.160.12:8187/api/v1/internal/poomgo-repair/changes/ord-20261109-7f3a/samples/last-good",
             "dom_dump_url": null},
 "pr_labels": ["deploy-59"],
 "_callback": {"connection_id": "bp-3plgw", "path": "/api/v1/internal/poomgo-repair/changes/ord-20261109-7f3a/result", "result_step": "repair"}}
```

| 칸 | 필수 | 설명 |
|---|---|---|
| `schema_version` | 예 | 이 입력 형식의 판. 지금은 `"1"` |
| `change_id` | 예 | 변경 지문. 3PLGW 가 만든 고유값. 가지 이름 `fix/poomgo-<change_id>` 와 회신 경로에 쓴다. 영문, 숫자, `-`, `_` 만 |
| `change_kind` | 예 | `FORMAT`(형식 변경: 새 키, 사라진 키, 새 상태값), `VALUE`(값 이상: 필수 칸 빈 비율 초과), `SCREEN`(화면 변경: 요소를 못 찾음) |
| `source` | 예 | 원천 이름. 3PLGW 가 정한 글자를 그대로 쓴다(예 `ORDER`, `INVOICE`, `INBOUND_REQUEST`) |
| `detected_at` | 예 | 감지 시각. UTC 오프셋 붙은 ISO-8601 |
| `summary` | 아니오 | 감지기가 쓴 한 줄. 승인 대기 사유에 그대로 실린다 |
| `repo.url` | 예 | https 주소. 실행기는 `GH_TOKEN` 으로 받고 밀어 올린다 |
| `repo.base_branch` | 예 | PR 의 바탕 가지 |
| `repo.commit` | 예 | 감지 시점에 돌던 수집기 커밋. 가지는 여기서 딴다 |
| `contract.version` | 예 | 지금 활성 계약 판 |
| `contract.url` | 예 | 계약 내용(spec: sourceCode, envelope, fields, valueMaps, screen) 조회 주소. 표본과 같이 머리글 `X-Internal-Service-Key`(실행기 env `TPLGW_INTERNAL_KEY`)로 받는다 |
| `samples.broken_url` | 예 | 어긋난 응답(개인정보 제거본) 조회 주소 |
| `samples.last_good_url` | 예 | 마지막 정상 응답(개인정보 제거본) 조회 주소. 그 원천의 첫 감지면 404 를 돌려주고, 실행기는 어긋난 표본과 계약만으로 간다 |
| `samples.dom_dump_url` | 아니오 | 화면 변경 때 DOM 덤프 주소. 없으면 null |
| `samples.broken`, `samples.last_good` | 아니오 | 작은 JSON 이면 본문을 바로 실어도 된다. 둘 다 있으면 본문을 먼저 쓴다. 3PLGW 는 넣지 않는다(3PLGW BIZ-R15) |
| `pr_labels` | 아니오 | PR 라벨. 없으면 `["deploy-59"]`(bp-infra CR-INFRA-008: 이 라벨이 붙은 가지의 BE 와 수집기가 59 에 자동 배포된다) |
| `_callback.connection_id` | 예 | Aimbase 에 등록된 3PLGW HTTP 연결 id. 설치 때 `bp-3plgw` 로 만든다 |
| `_callback.path` | 예 | 결과를 받을 3PLGW 경로. `/` 로 시작. 연결 `baseUrl` 뒤에 붙는다 |
| `_callback.result_step` | 아니오 | 회신 `result` 에 실을 단계. 그 단계의 구조화 출력(structured_data), 없으면 output 글. `repair` 를 권한다 |

응답 200:

```json
{"success": true,
 "data": {"id": "6c1f2b1e-...", "workflowId": "poomgo-change-repair", "status": "running", "startedAt": "2026-11-09T05:12:03.120Z"}}
```

`data.id` 가 run_id 다. 3PLGW 는 수리 요청 줄에 저장해 승인과 조회에 쓴다.

| 응답 | 뜻 |
|---|---|
| 400 `callback_invalid:<칸>` | `_callback` 칸이 틀렸다. run 을 만들지 않았다 |
| 401, 403 | 키가 없거나 다른 테넌트 키다 |
| 404 | 워크플로우가 없다(설치 전) |

## 3. 승인 전달 `POST /api/v1/workflows/runs/{run_id}/approve`

BO2 앱에서 사람이 승인하거나 거절하면 3PLGW 가 넣는다. 인증은 2절과 같다.

```json
{"approved": true, "reason": "검수자 홍길동, 채움률 98%"}
```

| 응답 | 뜻 |
|---|---|
| 200 `data.status = running` | 승인. 반영 단계(계약 활성화 또는 PR 머지)가 이어 돈다 |
| 200 `data.status = failed` | 거절. `data.error.reason = "Human approval rejected"`, `detail` 에 reason |
| 404 | 그 run 이 없다 |
| 409 | 승인 대기 상태가 아니다(이미 풀렸거나 시한이 지났거나 끝났다) |

## 4. 실행 종료 회신 (Aimbase 에서 3PLGW 로)

run 이 어떤 상태로든 끝나면 `_callback.connection_id` 연결의 `baseUrl` 뒤에 `_callback.path` 를 붙여 한 번 POST 한다. 머리글은 Aimbase 의 HTTP 연결 `auth` 가 넣는다(`X-Internal-Service-Key`, 값은 Aimbase api 서버 env `TPLGW_INTERNAL_KEY`).

```json
{"run_id": "6c1f2b1e-...",
 "workflow_id": "poomgo-change-repair",
 "status": "completed",
 "error": null,
 "result": {"result_kind": "CODE", "summary": "...",
            "changed": [{"kind": "FIELD_PATH", "name": "주문 번호", "before": "orderSheet.orderCode", "after": "orderSheet.orderNo", "change": "RENAMED"}],
            "contract_proposal": null,
            "pr": {"number": 57, "url": "https://github.com/therecommerce-develop/3plgw/pull/57", "branch": "fix/poomgo-ord-20261109-7f3a",
                   "title": "fix: 품고 ORDER 변경 대응 (ord-20261109-7f3a)", "repo": "therecommerce-develop/3plgw"},
            "tests": {"unit": "passed", "unit_passed": 41, "unit_total": 41, "replay_fill_rate": 0.98}, "failure_reason": null},
 "completed_at": "2026-11-09T06:02:11.004Z",
 "duration_ms": 3008000}
```

`result` 는 repair 단계의 구조화 출력이고, submit 단계가 3PLGW 「제안 등록」에 보낸 `proposal` 과 같은 것이다. `result_kind` 가 `CONTRACT` 면 `contract_proposal`(계약 spec 모양)이 차고 `pr` 은 null, `CODE` 면 `pr`(`title` 포함)이 차고 `contract_proposal` 은 null, `NONE` 이면 둘 다 null 이고 `failure_reason` 에 이유가 있다.

| `status` | `error.reason` | 뜻 |
|---|---|---|
| `completed` | null | 승인되어 반영 단계까지 끝났다. `result.result_kind` 가 `CONTRACT` 면 계약 활성화를 요청했고, `CODE` 면 PR 을 머지했다 |
| `failed` | `Human approval rejected` | 거절. `detail` 에 거절 사유 |
| `failed` | `approval_timeout` | 승인 시한 초과. `detail` 에 시한 시각 |
| `failed` | 그 밖(단계 실패 메시지) | 수리 실패, 검증 실패(제안 제출 4xx), 계정 한도 소진, 반영 실패. `result` 는 repair 단계가 끝났으면 실린다 |
| `cancelled` | null 또는 중지 사유 | 운영자가 Aimbase 에서 run 을 중지했다 |

3PLGW 가 2xx 가 아니면 Aimbase 가 5초 간격으로 3번까지 다시 보낸다(설정값). 그래도 안 되면 Aimbase 실행 이벤트에 남기고 멈춘다. 같은 run_id 회신이 두 번 올 수 있으니 받는 쪽이 한 번만 처리한다.

## 5. 조회 `GET /api/v1/workflows/runs/{run_id}`

회신이 안 왔을 때 3PLGW 가 당겨 본다. `data.status`(`running`, `pending_approval`, `completed`, `failed`, `cancelled`), `data.stepResults.repair.structured_data`(없으면 `output` 글)가 4절 `result` 와 같은 모양이다.

## 6. Aimbase 가 3PLGW 에서 받을 것 (3PLGW 가 정한다)

| 순번 | 필요한 것 | 쓰는 자리 |
|---|---|---|
| 1 | 「제안 제출」 API: 경로, 머리글, 본문. Aimbase 는 `run_id`, `change_id`, `proposal`(4절 `result` 모양)을 보낸다. 검증 실패는 4xx 로 답한다(그래야 단계가 실패하고 회신이 간다). 검증 통과면 제안을 등록하고 사람에게 승인 요청 통보를 보낸다 | submit 단계 |
| 2 | 「계약 활성화」 API: 경로와 본문. Aimbase 는 `run_id`, `change_id`, `contract_proposal` 을 보낸다 | activate 단계 |
| 3 | 회신 수신 API: 4절 본문을 받는 경로. 2절 `_callback.path` 에 실어 보낸다 | 회신 |
| 4 | 표본, 계약 조회 주소의 인증. 머리글 토큰이면 환경변수 이름 | repair 단계의 CLI 가 curl 로 받는다 |
| 5 | 3PLGW 주소: 59 와 운영 망 `aimbase-apps` 안쪽 | HTTP 연결 `bp-3plgw` 의 `baseUrl` |

받음(2026-11-09, 3PLGW T3-2 CR-3PLGW-094 2절): 1 `POST /api/v1/internal/poomgo-repair/changes/{change_id}/proposals`, 2 `POST .../changes/{change_id}/activate`, 3 `POST .../changes/{change_id}/result`, 4 머리글 `X-Internal-Service-Key`, 환경변수 `TPLGW_INTERNAL_KEY`, 5 59 `http://59.8.160.12:8187`, 운영 `http://bp-3plgw:8187`. 3PLGW 가 바란 승인 시한 72시간, `last_good_url` 404 허용, `result.pr.title` 은 반영했다.

## 7. 59 시험 값

- Aimbase 59 api: `http://59.8.160.12:8280`(바깥). 3PLGW 컨테이너가 Aimbase compose 망에 있지 않으면 바깥 주소를 쓴다
- 3PLGW 59: `http://59.8.160.12:8187`(HTTP 연결 `bp-3plgw` 의 `baseUrl`). 내부 키는 Aimbase 59 `.env` 와 `.env.runner-3plgw` 의 `TPLGW_INTERNAL_KEY`
- 테넌트 `bp_3plgw`, 워크플로우 `poomgo-change-repair`, 실행기 `cli-runner-bp-3plgw`, 연결 묶음 `cli-runner-bp-3plgw-rr`
- 소비앱 키는 설치 뒤 `secrets/bp-3plgw-api-key`. 컨타를 거쳐 3PLGW 창에 전한다

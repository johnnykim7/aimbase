# CR-163: 실행기가 대기 중인 CLI 출력을 읽다 다른 실행까지 멈추는 문제

- 발번: 2026-10-27
- 원본 요구사항: `docs/origins/원본_요구사항_CR163_실행기_대기_CLI_출력_읽기가_다른_실행을_멈춤_20261027.md`
- 요청: 컨타 3plcore-23636 브리핑. 사용자 10/27 14:55 /전승 ①「aimbase 에 별도 CR 을 내 원인을 재현해 고치고, 운영 설치(CR-162)는 별개로 진행」

- 규모: 소. 실행기가 CLI 출력을 읽는 스레드의 종류만 바꾼다. 새 API, 화면, 테이블, 설정이 없다
- 상태: 원인 확정, 로컬 수정 확인. 개발기 반영 대기(CR-161 앞 변경 커밋 뒤 빌드)

## 1. 문제

59 개발기 wes 실행기(aimbase-agent-wes, 16코어, Temurin 21.0.12.1)에서 10/27 14:24:46 에 시작한 wms-wave-plan-opinion 다섯 건이 5분을 넘겼다. 앞 회차(14:11, 14:20)는 27~75초였다.

| 시각(KST) | 실행기 기록 |
|---|---|
| 14:11:28~29 | 다섯 건 시작. 같은 초에 CLI 첫 출력(init)을 받음 |
| 14:20:29 | 다섯 건 시작. 같은 초에 첫 출력을 받음 |
| 14:24:46 | 다섯 건 시작. 첫 출력을 받지 못함 |
| 14:25:04 | 14:24 회차 CLI 다섯은 답을 끝냄(CLI 대화 기록) |
| 14:30:01 | 정리기가 14:11 회차 대기 CLI 하나(pid 66366)를 닫음. 같은 초에 14:24 회차 다섯 건의 첫 출력이 한꺼번에 들어옴 |
| 14:30:02~03 | 정리기가 14:11 회차 나머지 넷을 닫음 |

CLI 는 답을 다 만들었는데 실행기가 그 출력을 읽지 못하다가, 상관없는 대기 CLI 하나가 닫히자 읽었다.

## 2. 원인

1. 실행기는 CLI 하나마다 출력 읽기 둘(표준 출력, 오류 출력)을 가상 스레드로 띄운다(`ClaudeCliWorker.start`). 턴이 끝나도 CLI 는 다음 입력을 기다리며 살아 있고(정리기가 900초 뒤 닫는다), 읽기 둘도 그동안 파이프에서 기다린다.
2. JDK 의 프로세스 파이프 읽기는 synchronized 안에서 일어나(`ProcessPipeInputStream` 이 `BufferedInputStream` 하위 클래스다) 가상 스레드가 실행 자리(carrier)에서 내려오지 못한다. JDK 는 그만큼 자리를 보충하므로, 기다리는 읽기 하나가 자리 하나를 차지한 채 남는다.
3. 쉬는 자리는 30초씩 쉬면 하나씩 정리된다. 정리가 끝나면 남은 자리는 전부 기다리는 읽기다.
4. 새 가상 스레드가 들어올 때 쉬는 자리가 없고 전체 자리 수가 CPU 수 이상이면, JDK 는 자리를 새로 만들지 않는다(`ForkJoinPool.signalWork` 가 `deficit <= 0` 에서 멈춘다). 새 읽기는 줄에 선 채, 기다리는 읽기 하나가 끝나 자리가 날 때까지 돌지 못한다.
5. 59 는 14:11 회차 10개와 14:20 회차 10개로 기다리는 읽기가 20개가 되어 16을 넘었고, 14:24 회차 읽기 10개가 자리를 얻지 못했다. 14:30:01 에 pid 66366 이 닫혀 그 읽기가 끝나자 자리가 났고, 14:24 회차 읽기가 차례로 돌았다(돈 읽기가 다시 기다리면 JDK 가 자리를 보충하므로 이어서 풀린다).
6. 기다리는 읽기가 CPU 수에 닿으면 막히므로 대기 CLI 가 CPU 수의 절반이면 충분하다. 운영 chaws 실행기(8코어)는 대기 CLI 넷이면 걸린다. 계정을 나눠 써도 CLI 수는 같으므로 풀리지 않는다.

## 3. 재현

59 실행기 파일(md5 4922b20b010f6a66d48f30e626a34d9c)을 그대로 받아 맥(JDK 21.0.10, `-XX:ActiveProcessorCount=16`)에서 띄우고, 실제 CLI 대신 입력 한 줄마다 init, rate_limit_event, assistant, result 를 내고 다음 입력을 기다리는 스크립트를 썼다. 다섯 건씩 한 회차로 부르고 앞 회차 CLI 는 그대로 둔다.

| 순서 | 결과 |
|---|---|
| 회차 사이를 쉬지 않고 4회차(대기 CLI 20) | 매번 2.0~2.4초. 쉬는 자리가 남아 있어 막히지 않는다 |
| 3회차(대기 CLI 15) 뒤 약 3분 기다림 | 실행 자리 30개가 전부 기다리는 읽기, 쉬는 자리 0 |
| 그 상태에서 다섯 건 | 30초 동안 첫 출력 0건 |
| 앞 회차 실행 하나 취소(대기 CLI 하나 닫힘) | 같은 초(15:40:28)에 다섯 건의 첫 출력이 한꺼번에 들어옴 |

59 의 14:24~14:30 과 같은 모양이다.

## 4. 바꾸는 것

출력 읽기 둘을 가상 스레드에서 전용 플랫폼 스레드(데몬)로 바꾼다. 읽기는 CLI 가 사는 내내 파이프에서 기다리는 일이라 가상 스레드의 실행 자리를 쓸 까닭이 없다. 데몬이라 실행기 종료를 막지 않는 것은 가상 스레드 때와 같다.

바꾸지 않는 것

- 시간 제한(턴 600초, 정리기 900초)은 그대로 둔다. 막힘을 늦게 드러낼 뿐이다.
- `jdk.virtualThreadScheduler.parallelism` 같은 JDK 설정으로 자리 수를 늘리지 않는다. 막히는 문턱을 옮길 뿐이다.
- 정리기가 대기 CLI 를 900초 두는 것(CR-121)은 다음 턴을 빨리 받으려는 설계라 그대로 둔다.

플랫폼 스레드는 대기 CLI 하나에 둘이다. 실행기 하나의 대기 CLI 는 수십 개 수준이라 스레드 수 부담은 없다.

## 6. 시험과 개발기 반영

1. 단위시험 `ClaudeCliWorkerTest.cr163_output_readers_do_not_take_virtual_thread_carriers`. dev 는 CR-161 앞 변경(ChatRequest 등)이 커밋되기 전에는 platform-core 가 컴파일되지 않아, 그 커밋 위에서 돌린다.
2. 로컬. 59 실행기 파일에 고친 클래스만 끼운 사본과 고치기 전 파일을 같은 순서(다섯 건씩 4회차, 회차 사이 150초, 마지막 대기 CLI 20)로 돌렸다.

| 회차 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1 | 2.1초 | 2.1초 |
| 2 | 2.0초 | 2.0초 |
| 3 | 2.0~2.1초 | 2.0~2.1초 |
| 4 | 다섯 건 모두 60초 동안 첫 출력 0건 | 2.0초 |
| 끝난 뒤 실행 자리 | 30개, 전부 기다리는 읽기 | 0개(출력 읽기 40개는 모두 플랫폼 데몬 스레드) |

3. 개발기. CR-161 커밋 위에서 빌드해 `./deploy.sh agents` 로 실행기 전체를 올린다(실행기들은 한 파일을 같이 쓴다). 올린 뒤 bp-wms 창에 wms-wave-plan-opinion 다섯 번 재호출을 부탁해 앞 회차 시간(27~75초)으로 돌아오는지 본다.
4. 배포 전제. 59 실행기 Dockerfile 은 공용 폴더의 커밋되지 않은 판(psql, 문서 도구 설치)과 같고 커밋본에는 이 설치가 없다. 커밋본으로 올리면 wes 실행기가 DB 를 조회하지 못한다. 이 설치는 CR-162 정리 커밋에 들어 있으므로(컨타 회신 10/27) CR-163 은 싣지 않고, CR-161 커밋과 CR-162 정리 커밋 위에서 빌드한다.

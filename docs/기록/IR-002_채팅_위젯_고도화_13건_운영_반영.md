# IR-002 채팅 위젯 고도화 13건 운영 반영

- 일자: 2026-11-14
- 요청: 사용자 승인 2026-11-14 10:14 「(창 무관) 운영 반영, CR-185 창이 13건 묶음 운영 반영 계획을 짜서 올리고 승인 뒤 배포」 ①. CR-185 창이 완 처리되어 이 창이 맡았다.
- 대상: CR-177 ~ CR-189 (개발기 59 확인 완료, 운영 미반영)
- 운영: chaws (ubuntu@3.39.94.112, /home/ubuntu/aimbase). 우진비드 AWS(wjbid)는 위젯 화면이 없어 이 건 범위 밖이다.

## 결론

1. 13건만 떼어 운영에 올릴 수 없다. 13건이 운영에 없는 CR-161, CR-164, CR-165 코드 위에 쌓여 있어, 운영 가지(f7c02f4)에 옮기면 99개 커밋 중 48개가 부딪힌다. 59 에서 확인한 것은 origin/dev 그대로의 코드이다(59 api jar 클래스가 origin/dev 빌드와 같다).
2. 그래서 정석은 origin/dev 를 그대로 운영에 올리는 것이다. 이때 운영에 아직 승인되지 않은 CR-161, CR-164, CR-165, CR-168(설정 시드), CR-170 이 함께 실려 간다. 이 5건을 같이 승인해야 한다.
3. 그대로 올리면 안 되는 것이 네 가지 있어 배포 전에 먼저 고쳐야 한다(아래 「이슈」 1 ~ 4).
   - 운영 위젯 파일이 CR-185 마지막 고침 전 판이 된다.
   - CS 실행기의 Claude 프로세스 상한 설정이 빠진다.
   - 배포 뒤 문제가 생겨도 지금 운영 판으로 되돌릴 수 없다(옛 판이 새 DB 판을 보면 기동을 멈춘다).
   - 운영 nginx 에 공유 링크, 워크플로우 승인 구독, 음성 대화 길이 없다.
4. 운영에는 그림 연결, 음성 합성 연결, 받아쓰기 설정이 없어 CR-184(그림 만들기)와 CR-186(읽어 주기, 음성 대화)은 올려도 사용할 수 없다. 연결을 둘지는 사용자가 정한다.

## 이슈 (고치지 않고 컨타에 올린다)

1. 운영 위젯 파일이 오래된 판이 된다. chaws 빌드 작업 폴더에는 위젯 빌드 결과(dist)가 없어 jar 에 레포에 커밋된 위젯 파일이 들어간다. 그 파일(2170bae5, 57d8ab4 소스 빌드)은 CR-185 마지막 고침 31ced554 전 판이다. 새로 빌드하면 aimbase-chat.esm.js 에 승인 번호로 겹친 승인 카드를 거르는 부분이 생기고, 커밋된 파일에는 없다. dev 에 위젯 빌드 결과를 다시 커밋해야 한다. 59 위젯은 git 밖에서 다른 의존성으로 빌드되어 git 으로 재현되지 않는다.
2. dev 의 docker-compose.chaws.yml 에 CS 실행기 `AIMBASE_RUNNER_MAX_PROCESSES: "2"` 가 없다. 운영 가지(4b6a4b08)에만 있다. 이대로 올리면 상한이 0(무제한)이 되어 CS 실행기가 메모리 한도를 넘을 수 있다(CR-173 14절). dev compose 에 되살려야 한다.
3. 되돌릴 판이 없다. 운영 판 f7c02f4 의 Flyway 설정은 `ignoreMigrationPatterns("*:missing")` 만 두어 `*:future` 를 무시하지 않는다(FlywayMultiTenantConfig.java 42, 72, 97행, TenantMigrationRunner.java 201행). 이 배포로 높은 판이 DB 에 올라가면 옛 판은 기동 때 검증에서 멈춘다. 같은 문제를 dev 는 5300d984(CR-182)로 고쳤다. 운영 가지에 5300d984 를 얹은 되돌림 판을 미리 만들고 로컬에서 높은 판이 있는 DB 로 기동되는지 확인해 둬야 한다. 기동 멈춤 자체는 코드와 Flyway 규칙에서 읽은 것이고 실행해 보지는 않았다.
4. 운영 nginx(ai.banpoom.co.kr)는 `/widget/` 과 `/api/v1/chat/` 만 api 로 넘긴다. 다음 셋이 없다.
   - `/share/` (CR-182 공유 링크. CR-182 8절)
   - `/api/v1/workflows/runs/` (구독은 이번 배포 전부터 막혀 있었고, CR-185 승인과 거절도 이 길을 쓴다)
   - `/api/v1/chat/voice/stream` 의 웹소켓 업그레이드(CR-186 7절). 지금 `/api/v1/chat/` 블록은 Connection 을 비워 넘겨 업그레이드가 안 된다.
5. `chat.share.public-base-url` 이 운영에 없다. 비어 있으면 공유 링크를 만들 수 없다(ChatShareSettings.java 35 ~ 37행 usable). 운영 master 쓰기라 따로 승인이 필요하다.
6. 13건이 CR-161, CR-164, CR-165 에 기대고 있어 함께 실려 간다. CR-165 는 진행중이고, 운영에 이미 있는 음성 합성 길의 동작을 바꾼다(맥 엔진 먼저). 함께 실어 갈지, 13건만 운영 가지에 옮길지(새 이식 CR, 48개 충돌, 59 에서 시험하지 않은 조합)는 사용자가 정한다.
7. 운영에 그림 연결, 음성 합성 연결(tts_local, OpenAI), 받아쓰기 설정이 없다. CR-184, CR-186 은 올려도 503 이나 안내 문구로 끝난다. 연결을 둘지는 사용자가 정한다(CR-186 7절).
8. 서버 여유가 적다. /var/lib/docker 사용률 89%(남은 12G)에 LibreOffice 가 든 새 api 이미지와 pre 이미지 3개가 더해진다. api 메모리 한도 2g 에 지금 1001MiB 를 쓰고 있어 문서 변환이 몰리면 한도에 닿을 수 있다. 59 도 같은 2g 이다. 둘 다 추정이다.
9. 실행맵과 CR-186 은 「운영 반영은 건마다 따로 승인」이라 적혀 있고, 사용자 승인은 묶음 반영이다. 묶음 승인으로 건별 승인을 갈음하는지 확인이 필요하다.
10. 우진비드 AWS(wjbid)는 위젯 화면이 없어 이 계획에 넣지 않았다.

## 선택지

1. (권장) origin/dev 를 그대로 올린다. 59 에서 확인한 코드 그대로다. 이슈 1 ~ 4 를 dev 와 운영 가지에서 먼저 고치고, 함께 실려 가는 5건(CR-161, CR-164, CR-165, CR-168 시드, CR-170)을 같이 승인한다.
2. 13건만 운영 가지에 옮긴다. 함께 실려 가는 것은 없지만 48개 충돌을 푸는 새 이식 CR 이 필요하고, 59 에서 시험하지 않은 조합을 운영에 올리게 된다.

## 1. T1 요구사항

### 1.1 목적

스킬을 지시문 하나로 풀어 옮기지 않는다. 묶음을 그대로 올리고, Claude 든 다른 LLM 이든, API 연결이든 CLI 연결이든 같은 묶음을 같은 방법으로 쓴다.
특정 스킬 하나를 위한 기능이 아니라 어떤 스킬이 들어와도 같은 방법으로 받는다.

### 1.2 결정 (2026-10-12 22:30 사용자 결재, 원본 6절)

| 순번 | 정할 것 | 결정 |
|---|---|---|
| 1 | 진행 | 대규모로 진행, 설계서부터 |
| 2 | 같이 쓰는 범위 | 플랫폼 공용(모든 테넌트)과 테넌트 전용을 둘 다 둔다. 이름이 겹치면 테넌트 전용을 쓴다 |
| 3 | 판 관리 | 올릴 때마다 새 판을 남긴다. 워크플로우 단계는 판을 고정하거나 늘 최신을 쓴다 |
| 4 | 스크립트 실행 환경 | 스크립트만 도는 따로 떨어진 컨테이너. 비밀값과 바깥 인터넷 없이 작업장만 붙인다. 시간, 크기 상한은 설정값 |
| 5 | CLI 연결 | 세 모드 모두 Aimbase 통로로 같은 스킬 도구를 준다. 통로를 안 붙이던 NATIVE 에도 스킬 도구만은 붙인다 |
| 6 | 지금 지시문형 스킬 | 그대로 두고 묶음형과 함께 쓴다. 지금처럼 돌고 스킬 화면에 함께 보인다 |

결정 2 의 "앱 전용" 은 테넌트 전용으로 읽는다. 원본이 "여러 앱(테넌트)" 이라 적었고, 운영 테넌트(bidding_system, axopm_companyA)는 App 계층(CR-014)에 묶여 있지 않다(로컬 master tenants.app_id 실측).

### 1.3 범위 포함

1. 스킬 묶음 올리기. 테넌트 전용과 플랫폼 공용 두 곳. 올릴 때마다 새 판
2. 이름 해석. 테넌트 전용이 먼저, 판 지정이 없으면 가장 큰 판
3. 모델 도구 3개. `skill_open`(안내서와 파일 목록), `skill_read`(묶음 안 파일 하나), `skill_run`(스크립트 실행)
4. 스크립트 실행 컨테이너 `skill-sandbox`
5. 워크플로우 단계 지정. LLM_CALL 은 안내서와 지정 파일을 지시문에 붙이고, AGENT_CALL 은 목록을 보여주고 도구로 쓴다
6. CLI 연결 세 모드에서 같은 도구. NATIVE 에 스킬 도구만 있는 통로를 붙인다
7. 화면. 테넌트 스킬 화면에 묶음형 탭, 플랫폼 관리에 공용 스킬 화면, 워크플로우 스튜디오 단계 설정에 스킬 지정
8. 단계가 쓴 스킬과 판을 실행 기록(STEP_START 이벤트)에 남긴다

### 1.4 범위 제외

| 항목 | 이유 |
|---|---|
| 채팅 요청(채팅 API, 위젯)에서 스킬 지정 | 원본 7절의 쓰임이 워크플로우 단계뿐이다. 쓰는 곳이 생기면 같은 지정 칸을 채팅 요청에 연다. 도구 자체는 채팅에서도 이름으로 부를 수 있다 |
| 지시문형 스킬의 단계 지정, 묶음형으로 옮기기 | 결정 6. 지시문형은 지금처럼 `skill_invoke` 로 돈다 |
| 묶음별 패키지 설치(requirements.txt 등) | 실행 컨테이너는 바깥 인터넷이 없다. 필요한 패키지는 실행 컨테이너 이미지에 넣고 이미지를 다시 만든다 |
| App 계층(CR-014) 공용 스킬 | 쓰는 테넌트가 없다 |
| 묶음 원본 zip 내려받기 | 지금 쓰는 곳이 없다. 판의 파일은 화면과 API 로 볼 수 있다 |
| 스킬 앞머리의 allowed-tools 등 Claude Code 전용 칸 해석 | 다른 모델에 같은 뜻이 없다. 값은 저장만 하고 동작에 쓰지 않는다 |

### 1.6 비즈니스 규칙 (신규)

| ID | 규칙 |
|---|---|
| BIZ-118 | 스킬 묶음은 zip 이고 맨 위(또는 하나뿐인 최상위 폴더 바로 아래)에 SKILL.md 가 있어야 한다. 앞머리 name(소문자, 숫자, 하이픈, 64자 이하)과 description(설정 상한 이하)이 필수다. 하위 폴더 이름과 파일 종류는 정하지 않는다. 경로 이탈, 심볼릭 링크, 크기와 개수 상한 초과는 거부한다 |
| BIZ-119 | 같은 범위에 같은 이름을 올리면 새 판이 생긴다(1부터). 전체 내용이 직전 판과 같으면 새 판을 만들지 않는다. 판은 고치거나 지우지 않는다. 삭제는 비활성화이고, 다시 올리면 활성으로 돌아온다 |
| BIZ-120 | 이름 해석은 활성 테넌트 전용 묶음이 활성 플랫폼 공용 묶음보다 먼저다. 판 지정이 없으면 그 범위의 가장 큰 판을 쓴다. 지정한 판이 없거나 묶음이 비활성이면 그 단계는 실패한다 |
| BIZ-121 | 단계에 스킬 지정이 있으면 모델에게 보이는 목록과 스킬 도구 3개는 지정한 스킬과 판으로만 동작한다. 도구 허용 목록이 있는 AGENT_CALL 에는 스킬 도구 3개가 자동으로 더해진다. LLM_CALL 은 안내서와 지정 파일을 지시문에 붙이며 합계가 설정 상한을 넘으면 단계가 실패한다 |
| BIZ-122 | 스크립트는 실행 컨테이너에서만 돈다. 실행 컨테이너에는 비밀값과 바깥 인터넷이 없고, run 작업장 안의 파일만 실행하고 쓴다. 실행 시간과 출력 크기는 설정 상한을 따른다. 실행기는 파일 확장자로 정한다(.py, .js, .mjs, .sh). 작업장이 없는 호출은 거부한다 |
| BIZ-123 | CLI 연결은 AIMBASE, HYBRID, NATIVE 세 모드 모두 Aimbase 통로의 같은 스킬 도구를 쓴다. NATIVE 에는 스킬 도구만 있는 통로를 붙이며 다른 Aimbase 도구는 붙이지 않는다 |

## 2. T2 아키텍처

### 2.1 실행 순서 (AGENT_CALL, 어느 연결이든 같다)

| 순번 | 하는 일 | 하는 곳 |
|---|---|---|
| 1 | 단계 config 의 skills 를 이름 해석해 (이름, 범위, 판) 목록으로 고정하고 STEP_START 이벤트에 남긴다 | AgentCallStepExecutor, SkillCatalog |
| 2 | 지정 스킬의 이름과 설명을 시스템 메시지로 붙인다 | SubagentRunner |
| 3 | 모델이 `skill_open` 으로 안내서 본문과 파일 목록을 연다 | SkillOpenTool |
| 4 | 모델이 필요할 때 `skill_read` 로 파일 하나를 읽는다 | SkillReadTool |
| 5 | 모델이 `skill_run` 을 부르면 Aimbase 가 묶음을 run 작업장 `.skills/<이름>/v<판>/` 에 풀고 실행 컨테이너에 실행을 맡긴다 | SkillRunTool, skill-sandbox |
| 6 | 실행 결과(종료 코드, 출력, 바뀐 파일)를 도구 결과로 돌려준다 | SkillRunTool |

LLM_CALL 은 3~6 대신 안내서와 지정 파일을 시스템 지시문에 붙여 한 번 묻는다. 스크립트는 돌지 않는다.

### 2.2 연결 종류별 통로

| 연결 | 목록이 가는 길 | 도구가 가는 길 | 판 고정이 가는 길 |
|---|---|---|---|
| API (Anthropic, OpenAI, Ollama) | 시스템 메시지 | 도구 정의(getToolDefs) | ChatRequest 의 skillSet 을 ToolContext 로 |
| CLI AIMBASE | 시스템 메시지(첫 사용자 메시지 앞에 붙는 지금 방식, ClaudeCliWorker.java:402) | 기존 aimbase-server 통로(/mcp) | 러너 요청 skill_set, 통로 머리글 X-Aimbase-Skill-Set |
| CLI HYBRID | 같음 | 같음 | 같음 |
| CLI NATIVE | 같음 | 새 aimbase-skills 통로(/mcp-skills), 스킬 도구 3개만 | 같음 |

지금 NATIVE 는 MCP 설정을 비워 보낸다(ClaudeCliCommandBuilder.java:346). 지정이 있을 때만 aimbase-skills 하나를 넣는다. 지정이 없는 NATIVE 호출은 지금과 같다.

### 2.3 저장과 이름 해석

| 범위 | 저장 | 올리는 사람 |
|---|---|---|
| 플랫폼 공용 | Master DB `platform_skill_bundles` 외 2개 | Super Admin, `/api/v1/platform/skill-bundles` |
| 테넌트 전용 | Tenant DB `skill_bundles` 외 2개 | 테넌트 관리자, `/api/v1/skill-bundles` |

파일 내용은 DB 에 둔다. 묶음은 작고(계기 스킬 zip 70KB, 풀면 138KB), DB 에 두면 판과 파일이 한 트랜잭션으로 묶이고 로컬, S3 저장소 차이를 타지 않는다. 플랫폼 공용 워크플로우(master V9)와 같은 모양이다.

### 2.4 실행 컨테이너 skill-sandbox

| 항목 | 내용 |
|---|---|
| 이미지 | Python 3.12, Node 18, Chromium, 한글 글꼴(Noto CJK). 공통 패키지 pyhwp, python-docx, openpyxl, pillow, playwright(Python), docx(npm) |
| 연결망 | api 와만 닿는 내부 전용 망(compose `internal: true`). 바깥 인터넷 없음 |
| 볼륨 | api 와 같은 작업장 볼륨을 같은 경로로 붙인다(지금 사이드카와 러너가 하는 방식, docker-compose.prod.yml:75, 110). 다른 볼륨은 붙이지 않는다 |
| 환경변수 | 실행 컨테이너 자기 열쇠(SKILL_SANDBOX_API_KEY), 동시 실행 수, 작업장 뿌리 경로만. DB, LLM, 암호화 키는 넣지 않는다. 그래서 서버 `.env` 를 통째로 붙이지 않고 열쇠 한 줄만 넘긴다. 열쇠가 비면 실행 컨테이너만 기동을 거부한다 |
| 사용자 | uid 999. api 와 같아야 작업장 파일을 쓰고 읽는다(platform-core Dockerfile 의 고정 uid). gid 는 볼륨 접근에 필요 없고 이미지에 따라 999 가 이미 있어 자동 할당으로 둔다(platform-core 와 같음) |
| 자원 | 메모리 상한 2GB, CPU 2 (compose) |
| 브라우저 | Chromium 은 `PLAYWRIGHT_BROWSERS_PATH=/ms-playwright` 에 둔다. 실행 프로세스의 HOME 은 작업장 안이라 HOME 밑에 두면 찾지 못한다 |
| 소스와 배포 | `skill-sandbox/` (server.py, Dockerfile, tests). `./deploy.sh sandbox` 가 소스와 compose 를 보내고 이 서비스만 다시 만든다. 서버 `.env` 에 SKILL_SANDBOX_API_KEY 가 없으면 보내기 전에 멈춘다. api 가 새 망에 붙는 것은 api 를 다시 만들 때다(`./deploy.sh be`) |
| 로컬 | docker-compose.yml 서비스 skill-sandbox, 호스트 포트 18147. 맥의 `~/aimbase-workspace` 를 같은 경로로 붙인다. 내부 망에는 호스트 포트를 열 수 없어 로컬은 기본 망이다. 격리는 `docker network create --internal` 망에서 따로 본다 |
| 로컬 작업장 | 로컬 bootRun 의 작업장 뿌리를 `~/aimbase-workspace` 로 둔다(application-local.yml `aimbase.workspace`). 전에는 운영 경로 `/data` 를 그대로 써 맥에서 run 작업장을 만들지 못했다 |

계기 스킬의 스크립트가 쓰는 것: check_coverage.py(표준 라이브러리만), capture_diagram.py(playwright 또는 Chromium), convert_hwp.py(pyhwp, 없으면 pip 설치를 시도하는데 실행 컨테이너는 인터넷이 없으므로 이미지에 미리 넣는다), docx-build-reference.js(npm docx).

지금 `bash` 도구는 본체 컨테이너에서 돈다(tool-sdk-core BashTool, ProcessBuilder). 이번 CR 은 이를 바꾸지 않는다. 5.3 참고.

### 3.3 이름 해석과 판 (BIZ-120)

`SkillCatalog.resolve(name, version)`:

1. 테넌트 DB 의 활성 `skill_bundles` 에서 이름을 찾는다. 있으면 범위 TENANT
2. 없으면 Master DB 의 활성 `platform_skill_bundles` 에서 찾는다. 있으면 범위 PLATFORM
3. version 이 없으면 그 범위의 latest_version, 있으면 그 판. 없으면 오류

`SkillCatalog.list()`: 두 범위의 활성 묶음을 이름으로 합친다. 이름이 겹치면 테넌트 전용만 남긴다.

해석 결과는 `ResolvedSkill(name, scope, version, description)` 이다. 단계 시작 때 한 번 고정하고, 그 단계의 도구 호출은 고정된 판만 쓴다. 단계 중간에 새 판이 올라와도 그 단계는 바뀌지 않는다.

### 3.4 모델 도구

세 도구는 builtin 이고 `mcp.cli-exposed-tools` 에 더한다(V69 seed, McpExposurePolicy.DEFAULT_FALLBACK 도 같이). 그래서 API 경로와 CLI 경로가 같은 도구를 본다(CR-104, CR-110 불변식).

스킬 지정(SkillSet)이 있는 호출은 지정한 이름만 받는다. 지정이 없는 호출은 SkillCatalog.resolve 로 활성 묶음 아무거나 이름으로 받는다(BIZ-121).

`skill_open` (읽기 전용)

| 입력 | 설명 |
|---|---|
| name | 스킬 이름. 필수 |

결과 텍스트: 이름, 범위, 판, 묶음 위치(`.skills/<name>/v<판>/`, 작업장이 있을 때), 안내서 본문, 파일 목록(경로, 크기). 안내서는 "파일은 skill_read 로 읽고 스크립트는 skill_run 으로 돌린다" 는 안내와 함께 나간다. 안내 문구는 prompt_templates 키 `tool.skill_open.guide` (CR-036 방식, resources/prompts 폴백).

`skill_read` (읽기 전용)

| 입력 | 설명 |
|---|---|
| name | 필수 |
| path | 묶음 안 상대 경로. 필수 |
| offset | 시작 줄(1부터). 선택 |
| limit | 줄 수. 선택 |

텍스트 파일은 줄 번호를 붙여 돌려준다. 한 번에 `skills.read-max-bytes` 까지, 넘으면 잘렸다는 표시와 다음 offset 을 붙인다. 텍스트가 아니면 크기와 "skill_run 이나 작업장의 묶음 위치로 쓰라" 는 안내만 돌려준다.

`skill_run` (쓰기, 동시 실행 안전하지 않음)

| 입력 | 설명 |
|---|---|
| name | 묶음 스크립트를 돌릴 때 스킬 이름. 없으면 script 는 작업장 기준 경로 |
| script | 실행할 파일 경로. name 이 있으면 묶음 기준, 없으면 run 작업장 기준 |
| args | 문자열 배열. 선택 |
| timeout_seconds | 선택. 기본 `skills.script-timeout-seconds`, 최대 `skills.script-timeout-max-seconds` |

처리:

1. ToolContext.workspacePath 가 없으면 거부(BIZ-122)
2. 지정된(또는 해석한) 판의 파일을 작업장 `.skills/<name>/v<판>/` 에 쓴다. 다 쓴 뒤 `.complete` 표시 파일을 둔다. 표시가 있으면 다시 쓰지 않는다
3. script 의 최종 경로가 작업장 안인지 확인하고 확장자로 실행기를 고른다. 실행기 표는 실행 컨테이너가 가진다
4. 실행 컨테이너에 실행을 맡긴다(3.7)
5. 결과: exit_code, timed_out, stdout, stderr(각각 `skills.script-output-max-bytes` 에서 자름), changed_files(실행 중에 생기거나 바뀐 작업장 파일, 100개까지)

작업장 기준 script 는 모델이 file_write 로 만든 파일이다. 계기 스킬의 워드 조립(본문 작성 단계)이 이 길을 쓴다. 모델은 묶음 위치의 docx-style.js 를 불러 쓰는 조립 파일을 작업장에 쓰고 skill_run 으로 돌린다.

### 3.5 스킬 목록 메시지

지정이 있는 AGENT_CALL 에 SubagentRunner 가 시스템 메시지 하나를 더한다. 머리말은 prompt_templates 키 `skill.listing.header`, 항목은 `- <name>: <description>`.

API 경로와 CLI 경로가 같은 메시지를 받는다. CLI 는 시스템 메시지를 첫 사용자 메시지 앞에 붙여 보낸다(지금 방식).

### 3.6 워크플로우 단계 지정 (BIZ-121)

LLM_CALL, AGENT_CALL 단계 config 에 `skills` 를 받는다.

```json
"skills": [
  { "name": "ax-proposal", "version": 3, "files": ["references/01-rfp-analysis.md"] },
  { "name": "sam-gov-review" }
]
```

| 칸 | 설명 |
|---|---|
| name | 필수 |
| version | 선택. 없으면 최신(단계 시작 때 가장 큰 판) |
| files | 선택. 지시문에 미리 붙일 묶음 안 파일. 텍스트 파일만 되고, 없거나 텍스트가 아니면 단계 실패 |

한 단계(에이전트 하나) 안에서 같은 name 을 두 번 적을 수 없다.

고정은 단계 시작 때 한 번이다. 재시도는 같은 판을 쓰고, FOREACH 본문 단계는 항목 전부가 같은 판을 쓴다. 이름이나 판이 없으면 단계 실패다(BIZ-120).

LLM_CALL:

1. 단계 시작 때 해석하고 STEP_START 이벤트 payload 에 `skills: [{name, scope, version}]` 를 남긴다
2. 단계 system 뒤에 스킬마다 안내서 본문과 files 내용을 붙인다. 감싸는 틀은 prompt_templates 키 `skill.inline.wrapper`
3. 붙인 합계가 `skills.inline-max-bytes` 를 넘으면 단계 실패. 메시지에 BIZ-121 과 크기

AGENT_CALL:

1. 해석하고 STEP_START 이벤트에 남긴다(LLM_CALL 과 같음)
2. SubagentRequest 에 SkillSet 을 싣는다. SubagentRunner 가 목록 메시지(3.5)와 files 내용을 시스템 메시지로 붙인다. files 내용 합계도 `skills.inline-max-bytes` 를 넘으면 단계 실패
3. config.tools(허용 목록)가 있으면 skill_open, skill_read, skill_run 을 더한다
4. ChatRequest.skillSet 으로 ToolContext 까지 넘긴다(API). CLI 는 3.8

멀티 에이전트(`agents`) 모드는 에이전트 config 마다 skills 를 받는다.

WorkflowValidator: skills 가 배열이 아니거나 name 이 비었거나 같은 name 이 두 번 있거나 version 이 1 이상 정수가 아니거나 files 가 문자열 배열이 아니면 저장할 때 거부한다. FOREACH 본문 단계와 agents[].skills 도 본다. 이름과 판이 있는지는 실행 때 본다(판은 나중에 올라올 수 있다).

### 3.7 실행 컨테이너 API

`POST http://skill-sandbox:8300/run` (내부 망 전용, 머리글 `X-Sandbox-Key`)

요청:

```json
{
  "workdir": "/data/workspace/<run 작업장>",
  "script": "/data/workspace/<run 작업장>/.skills/ax-proposal/v3/scripts/check_coverage.py",
  "args": ["reqs.md", "draft.md"],
  "timeout_seconds": 120,
  "max_output_bytes": 65536
}
```

응답:

```json
{ "exit_code": 0, "timed_out": false, "stdout": "...", "stderr": "", "duration_ms": 812,
  "stdout_truncated": false, "stderr_truncated": false,
  "changed_files": ["out/coverage.md"], "changed_files_total": 1 }
```

| 규칙 | 내용 |
|---|---|
| 경로 | 심볼릭 링크를 푼 실제 경로로 본다. workdir 가 작업장 뿌리(`SANDBOX_WORKSPACE_ROOT`) 아래가 아니거나 뿌리 자체면 400, script 가 workdir 아래가 아니면 400 |
| 실행기 | `.py` python3, `.js` `.mjs` node, `.sh` bash. 그 밖은 400 |
| 환경 | 실행 프로세스 환경변수는 PATH, HOME(작업장 안 `.home`), LANG, NODE_PATH(전역 npm), PLAYWRIGHT_BROWSERS_PATH 만 |
| 시간 | 넘으면 프로세스 묶음을 죽이고 timed_out true |
| 동시 실행 | `SANDBOX_MAX_CONCURRENCY`(기본 2). 넘으면 기다린다 |
| 출력 | stdout, stderr 를 각각 max_output_bytes 까지만 받고 넘으면 `*_truncated` true. 잘린 글자 조각은 버린다 |
| 바뀐 파일 | 실행 전후 workdir 를 비교해 만들거나 바꾼 파일을 workdir 기준 경로로 최대 100개, 전체 수는 changed_files_total |
| 끝난 뒤 | 정상 종료여도 프로세스 묶음을 죽인다. 스크립트가 남긴 백그라운드 자식이 응답을 붙잡지 않게 한다 |
| 거부 | 열쇠가 틀리면 401, 요청이 잘못되면 400 `{"error": "..."}`. 시간 상한과 출력 상한은 컨테이너 최대값(SANDBOX_MAX_TIMEOUT_SECONDS 600, SANDBOX_MAX_OUTPUT_BYTES 1MiB)으로 줄인다 |

api 쪽 설정(application.yml, 환경변수): `aimbase.skill-sandbox.url`(SKILL_SANDBOX_URL, 운영 `http://skill-sandbox:8300`, 로컬 `http://localhost:18147`), `aimbase.skill-sandbox.api-key`(SKILL_SANDBOX_API_KEY), `connect-timeout-seconds`(5), `response-grace-seconds`(30, 시간 상한에 더해 응답을 기다림). 주소와 열쇠는 환경마다 달라 global_config 가 아니라 환경설정에 둔다. 스크립트가 0 이 아닌 코드로 끝난 것은 도구 실패가 아니라 결과다. 실행 컨테이너에 닿지 못하거나 거부되면 도구 실패다.

### 3.8 CLI 통로 (BIZ-123)

1. ClaudeCliRunnerClient 가 요청 body 에 `skill_set: [{name, scope, version}]` 를 싣는다(지정이 있을 때만)
2. 러너(ClaudeCliWorker)가 aimbase-server 항목 머리글에 `X-Aimbase-Skill-Set`(JSON 을 base64url 로)을 넣는다. CR-117 의 작업장 경로 머리글과 같은 자리다
3. NATIVE 이고 skill_set 이 있으면, MCP 설정을 비우지 않고 `aimbase-skills` 항목 하나(같은 열쇠, 같은 머리글)만 넣는다. 주소는 aimbase-server 주소가 `.../mcp` 로 끝나면 `.../mcp-skills`, 아니면 호스트 바로 아래 `/mcp-skills` 다. 이때 `--allowedTools` 에도 `mcp__aimbase-skills__<스킬 도구>` 이름을 더한다
4. AgentIdRequestFilter 가 머리글을 풀어 RequestContext 에 두고, ServerMcpToolDispatcher 가 그것으로 ToolContext.skillSet 을 채운다. 머리글이 깨졌으면 400 이다. 최신 판으로 조용히 넘어가지 않는다
5. 새 통로 `/mcp-skills`: 두 번째 McpSyncServer 와 Streamable 전송. ToolRegistry 의 skill_open, skill_read, skill_run 만 등록한다. SecurityConfig 에 `/mcp-skills/**` 인증을 `/mcp/**` 와 같게 더한다. 호출은 ServerMcpToolDispatcher 를 그대로 탄다
6. 두 McpSyncServer 모두 `immediateExecution(true)` 로 도구를 요청 스레드에서 돌린다. SDK 기본값은 boundedElastic 스레드로 넘기므로 필터가 채운 TenantContext 와 RequestContext(작업장 경로, 스킬 지정)가 빠진다. 그대로 두면 스킬 도구가 테넌트 DB 를 못 찾고, 고정한 판 대신 최신 판을 연다. Streamable 서블릿 전송은 doPost 안에서 응답이 끝날 때까지 block 하므로 요청 스레드에 그대로 남는다
7. skill_set 이 있는데 러너 MCP 설정에 aimbase-server 항목(주소 포함)이 없으면 세 모드 모두 워커 기동을 실패시킨다(BIZ-123). 스킬 도구 없이 돌면 모델이 지정과 무관한 답을 낸다. 실패해도 run 의 워커 자리는 돌려준다

워커는 기동 때의 MCP 설정을 계속 쓴다. AGENT_CALL 은 단계마다 자식 세션이라 단계마다 새 워커가 뜨므로 단계별 지정이 섞이지 않는다.

## 5. 영향과 남은 위험

### 5.1 영향

| 대상 | 영향 |
|---|---|
| 지금 지시문형 스킬, skill_invoke | 없음 |
| 스킬 지정이 없는 워크플로우와 채팅 | 도구 목록에 스킬 도구 3개가 늘어난다. 그 밖은 같다 |
| CLI NATIVE | 지정이 없으면 같다 |
| 서버 MCP `/mcp` 의 모든 도구 | 요청 스레드에서 돈다(3.8 6). 지금까지는 다른 스레드에서 돌아 테넌트와 작업장 경로가 빠졌고, 테넌트 DB 를 쓰는 도구가 제 DB 를 보지 못했다. 이번에 바로잡힌다 |
| 운영 compose | skill-sandbox 서비스와 내부 망이 하나씩 는다. api 가 그 망에 더 붙는다 |

### 5.2 트레이드오프

| 고른 것 | 잃는 것 |
|---|---|
| 파일을 DB 에 둔다 | 큰 묶음(수십 MB)에는 맞지 않는다. 상한 20MB 로 막는다 |
| 실행 컨테이너에 인터넷이 없다 | 스크립트가 실행 중에 패키지를 받거나 웹을 부를 수 없다. 패키지는 이미지에 넣는다 |
| 작업장에 묶음을 푼다 | run 작업장마다 묶음 사본(계기 스킬 138KB)이 남는다. 지금 run 작업장을 지우는 정리 작업은 없다(ArtifactGcScheduler 는 out/ 만 본다) |

### 5.3 남은 위험

1. 지금 `bash` 도구는 본체 컨테이너에서 돌고 mcp.cli-exposed-tools 에 들어 있다. 모델이 skill_run 대신 bash 로 스크립트를 돌리면 실행 컨테이너를 거치지 않는다. 이번 CR 은 안내 문구로 skill_run 을 쓰게 하고, bash 를 실행 컨테이너로 옮길지는 따로 정한다
2. HYBRID 와 NATIVE 의 CLI 는 자기 Bash 도구가 있어 작업장의 `.skills/` 스크립트를 직접 돌릴 수 있다. 그 경우 러너 컨테이너의 패키지로 돌아 결과가 다를 수 있다
3. 실행 컨테이너 이미지에 없는 패키지를 쓰는 스킬은 올라가도 스크립트가 실패한다. 올릴 때 미리 잡지 않는다
